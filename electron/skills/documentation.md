## Overview

Warroom is a cross-platform desktop application built for competitive debaters. Primarily designed for policy debate but also supports Public Forum (PF) and Lincoln-Douglas (LD). It centralises everything a debate team needs during prep and at tournament: case management, evidence cards, opponent scouting, round tracking, live tournament monitoring, team chat, and Warroom AI.

Runs as a native Electron app on macOS and Windows. All core data is stored locally (no account required for prep features); collaborative features (chat, sharing) use Supabase for real-time sync.

### Process architecture

The app follows Electron's two-process model. `electron/main.ts` is the main process — it handles file I/O, secure storage, all network requests to external APIs (Tabroom, OpenCaselist, Debate Land, Gemini, Google Drive), and the Tabroom monitor background worker. `electron/preload.ts` exposes a `window.warroom` IPC bridge to the renderer. The renderer (`src/`) is a React SPA that never makes direct network calls.

## Data Model

All local data lives in a single `DB` object (defined in `src/types.ts`) persisted as `userData/warroom/db.json`.

| Entity | Key Fields |
|--------|-----------|
| Case | id · name · side (aff\|neg) · blocks[] · shared? |
| Block | id · caseId · title · type · cards[] · createdAt · updatedAt |
| Card | id · blockId · tag · cite · body · year · flagged · createdAt |
| Opponent | id · teamName · school · teamId · caselist · notes · disclosures · roundsAgainst[] · stats · tabroom_entry_id |
| Tournament | id · name · date · start · end · location · event_type · rounds[] · tabroom_id · tabroom_event_id · tabroomEntryCode |
| Round | id · tournamentId · number · side · opponentId · room · time · result · notes · judgeNotes · argsRead[] · argsWorked[] · argsFailed[] · judgeName · judgeParadigm · autoFilled · isBye |

Relationships use string ID references (e.g. `Block.cards` is an array of Card IDs). The DB root also stores `manualWins` and `manualLosses` for adjusting the W/L record beyond round-derived totals.

## Navigation

Navigation is view-stack-free: one active `View` at a time, stored in Zustand. The sidebar provides top-level navigation to everything — Cases, Tournaments, Scouting, Cards, Google Drive, Flow, Speech doc, Chat, and Topics are all reachable at once; there's no separate mode to switch between. Views are rendered by a `Router` function in `App.tsx`. Three "persistent" webviews (FindCards, OpenEv, AgentSearchViews) are always mounted but hidden so they don't reload on navigation.

## Undo Toasts

A shared `pushUndoToast(message, onUndo)` action on the Zustand store (`appStore.ts`) drives a
bottom-left toast (`UndoToast.tsx`, mounted once in `App.tsx`, mirrors `AiErrorToast.tsx`'s
pattern but bottom-left instead of bottom-right): "Deleted 'X'" plus an Undo button, auto-dismissing
after 3.5s. Wired up on the major destructive deletes: cases, blocks, cards, tournaments, rounds,
opponents, flows, flow sheets (reuses the flow editor's own undo-history stack via `undo()` rather
than a separate snapshot), saved AI chats, saved impact calc entries, impact library entries, and
folders. Deliberately NOT wired up on chat/DM message deletion (syncs live to other users — a
delayed-looking soft-delete would read as inconsistent) or flow column/arrow deletes (too
fine-grained during active flowing).

Each delete site snapshots the relevant state right before mutating it, then passes a closure that
restores that snapshot as the `onUndo` callback. For anything backed by the main `db` object,
**the snapshot must be `structuredClone(db)`, not a bare reference** — the existing delete-reducer
convention across the app (`const next = { ...db }; delete next.cards[id];`) only shallow-copies
the top-level `db` object, so `next.cards`/`next.blocks`/etc. are the SAME nested object as
`db.cards`/`db.blocks`; mutating them in place would silently corrupt a bare `db` reference held
for undo. Non-db state (flows_index + `flow_data_${id}` in `window.warroom.storage`, the Gemini
conversation list + per-conversation history in localStorage, impact calc saves) is snapshotted the
same way at its own storage layer. The Impact Library (Supabase-backed) has no restore-by-id API,
so its undo re-submits the same content as a new row (new id, votes reset) — best effort, not a
true restore.

## Global Search (⌘K)
A command-palette search (`SearchPalette.tsx`) opens on **⌘K / Ctrl K** or via the Search bar below Home in the expanded sidebar. State lives in `useApp` (`searchOpen`, plus handoff fields `pendingSearchQuery`, `pendingFindQuery`, `pendingDisclosureQuery`). The index and search live in `src/lib/searchIndex.ts` using Fuse.js (title weight 0.7, haystack 0.3, threshold 0.38).

**Indexed entry types**: cases (name + OC source + `searchKeywords`), speech docs (file name + cached keywords), flows (name + every cell), opponents (team/school/notes + disclosure titles — file names only, never contents), judges (name/institution/paradigm), tournaments, current topics, and AI chats (full history). Results are grouped by type, max 4 per group.

**Keyword distillation**: on launch, `extractKeywords(text, DOC_KEYWORD_CAP, priorityText)` distills up to `DOC_KEYWORD_CAP = 2000` frequency-ranked content keywords per case and speech doc (stopwords + 1–10 filtered; numbers >10 kept) — but `DOC_KEYWORD_CAP` is a floor for that frequency-ranked portion, not a hard ceiling. `priorityText` (every heading + cite line — tagline, author, date, publication — computed by `extractDocxPriorityText` in `electron/main.ts`, reusing the same tag/cite detection as `speechdoc:extract`; see `DEBATE_DOC_STRUCTURE.md` §2) is tokenized separately and every distinct meaningful word from it is guaranteed included ahead of the frequency-ranked words, even if that pushes the total above 2,000 — a tag mentioned once shouldn't lose to a body word repeated 50 times. `fs:extractDocxText` returns both `text` (mammoth flat text, used for frequency ranking) and `priorityText` (docx-only; empty for non-docx files). Cases cache to the DB `Case.searchKeywords`/`searchSig`; speech docs cache to localStorage (`warroom-speechdoc-keywords`) keyed by `{ size, ver }`. `DOC_KEYWORD_VERSION` bumps invalidate all caches (bumped to 3 when priority-text guarantee landed). The palette self-heals via `refreshSpeechDocKeywords()` on open.

**Handoff**: opening a case/speech-doc result sets `pendingFindQuery` (auto-opens the in-doc find on the term); an opponent result sets `pendingDisclosureQuery` (auto-scrolls + highlights the disclosure title). The footer runs external searches (Logos / Google Scholar / Open Evidence) by setting `pendingSearchQuery` and navigating. Warroom AI exposes the same data search via the `search_warroom` agent tool (see AI Help Guide).

**In-page find**: the Documentation and User Manual pages use a shared `useInPageFind` hook (`useInPageFind.tsx`) — ⌘F / Ctrl F opens a find bar that paints matches via the CSS Custom Highlight API (no DOM mutation). The User Manual view (`UserManual.tsx`) renders `electron/skills/user_manual.md` with `react-markdown`, builds its TOC from `##` headings, and shows an "Ask Warroom AI" hint pointing at the title-bar AI button.

## Keyboard Shortcuts (⌘/)
**⌘/ / Ctrl+/** opens `ShortcutsOverlay.tsx` — the full, organized shortcuts list for the app, also reachable from Settings → Keyboard Shortcuts. Purely client-side: a static `GROUPS` array (title + `{ id?, keys, label }[]`), no IPC, `⌘`/`Ctrl` labels picked off `window.warroom.platform`. State is `useApp`'s `shortcutsOpen`/`setShortcutsOpen`, mirroring the search palette's `searchOpen` exactly (same backdrop + card styling, Esc-to-close, mounted unconditionally in `App.tsx` since the component self-guards on `shortcutsOpen`). The global `⌘K`/`⌘/` listener lives in `App.tsx` alongside the search-palette one.

Groups: **Global** (⌘K search, ⌘/ this list, Esc closes any overlay), **Find on a page** (⌘F), **AI panel & team chat** (Enter/Shift+Enter/@/Esc — `Chat.tsx` and `GeminiPanel.tsx` share the same composer conventions), **Speech doc viewer** (⌘⌥M comments on the selected text, Google Docs' own binding — `doc-insert-comment` in `shortcutPrefs.ts`), and **Flow editor** (formatting, undo/redo, arrow-drawing, sheet switching, cell navigation — see the Flows section below for the full list). **Keep this in sync**: whenever a new global or component-level shortcut is added anywhere in the app, add it to `GROUPS` in `ShortcutsOverlay.tsx`, the "Keyboard Shortcuts" section of `user_manual.md`, and this section — grep `metaKey || e.ctrlKey` across `src/` to enumerate every shortcut currently wired up.

**Disabling & rebinding**: `src/lib/shortcutPrefs.ts` is the single source of truth. `DEFAULT_BINDINGS: Record<string, KeyBinding>` (`{ mod, shift, alt, key }`) holds the default combo for every rebindable id — `global-search`, `shortcuts-overlay`, `find-page`, `flow-bold`, `flow-italic`, `flow-underline`, `flow-strike`, `flow-highlight`, `flow-undo`, `flow-redo`, `flow-link`, `flow-sheet-new`. Two ids are disableable-only (not in `DEFAULT_BINDINGS`, so not rebindable — they're multi-key groups, not a single combo): `flow-move-row` (⌘↑/⌘↓ pair) and `flow-sheet-switch` (⌘1–9 range).

Two `localStorage` keys back this: `warroom-disabled-shortcuts` (a `Set<string>` of disabled ids) and `warroom-shortcut-bindings` (a `Record<string, KeyBinding>` of per-user overrides). `getEffectiveBinding(id)` returns the override if set, else the default. The single function every consumer calls is `matchesShortcut(e, id)` — checks disabled state, then compares the event against the effective binding — replacing the old pattern of each handler hand-rolling its own `e.metaKey`/`e.key` comparison. `matchesShortcut` and `bindingFromEvent` accept a structural `KeyEventLike` type (not `KeyboardEvent` directly), since `FlowView.tsx`'s per-cell handler receives React's synthetic `KeyboardEvent<HTMLDivElement>` while every other consumer uses a native `window.addEventListener('keydown', ...)` handler.

Call sites: `global-search`/`shortcuts-overlay` in `App.tsx`; `find-page` in `useInPageFind.tsx`, `useWebviewFindInPage.tsx`, `SpeechDocViewer.tsx`, `Settings.tsx`, and `FlowView.tsx`'s global handler (one id, several call sites — ⌘F is one conceptual feature). `useWebviewFindInPage.tsx` is the webview variant (Logos/Open Ev/Google Scholar): a `<webview>`'s content is a separate renderer document, invisible to `useInPageFind.tsx`'s CSS-Custom-Highlight DOM walk, so it goes through Electron's native `webview.findInPage()`/`found-in-page` instead — same `{open, query, idx, count, step, close}` shape, so it renders the same `<FindBar>`. Gated by an `active` flag per call site (`view.kind === 'logos' | 'open-ev' | 'google-scholar'`) since these three webviews stay permanently mounted (just `display:none`'d) to avoid reloading on navigation — without that gate, one ⌘F press would fire in all three at once. The rest of the ids are in `FlowView.tsx`'s per-cell `handleKeyDown` and global handler. `flow-redo` previously also accepted `⌘Y` as a hardcoded alternate — removed when rebinding landed, since a dual-default doesn't fit the one-binding-per-id model; it's `⌘⇧Z` only now (rebindable like everything else). `flow-link` previously matched `⌘L` regardless of Shift state (a latent inconsistency vs. bold/italic/underline, which always required `!shiftKey`) — `matchesShortcut` now requires an exact match against the binding's `shift` flag, so `⌘⇧L` no longer also triggers it.

The UI (`ShortcutsOverlay.tsx`) keeps disabling and rebinding as two fully separate gestures, no checkboxes: clicking the `<Kbd>` badge itself (now a `<button>` when `s.id` is set) toggles disabled state — hover shows a faint `currentColor` strikethrough line drawn across the badge via an absolutely-positioned overlay span (not `text-decoration`, so it reads as a line through the *whole* bubble, not just the glyphs), and a disabled badge gets a persistent red tint (`color-mix(... var(--neg) 16%, var(--bg-input))`), red border, and full-opacity red strikethrough. A separate `EditBinding` pencil button to the shortcut row's left starts a rebind — `onClick` sets `recordingId`, which mounts a capture-phase (`addEventListener('keydown', onKey, true)`) listener that treats the next non-modifier-only keydown as the candidate binding. `isBindingValid` rejects anything without `mod` or `alt` set — Shift alone isn't accepted, since Shift+letter is just typing a capital letter, and this listener is live while a flow cell could be focused. `findConflict` rejects a combo already claimed by another *enabled* shortcut and names it in the error shown in place of the key badges. Esc while recording cancels the recording (not the overlay); a second Esc then closes it. A customized id (`hasCustomBinding`) shows a low-opacity "reset" text link (hover-revealed) that calls `resetBinding(id)`. `rebindable` (an id present in `DEFAULT_BINDINGS`) gates whether the pencil button renders at all; `s.id` alone (rebindable or not) gates whether the badge is clickable for disable, so `flow-move-row`/`flow-sheet-switch` get a disable click but no pencil.

Both `shortcutPrefs.ts` localStorage keys — `warroom-disabled-shortcuts` and `warroom-shortcut-bindings` — are in `SETTINGS_LOCALSTORAGE_KEYS` (`settingsExport.ts`), so a full Settings export/import (Settings → Import/Export Settings) carries custom rebindings and disables across a reinstall or a second machine, same as every other listed preference.

**Correctness note**: `ShortcutsOverlay` never unmounts (mounted unconditionally in `App.tsx`, self-guards on `shortcutsOpen` by returning `null`). The effect that resets `recordingId` on open is keyed on `shortcutsOpen` and **must also fire on close** — otherwise closing the overlay mid-recording via the backdrop or × button (anything other than Escape) would leave the capture-phase listener attached indefinitely, since nothing else would ever null out `recordingId` to trigger its cleanup. Preserve that early-return-clears-state branch if this file is touched again.

`⌘/` (`shortcuts-overlay`) is itself disableable/rebindable, but Settings → Keyboard Shortcuts calls `setShortcutsOpen(true)` directly, bypassing the check — so disabling or rebinding it never locks a user out of the overlay that would let them undo that.

## Cases & Blocks

Cases are the top-level unit of prep — an aff or neg position. Each case contains **blocks** (e.g. "T-Topicality", "Heg DA", "2AC vs DA"). Blocks hold individual evidence **cards** (tag + cite + body text + year).

### Card extraction
Cards can be imported from a `.docx` file via AI extraction. The main process parses the file with mammoth, then sends the text to Warroom AI (using the `extractCards` IPC handler) which returns structured `{ tag, cite, body, year }` objects. The cards are created in the selected block. Prompt template: `electron/prompts/card_extraction.txt`.

### Block suggestions
On the Mission Brief (round view), Warroom can suggest which blocks to read against an opponent's positions using `suggestBlocks` — Warroom AI compares the opponent's disclosed arguments against your block list and returns a ranked selection. Prompt template: `electron/prompts/suggest_blocks.txt`.

## Cases Grid & Folders

Clicking the **Cases** title in the sidebar opens the `{ kind: 'cases-grid'; folderId?: string }` view — a full-screen grid of every case *and* every imported speech doc, each drawn as a Google-Docs-style first-page preview.

`buildCaseItems(db)` (`src/utils/caseItems.ts`) flattens the three sources that live in different places into one `CaseItem` list:

- `case` — built from blocks, lives in `db.cases`. No docx behind it.
- `oc-case` — an OpenCaseList import. Also in `db.cases`, but backed by real docx bytes via `ocSource`.
- `speech-doc` — a `.docx` you opened. Lives only in the `warroom-speech-doc-recents` localStorage list, not the db.

### The folder model

Folders live in `src/utils/caseFolders.ts` and persist through `window.warroom.storage` under the `case_folders` key — not localStorage, because this is durable library structure rather than view state.

`CaseFoldersData` is two fields:

- `folders` — a flat array of `{ id, name, parentId, createdAt }`. `parentId: null` means top level; nesting is arbitrary depth.
- `assignments` — a map of `itemKey → folderId`. An item with no entry sits at the top level.

Item keys are namespaced so one map can address either bucket: `case:<id>` for cases and `doc:<path>` for speech docs (`itemKeyForCase` / `itemKeyForDoc`).

**A folder is only a label.** Filing something into one writes an assignment and nothing else — it never moves, copies, renames, or deletes the underlying file on disk or the record in `db.cases`. The whole folder structure can be thrown away without losing a single document.

Consequently **deleting a folder keeps its documents**: `deleteFolder` re-parents its subfolders and reassigns its items to the deleted folder's parent (or back to the top level), so the only thing lost is the grouping. `resolveItemFolder` is defensive in the same spirit — an assignment pointing at a folder that no longer exists resolves to the top level rather than stranding the document somewhere unreachable.

Every mutation (`createFolder`, `renameFolder`, `deleteFolder`, `moveFolder`, `moveItem`) is **pure** and returns a new `CaseFoldersData`; callers apply it through the `useCaseFolders()` hook's `update((d) => moveItem(d, key, folderId))`. Writes broadcast a window event, so the grid and the sidebar tree — both consumers of the same hook — re-render together in the same tick. `moveFolder` refuses a move into the folder's own subtree (`isSelfOrDescendant`) since that would orphan it.

### Sidebar tree

The sidebar's Cases section mirrors the same state as a nested tree. Top-level folders come from `childFolders(folders, null)`; expanding one reveals its subfolders recursively plus the items assigned to it, and the loose list underneath holds only items whose `resolveItemFolder` is `null`. Expanded folders persist in localStorage under `sidebar-cases-folders-open`.

A folder row navigates to `{ kind: 'cases-grid', folderId }`; the section title itself opens the grid at the top level (the `+` button still opens the speech-doc view). Items and folders are HTML5-draggable onto folder rows to file them, and dropping anywhere that isn't a folder row falls through to a top-level drop zone, which is how something gets un-filed.

### Page previews

Items backed by real docx bytes (speech docs and `oc-case` imports) get a **real first page**: the docx is rendered with `docx-preview` using `breakPages: true`, and only page one is kept and scaled down into the tile. Because that render is expensive, the result is cached in localStorage under `warroom-case-preview-<key>`, keyed by the same namespaced item key as the folder assignments — so a revisit is instant and offline.

Block-built `case` items have **no docx behind them**, so there is no page to render. Their tile is **synthesized** instead — a page-shaped mock laid out from the case's own tags and cites — so the grid reads as one consistent wall of documents rather than a mix of pages and placeholders.

### Cross-view drag-and-drop

The sidebar tree and the grid are separate React trees, so a drag started in one has no way to see the other's local component state (drag-in-progress highlighting, etc.) — the only thing both sides can read is the native HTML5 `DataTransfer`. `ITEM_DRAG_MIME` / `FOLDER_DRAG_MIME` (`caseFolders.ts`) are the shared MIME strings both `Sidebar.tsx` and `CasesGrid.tsx` write on `dragstart` and read on `drop`, so a drag that starts in either tree is understood by both.

The subtler half of the fix is on `dragover`: a drop only fires if `dragover` calls `preventDefault()`, and each tree's own `canDrop` check originally required *local* drag state to be set — which is never true for a drag that started in the other tree. Both `onDragOverTarget` (Sidebar) and `handleDragOver` (CasesGrid) now fall back to inspecting `e.dataTransfer.types` (readable during `dragover`, unlike `.getData()`, which only resolves at `drop`) whenever there's no local drag state, so a cross-tree hover is still accepted. The one thing that can't be checked until `drop` is whether a folder is being dragged onto its own descendant — `moveFolder` already refuses that internally, so the drop safely no-ops rather than orphaning the subtree.

### Multi-select and bulk actions

Cmd/Ctrl+click toggles an item into a `Set<string>` of selected keys (`Sidebar.tsx`'s `CasesSection`, `CasesGrid.tsx`'s `ItemTile`) without navigating — the click is intercepted in the capture phase (`onClickCapture`, checking `e.metaKey || e.ctrlKey`) so it never reaches the item's own `onClick`. A selection bar appears with **Move to** (every folder, `flattenFolders` + `folderTrail` breadcrumb labels) and **Delete**, both folding over the selected keys via `update`.

Right-click (or a hover "⋯" button in the grid) opens the same three actions — **Move to**, **Rename**, **Delete** — for a single item, in both the sidebar (`NavItem`'s `moveOptions` prop) and the grid (`ItemMenu`). Deleting a `case`/`oc-case` and deleting a `speech-doc` are genuinely different operations (db mutation vs. localStorage recents entry), unified behind two small exported helpers in `caseItems.ts` — `deleteCaseAndBlocks(db, caseId)` and `removeFromRecents(path)` / `renameInRecents(path, name)` — so the sidebar, the grid, and any future bulk-action UI can't drift out of sync on what "delete a case" actually means.

### Importing a whole folder of docx files

`dialog:openFolderOfDocx(extensions?: string[])` (main process) opens a native directory picker, recursively walks the chosen folder (`fs.readdir` with `withFileTypes`, skipping dotfiles/dirs and `node_modules`, capped at 2000 files as a safety net) for files matching `extensions` (default `['docx']`), and returns `{ folderName, paths }` — `null` only on cancel; an empty `paths` array is a valid, distinguishable "no matches found" result. Every found path is trusted via `trustPath`/`persistTrustedPath`, the same anchor a file dialog provides, before the renderer ever sees it. `Onboarding.tsx`'s "import your prep" step passes `['docx', 'xlsx']` to pull in both speech docs and flows from one folder walk.

`SpeechDocViewer.tsx`'s `pickFolder()` calls this, batch-adds every result to recents (same `addRecents` path multi-file import uses), then creates a new `CaseFolder` named after the picked directory (`createFolder(data, folderName, null)`) and files every imported doc into it (`moveItem`) in one `useCaseFolders().update()` call — so the whole batch lands in one new, correctly-named folder rather than at the top level.

### Sharing a whole folder

A **Share folder** tile action (`CasesGrid.tsx`'s `FolderTile`, alongside Rename/Delete — same reused-across-`FlowsGrid` component, so its new `onShare?` prop is optional and left unset for Flow folders, which keep their own live-collab share model) opens `SharePanel` in a new multi-item mode rather than the single `type`/`id`/`getData` mode every other share site uses. `itemsInFolderRecursive(folders, items, folderId)` (`caseItems.ts`) collects every case/oc-case/speech-doc filed under the folder **and its subfolders** (via `descendantFolderIds`, the same set `deleteFolder`'s cascade logic already needs) — sharing a folder means the whole subtree, not just its direct contents. `CasesGrid.tsx`'s `folderShareItems()` maps each into a `ShareItem` (`{ type, id, name, getData }` — exported from `SharePanel.tsx`), reusing the *exact* payload shapes the single-item share sites already build: `speech-doc` reads file bytes via `window.warroom.fs.readFileBytes`, same as `SpeechDocViewer.tsx`'s own share button; `case`/`oc-case` both share as `type: 'case'` with `{ case, blocks }`, same as `CaseView.tsx`'s.

`SharePanel`'s `handleShare` branches on whether `items` was passed: multi-item builds one `attachments` array (every item individually encrypted with the team key, same `encryptAttachmentData` call as before) and sends it as a **single message** per recipient/room — the recipient sees one message with N attachment chips, not a flood of separate shares. Single-item share is unchanged, still exactly one attachment. `type`/`id`/`getData` are optional on `SharePanel`'s props specifically to make room for this — a folder share has no single id/type of its own, just its `name` (used for the header and the "Shared folder …" message text) and its `items`. Marking cases `shared: true` after sending loops over every `case`-typed item instead of touching a single id. An empty folder disables the Share button and shows an inline "nothing to share" note rather than silently no-op'ing.

## Cards (Card Library)

The Cards view (sidebar label "Cards", view kind `library`) aggregates all cards across every case and block. Cards can be searched, flagged, and clicked to open their block. Flagged cards are highlighted for quick reference. Cards can be exported or shared as attachments in team chat.

### Guided card cutter (Cut a card with Warroom AI)

A **＋** button sits next to **Cards** in the sidebar (`Section action={openCardCutter}`). It calls the store's `openCardCutter()` (navigates to `library` and sets `cardCutterOpen`), and `Library.tsx` renders `<CardCutter>` while that flag is set. The cutter is a multi-step wizard (`src/components/CardCutter.tsx`):

1. **Pick** — file dialog for `.html/.htm/.xhtml/.mhtml/.pdf`. Instructions tell the user to save with ⌘S/Ctrl+S as HTML (keeps images) or Print → Save as PDF (text only).
2. **Read source** — `window.warroom.ai.cutterReadSource(filePath)` → `ai:cutterReadSource` in `electron/main.ts`. For HTML it parses with **cheerio**: strips chrome (`script/style/nav/aside/ads/...`), picks the `article`/`main`/`body` container, collects verbatim paragraphs, and gathers `<img>` candidates (alt-text aware; filters logos/ads/icons by class/id/size; inlines relative images from the saved page's `_files` folder as data URLs, keeps remote `http(s)` srcs). For PDF it uses `extractText` (pdf-parse), no images. It then sends numbered paragraphs + image alt-text to `callAI(prompt, 'balanced')` (with the `card_cutting` skill for cite rules) to get `{ author, year, title, cite, bodyIndices, imageIndices }`. Returns a `CutterSource` (verbatim body paragraphs filtered to `bodyIndices`, images flagged `suggested`). Prompt template: `electron/prompts/cutter_read_source.txt`.
3. **Select** — the user highlights body chunks (additive ranges captured via `selectionOffsets`, merged; hover-✕ removes one), optionally picks images from a dropdown, types an **intent**, and chooses a highlight color (**yellow / cyan / green**).
4. **Cut** — `window.warroom.ai.cutterEmphasize({ body, intent, highlightColor, cite, clarifications })` → `ai:cutterEmphasize` returns `{ taglines, underline[], highlight[], small[] }` as **exact verbatim substrings**. `buildAttrsFromSpans` (in `src/utils/cardFormat.ts`) applies them onto the verbatim body (exact match, then whitespace-flexible regex fallback) to produce per-character attributes. Prompt template: `electron/prompts/cutter_emphasize.txt`.

   **Clarifying question (ambiguity escape hatch).** If intent wasn't specified and the body genuinely supports more than one distinct framing (e.g. it could be cut as a uniqueness card or a link card), the response can instead be `{ question: AIQuestion }` (`AIQuestion`/`AIClarification` in `src/types.ts`, shared with Auto Flow and Round Analysis). `CardCutter.tsx`'s `runEmphasize()` checks for this and, when present, shows `<AIQuestionPrompt>` (`src/components/AIQuestionPrompt.tsx`) instead of the "cutting…" spinner. The user picks an option (or types "Other…"), which appends `{question, answer}` to `clarifications` and re-calls `cutterEmphasize` with the same body/intent. The prompt is capped at **one question per cut** — it's told the running count via `{{QUESTIONS_ASKED}}` and instructed never to ask again once it's ≥ 1.
5. **Edit** — a read-only mini editor (no text editing, so the body stays verbatim) lets the user select text and toggle **underline / highlight(color) / small / clear**; pick or rewrite a tagline; edit cite/year. Saving writes a `Card` with `bodyRuns` (and optional `images`) into the `__cut__` case ("Cut Cards") / `__cut_inbox__` block.

**Formatted cards.** `Card` now carries optional `bodyRuns: CardRun[]` (`{ text, underline?, highlight?: 'yellow'|'cyan'|'green', small? }`) and `images: CardImage[]`. `body` stays the plain verbatim text (search/preview). The shared `FormattedBody` / `CardImages` components (`src/components/CardBody.tsx`) render the emphasis everywhere a card shows — the Cards list (`Library.tsx`) and block view (`BlockView.tsx`). **Green highlight** was added to the read-aloud set in `speechdoc:extract`'s token-saving regex (alongside cyan/yellow); the viewer's luminance-based `isBrightHighlight` already accepted it. This guided cutter differs from `ai:extractCards`, which pulls already-formatted cards out of a Verbatim doc rather than cutting new ones from raw prose.

### Notes: private + per-team panels, tagging
`SharedNotesEditor.tsx` renders a **Private** panel plus one panel per team the user belongs to (`TeamPanel`, one instance per `ChatTeam`), each independently toggled via a pill row at the top instead of the old single visibility `<select>`. Tagging no longer has a dedicated "+ Tag" button. Typing `@` in either textarea (`useAtMention` hook, shared by `PrivatePanel` and `TeamPanel`) opens `MentionPicker` filtered to `['speechdoc','case','flow','opponent','judge']`, same as before; selecting an item strips the "@query" text fragment (via `stripTrigger`) instead of inserting mention text, since tags render as chips (`NoteTagBar.tsx`, now display-only — no picker/onAdd of its own) below the textarea, not inline. The placeholder text (`"Add your notes… type @ to attach a doc, flow, opponent, or judge"`) documents this inline.

- **Private notes** — tags are stored locally as `noteTags` on the opponent/judge record (`db.opponents[id].noteTags` / `db.judges[id].noteTags`); nothing is uploaded, and the tag just points at the local item by id (or local file path for a speech doc).
- **Shared (team) notes** — tagging inserts a row into the generalized `message_attachments` table (Supabase). That table, previously only usable for chat attachments (FK'd to a `message_id`), now also accepts rows keyed by `team_id` + `note_entity_type`/`note_entity_id` + the tagging user's id (`note_user_id`/`note_user_name`), via new IPC handlers `notes:attachTag` / `notes:getTags` / `notes:removeTag` in `electron/main.ts`. A tagged flow that the opener doesn't have locally is imported as a new flow from a stored JSON snapshot; a tagged opponent/judge is resolved by a stable cross-user id (OpenCaselist team ID or Tabroom judge `personId`) against the opener's local records, falling back to the Scouting list if no match exists. Opening a `teamFile`-kind tag re-fetches that `team_files` row, decrypts it with the team key, and writes it to a temp file the same way a `bytes`-kind tag does.
- **Unreachable-tag warning** — `NoteTagBar.tsx`'s `DisplayTag` gained a `warning?: string` field. `TeamPanel` sets it on the tagger's own chips when `type === 'case' && data.kind === 'unavailable'` (a non-OC case tag has no portable identity for a teammate to resolve). Rendered as an amber border + ⚠️ icon in place of the type icon, tooltip = the warning text — shown to the tagger, not just discovered by a teammate hitting a dead end.

### Reverse lookup: "Tagged in" (`src/lib/noteTags.ts`, `TaggedInIndicator.tsx`)
A new shared module, `src/lib/noteTags.ts`, holds logic for two read-only consumers that don't belong inside `SharedNotesEditor.tsx` itself (which keeps its own copy of open/attach logic — this module is for new call sites, not a refactor of the original):

## Tabroom Live Monitor

The Tabroom monitor polls Tabroom's public API in the background for new pairings at an active tournament. When a new round is posted it:
- Fires an OS-level notification
- Scrapes the judge's paradigm from Tabroom
- Pulls opponent disclosures from OpenCaselist
- Fetches opponent stats from Debate Land
- Auto-creates the round entry in your tournament (marked `autoFilled`)
- Navigates directly to the new round's Mission Brief

To start: open a tournament → click **Start Monitor** → enter your entry code (the team code used on Tabroom, e.g. `Emery BL`). No Tabroom login required — uses the public pairing API. Requires OpenCaselist credentials (set in Settings) for disclosure fetching.

## Background Notifications (Daemon)

Warroom's five watchers — followed-judge paradigm updates, opponent disclosure updates, the live Tabroom round monitor, the Tabroom inbox (ballot results), and the NSDA topic scraper — keep notifying **even when the app is closed**. This is handled by a headless background daemon.

**Architecture.** The daemon is the *same* Electron binary relaunched with a `--daemon` flag — the only approach that can decrypt the existing `safeStorage`-encrypted Tabroom / OpenCaselist credentials (a separate binary would hit a different keychain/DPAPI scope). It reuses every fetch helper in `main.ts` (`tbFetchJudgeData`, `ocFetch`, `tbFetchData`/`tbExtractPairings`, `tbInboxFetch`, `scrapeNSDATopics`). Pure helpers live in `electron/daemonShared.ts`.

**Hybrid runtime (cross-platform).** A single OS scheduler entry — macOS: a `launchd` LaunchAgent (`com.warroom.daemon`, `RunAtLoad` + `StartInterval=600`); Windows: a Task Scheduler task (`WarroomDaemon`, `LogonTrigger` + `Repetition` `PT10M`, `MultipleInstancesPolicy=IgnoreNew`, `ExecutionTimeLimit=PT0S`). Each daemon process: on macOS sets `app.setActivationPolicy('prohibited')` (headless, no Dock icon — on Windows a no-window Electron process simply shows no taskbar entry), does **not** take the single-instance lock, runs the periodic judge/opponent/topic checks once (cadence-gated), then — if a tournament monitor is active — enters a resident 60s loop for live round + inbox polling, else exits. Both schedulers won't spawn a second copy while one is resident, so the interval is suppressed during a tournament.

**No double-firing.** The GUI process writes `runtime/heartbeat.json` `{pid, ts}` every 20s (cleared on quit). The daemon treats the app as alive when the timestamp is ≤60s old *and* the pid is live, and **defers all work** while the app is alive — it only takes over when the app is closed/crashed. Periodic cadence is tracked in `runtime/daemon-runs.json` (judges/opponents = 4h, topics = 30m, both processes update it). Live-monitor config + shared seen-round/seen-inbox dedup sets live in `runtime/monitors.json` (written by `tabroom:monitor:start`/`inbox:start`, cleared on stop, expires 18h after `startedAt`).

**Install.** Auto-installed on first launch (packaged builds only) via `ensureDaemonInstalled()`, which dispatches by platform: macOS writes/reloads the plist with `launchctl load -w`; Windows writes a UTF-16LE Task Scheduler XML and registers it with `schtasks /create /xml`, and the NSIS uninstaller (`resources/installer.nsh`) removes the task with `schtasks /delete`. Both show a one-time heads-up and record state in `runtime/daemon-meta.json`. No-op in dev. Windows toast notifications require `app.setAppUserModelId('com.warroom.app')` (set at startup). Status is exposed over IPC at `daemon:status` (`window.warroom.daemon.status()`).

**Deep links.** Clicking a daemon notification spawns the app binary with a `warroom://` argv (routed by the single-instance handler / cold-start argv scan, `shell.openExternal` fallback in dev): `warroom://open/judge/<id>`, `warroom://open/opponent/<id>`, `warroom://open/tournament/<id>?round=<n>`, `warroom://topics/<pf|ld>`. Handled in `handleDeepLink` via the existing renderer events (`scouting:openJudge/openOpponent`, `navigate-to-topics`, `tabroom:monitor:notifClick`).

## Speech Timer

A countdown timer (`SpeechTimer` in `TitleBar.tsx`) lives in the title bar, always visible. A dropdown selects the speech type (auto-matched to the active debate event — Policy/PF/LD); clicking the time display starts/pauses it. For Policy, an `HS`/`CLG` pill switches speech lengths. Turns amber inside the last 30 seconds, red and counts up once time expires. Warroom AI can fully control it (start/pause/reset/select/switch level) via the `control_timer` agent tool.

### Coin Flip

A photorealistic minted-coin icon (`CoinFlip` in `TitleBar.tsx`, faces rendered by `Coin.tsx`) sits immediately to the left of the timer. Each face is SVG with a radial metal gradient, beveled/reeded rim, and an engraved `H`/`T` letter built from offset light+dark copies for a relief effect. Clicking it opens a popup with an animated 3D coin (CSS `rotateY` on a two-sided element, `backfaceVisibility: hidden`); clicking **Flip** spins and lands on heads or tails.

**It is a genuine, unweighted 50/50 flip.** The result is decided synchronously the instant Flip is clicked — `const landsOnTails = Math.random() < 0.5` — *before* any animation starts. A second `Math.random()` call picks a random 4–7 extra full spins for visual variety. The rotation is then computed to land the coin at the angle (0° = heads face-out, 180° = tails face-out) matching the already-decided outcome — the spin is cosmetic dressing on a decision already made, never a driver of it. `Math.random()` (not a CSPRNG) is intentional here — it's the right tool for a coin flip, no adversarial-unpredictability requirement applies.

### Touch Bar (macOS)

`setupTouchBar()` in `electron/main.ts` mirrors the title bar's search/coin/timer onto the physical Touch Bar on supported hardware, gated `if (isMac)` in `createWindow()`. Items: a search button, a coin-flip button, a speech-type button (cycles instead of opening a dropdown — no menu widget on that hardware), `−15s`/`+15s` steppers, a live time `TouchBarLabel`, a play/pause button, and a reset button.

**State flows one way, actions the other.** The timer's actual state lives only in the renderer (`SpeechTimer` in `TitleBar.tsx`) — the main process has no copy of it. `SpeechTimer` pushes `{ speechLabel, display, running }` to main on every change via `window.warroom.touchBar.updateTimer(...)` → `ipcMain.on('touchbar:timerState', ...)`, which mutates the live `tbSpeechButton.label` / `tbTimeLabel.label` / `tbPlayPauseButton.label` (Touch Bar item properties re-render immediately on assignment — no explicit refresh call needed). Button presses go the other way: `win.webContents.send('touchbar:control', { target, action, ...extra })` → a single `App.tsx` listener (`window.warroom.touchBar.onControl`) → re-dispatched as the *same* `warroom-timer-control` / `warroom-coinflip-control` `window` custom events the AI agent (`control_timer` tool) and the coin's own click handler already use. One implementation of "start the timer" or "flip the coin", reused by three triggers (UI click, AI agent, Touch Bar) rather than reimplemented in the main process.

`SpeechTimer`'s `warroom-timer-control` handler gained two actions for this: `cycle` (advance to the next speech, wrapping — calls the same `cycleSlot()` helper `selectSlot((safeIdx + 1) % slots.length)` uses; not exposed as in-app UI, the title bar keeps its dropdown) and `nudge` (`{ deltaSeconds }`, clamped at 0 — the Touch Bar has no text-entry widget, so custom time is set via +/- steps instead of typing; pauses a running timer first, matching the in-app edit behavior). Both read `runningRef`/`displayRef`, not `running`/`display` directly, since this effect's deps array is `[slots]` — reading the closed-over state values directly would go stale between slot changes.

The coin's Touch Bar button can't run the actual 3D flip animation on the Touch Bar itself — no widget there can host the renderer's CSS content — so `CoinFlip` listens for `warroom-coinflip-control` and responds by opening its popover and calling its own `flip()`, exactly as if the user had clicked it normally; the animation plays on the real display, the Touch Bar button is a trigger only.

## Flows

Flows are `.xlsx` spreadsheets opened in-app using SheetJS. They appear in the sidebar under a "Flows" section. Opening a `.xlsx` file from Finder/Explorer registers it in the flows index and opens the flow view automatically. Flows can be shared via team chat with view or edit permissions.

Each flow has an ID, name, and debate event type. The flows index is persisted separately from the main DB in `flows_index.json`.

### Sidebar icon rendering (why icons looked blurry)

Two separate causes, both fixed:

1. **CSS `transform: scale()` on an icon.** Chromium rasterizes a transformed element at its layout size and scales the resulting bitmap, so `scale(0.72)` on a 20px icon produced a blurry 14.4px bitmap instead of a crisp vector render. Section icons now size the SVG directly (`.sb-ico-14` / `.sb-ico-16` set `width`/`height` on the child `svg`), with `stroke-width` bumped to compensate so the rendered stroke still lands near 1.5 CSS px.

2. **Fractional units-per-pixel.** The main `Ico` primitive draws on a 20-unit viewBox, and the sidebar's header action buttons render it at 16px — 1 unit = 0.8 px, so every axis-aligned edge falls mid-pixel and antialiases into a grey smear. That is what made the Flow toolbar read as blurry; the artwork was fine.

`IcoPx` (`Sidebar.tsx`) is the fix for case 2: a **16-unit viewBox rendered at exactly 16 CSS px**, so one user unit is one pixel. Axis-aligned strokes are placed on `.5` coordinates with a 1px stroke, which fills exactly one pixel column edge-to-edge with no antialiasing — and stays exact at 2x (1.5 → device px 3.0, a 2-device-px stroke spanning 3.0–4.0... i.e. still integral). `IcoImport` and `IcoAutoFlow` are drawn on this grid. Note `strokeWidth` must be set via inline **style**, not the presentation attribute, because `.sb-ico-16 > svg` sets `stroke-width` in CSS and a CSS rule beats a presentation attribute.

3. **A 1.5px stroke can never land on a pixel boundary.** This was the widest cause. The icon set's default stroke is 1.5, and axis-aligned lines were drawn at INTEGER coordinates — so a track at `y=6` spans 5.25–6.75, i.e. two half-lit pixel rows rather than one solid line, at 1x *and* 2x. The Settings icon (three slider tracks) was the most obvious victim. The rule for crisp axis-aligned strokes: **2px on an integer coordinate** (spans two whole rows) or **1px on a `.5` coordinate** (spans one). Anything else antialiases. Icons with straight rules — Settings, Cases, Speech doc, Tournament, Topics — now set `strokeWidth="2"` on just those elements. Curves (circles, diagonals) keep the 1.5 default: they antialias regardless and are *supposed* to, which reads as smooth rather than blurry. Note a child's `strokeWidth` presentation attribute beats the value inherited from the parent `<svg>`, so this override works without touching the shared primitive.

**`scripts/icon-audit.py`** is a repeatable checker for all three causes. It parses every inline `<svg>` in `src/`, works out each icon's px-per-unit from `width` ÷ `viewBox`, and reports (a) `FRACTIONAL_SCALE` — a render size that doesn't divide the viewBox cleanly, and (b) `BLURRY_STROKE` — axis-aligned lines, rect edges, and `h`/`v` path runs whose stroke edges don't land on whole device pixels at 1x **and** 2x. Run it with `python3 scripts/icon-audit.py` before and after touching icons. Note that not every hit is worth fixing: short strokes, diagonals, curves, and pure fills antialias imperceptibly. Prioritise long straight rules in always-visible chrome — those are what the eye reads as "out of focus".

Use `IcoPx` for small boxy icons (grids, sheets, arrows) that live in the 16px header row; the 20-unit `Ico` is still right for icons rendered at their natural 20px, and for organic shapes (circles, diagonals) that antialias regardless.

### Collapsed sidebar: grid navigation and right-click quick-create

`CollapsedNav`'s Cases icon (`Sidebar.tsx`) always opened `{ kind: 'cases-grid' }` directly; the Flow icon used to call a `goFlow()` helper instead — open the first flow, or create one if none existed — never showing the grid. It now opens `{ kind: 'flows-grid' }`, same as Cases, and `isFlow` includes `'flows-grid'` so the icon lights up there too.

`CIcon` takes an optional `onContextMenu` prop (wired with `e.preventDefault()` so the OS context menu never shows) and `contextLabel`, which folds into the button's `title` as `"<label> (right-click: <contextLabel>)"`. Cases wires it to `setView({ kind: 'speech-doc' })` (new case) and Flow wires it to `createFlow` — the same actions their expanded-sidebar `+` buttons trigger — so collapsing the sidebar doesn't lose that shortcut.

### Flow folders and the Flows grid

Clicking **Flow** in the sidebar opens `FlowsGrid` (view `{ kind: 'flows-grid', folderId? }`, routed in `App.tsx`) — the flow library as a grid of folders + flow tiles, mirroring the Cases grid. Folder management lives there, not in the sidebar header: the standalone new-folder button was removed from the Flow section, matching how Cases works.

`src/utils/flowFolders.ts` stores the same `{ folders, assignments, order }` shape as `caseFolders.ts` under its own `flow_folders` key, and reuses every pure tree helper (`childFolders`, `folderTrail`, `moveItem`, `moveInOrder`, `sortByOrder`, `deleteFolder`, `pruneAssignments`, …) — only the store (key, change event, cache, `useFlowFolders` hook) is separate. `FlowsGrid` also imports the generic folder UI (`Crumb`, `FolderTile`, `DeleteFolderConfirm`, `CARD_BASE`) directly from `CasesGrid` rather than reimplementing it, so the two libraries can't drift apart visually; only the tile itself (`FlowTile`, a mini flow-grid glyph + name + event/live line) is flow-specific.

Behavior matches Cases throughout: drag-to-file (with distinct MIME types `application/x-warroom-flow-item`/`-flow-folder` so flows and cases can't be cross-filed), drag-tile-onto-tile to reorder, a right-click menu with Move to / Rename / Delete that works when the target folder is collapsed, breadcrumb navigation with folders as drop targets, search that spans **every** folder, and assignment pruning for deleted flows. A flow created while inside a folder is filed into that folder. `FlowsSection` in `Sidebar.tsx` still renders the same folders as an expandable tree (shared store, so both views update together), and its title now navigates to the grid via `onTitleClick`.

### Default order: newest first, then manual

`FlowMeta` (`appStore.ts`) now carries an optional `createdAt` ISO string, set at every creation site (`Sidebar.tsx`, `FlowsGrid.tsx`, `Chat.tsx`, `ChatMessage.tsx`, `AutoFlow.tsx`). Both `FlowsGrid` and `Sidebar.tsx`'s `FlowsSection` run the same `ensureOrderSeeded` effect Cases already used, keyed on `itemKeyForFlow(f.id)` — new flows are seeded into `folders.order` newest-`createdAt`-first, ahead of anything already ordered, so a manual drag-reorder is never silently undone. Flows created before this field existed have no `createdAt`; they fall back to their position in `flowsIndex` (oldest→newest, since `createFlow` appends), zero-padded so it sorts correctly the one time it's compared against real timestamps during the initial seed. `Sidebar.tsx` additionally wraps `flowsIndex` in `sortByOrder` (`orderedFlows`) before rendering the tree, so the two views always agree.

### Multi-select and bulk actions on the Flows grid

Mirrors Cases exactly: Cmd/Ctrl+click on a `FlowTile` toggles its key into a `Set<string>` (checked in the tile's own `onClick`, not a capture-phase intercept like Cases — there's no nested clickable inside a flow tile to protect against). `ItemSelectionBar` (previously private to `CasesGrid.tsx`) is now exported and reused as-is rather than reimplemented, so the two grids can't drift on bulk-bar behavior. Bulk delete (`deleteFlows`) is undoable via `pushUndoToast` — it snapshots each removed flow's `flow_data_<id>` before clearing it, matching `CasesGrid`'s `deleteItems`; the grid's previous single-tile `deleteFlow` had no undo, so this closes that gap for both the bulk bar and the per-tile "⋯" menu, which now both call `deleteFlows`.

### Content-aware tile preview

`FlowTile`'s mini flow-grid glyph used to be a fixed decoration on every tile. `FlowsGrid` now lazily reads each flow's `flow_data_<id>` once (gated by a `requestedFill` ref so it never refetches on re-render) and computes `computeColumnFill(cells)` — a `boolean[4]` for whether the first sheet's columns 0–3 have any non-empty cell content (cell keys are `"ri-ci"`; only the column index is used). `FlowTile` conditionally renders each decorative bar based on that array; while it's still loading (`columnFill` undefined), every bar shows, so a tile never flashes from "full" to "empty" once the real data lands.

### Importing a flow

An **import button** sits next to the `+` in the sidebar's Flow section. Clicking it opens a file picker for an existing flow spreadsheet (`.xlsx`); the app parses it and creates a new flow named after the file. Each **worksheet (tab)** in the workbook becomes its own flow sheet in the app.

Import is **very robust** — it works no matter how the spreadsheet is laid out. It first tries to auto-detect the structure algorithmically, recognizing speech-column headers (for policy: `1AC`, `1NC`, `2AC`, `2NC/1NR`, `1AR`, `2NR`, `2AR`, plus PF column layouts). Real policy debate has 8 speeches, but the app merges **2NC + 1NR** (the neg block) into a single column, so a standard 8-column source sheet maps cleanly onto the app's layout. If it can't confidently figure out a sheet's structure, it falls back to **Warroom AI** to interpret the spreadsheet and map the columns correctly. Both policy and PF flows are supported. Prompt template: `electron/prompts/flow_import.txt`.

The imported flow appears in the sidebar and can be renamed and edited like any other flow.

### Editing flows

The flow editor works like a paper flow with spreadsheet conveniences. Cells support **rich text** — `⌘B` bold, `⌘I` italic, `⌘U` underline, `⌘⇧X` strikethrough, and `⌘⇧H` highlight (amber). Each has a toolbar button too. Highlight is a `background-color` span rather than an `execCommand` flag, so it has no native toggle — the handler reads the caret's current background via `queryCommandValue('backColor')` and clears it if it is already the highlight color. Highlighted runs are forced to dark ink by a `.flow-cell` rule in `index.css` so amber stays readable in dark mode. Cells **auto-grow** to fit their text.

Cell values are stored as HTML. The sanitizer, the clipboard cleaning, and the plain-text/HTML conversions live in **`src/lib/cellHtml.ts`** (not in `FlowView.tsx`) so they can be exercised headlessly by `scripts/test-cell-paste.ts` — run the whole flow suite with `npm run test:flows`. Every path that puts untrusted HTML into a cell (remote collaborator updates, AI/MCP-written values, the clipboard) goes through `sanitizeCellHtml`, which parses inertly with `DOMParser` and reserializes from a tag/style allowlist.

**Keyboard navigation:** `←` / `→` are never intercepted — they always move the caret through the cell's text. `↑` / `↓` move a line *within* the cell and only jump to the cell above / below once there is no line left to go to. Because cells wrap, "is the caret on the first/last line" has no node boundary to test, so `caretOnEdgeLine()` compares the caret's screen `y` against a caret probed at the very start / end of the cell (half a line of tolerance). `Tab` / `⇧Tab` move between columns; `Enter` moves down a row.

**Pasting (`onPaste` → `cleanPastedHtml`):** Word and Google Docs put fully-styled HTML on the clipboard — font family, point size, explicit ink color, `background-color`. Pasting natively drags all of it in, so a tag copied out of a speech doc lands in the wrong font at the wrong size (and, from a dark-themed doc, in white-on-white). The cell intercepts paste, runs the clipboard HTML through the sanitizer with the stricter `PASTE_STYLE_PROPS` list, and inserts the result; if the HTML sanitizes to nothing it falls back to the `text/plain` flavor. Emphasis (bold / italic / underline / strike / sub / sup) survives.

**`color`, `font-family` and `font-size` are excluded from `ALLOWED_STYLE_PROPS` outright — not just on the paste path.** Nothing in the app can legitimately set them on a cell: there is no text-color picker, per-column colors live on the cell's *wrapper* element, and cell font size is a view-level setting applied inline to the cell div. So a run carrying any of them can only have come from pasted Word / Google Docs markup — which is what made a pasted tag land in 22pt black-on-dark. Excluding them at the render path too means cells pasted *before* this fix repair themselves the next time they render, rather than staying broken forever (storage keeps whatever was pasted; `cellToHtml` scrubs on the way to the DOM).

`background-color` is allowed on the render path (it is how the ⌘⇧H highlight is stored) but dropped on paste, because Word and Google Docs stamp it on nearly every span with junk values (`transparent`, `white`) — left in, `background-color:transparent` would match the `.flow-cell span[style*="background-color"]` dark-ink rule intended for our own highlights and render pasted text near-black on a dark background.

**Whitespace and block structure.** Cells render with `white-space: pre-wrap` so typed spacing survives — which means a literal newline in cell markup becomes a real blank line on screen. Word and Google Docs pretty-print their clipboard HTML (newlines + indentation between every tag), so pasted markup arrives carrying blank lines it never intended, and a surviving `<p>` adds its default 1em margin on top of that. Two defenses:

- `pasteNode` (paste path) flattens every block tag to a single `<br>`, collapses whitespace the way normal non-pre-wrap rendering would, coalesces runs of `<br>` (empty Word paragraphs emit nothing else), and trims leading/trailing breaks. A pasted tag + cite becomes `tag<br>cite` — one flowing run, no `<p>` at all.
- `collapseSourceWhitespace` (render path) turns newlines/tabs in text nodes into a space. Raw newlines can only come from pasted markup — typing produces `<br>` — so this is safe, and it leaves runs of *spaces* alone since pre-wrap preserves those on purpose. Paired with the `.flow-cell p, .flow-cell div { margin: 0 }` rule in `index.css`, it makes cells pasted *before* the paste fix render tight instead of blank-lined.

**Sheets by keyboard:** `⌘1`–`⌘8` jump straight to that sheet by position and `⌘9` jumps to the *last* sheet (the browser-tab convention, so it still lands somewhere useful when a flow has more than nine sheets). `⌘T` creates a new sheet. Both live in the window-level shortcut handler rather than the cell handler, so they work whether or not a cell has focus.

**Per-sheet scroll position:** every sheet shares one scroll container, so switching tabs would otherwise keep wherever you were — scroll to the middle of the Politics DA and the Case sheet opens mid-page. `sheetScroll` (a ref, keyed by **sheet id** rather than index so deleting or reordering can't hand one tab another's offset) records `scrollTop`/`scrollLeft` on scroll and before any tab change, and a `useLayoutEffect` on `activeSheetIdx` restores it before paint. A sheet that has never been visited has no entry and lands at the top. These offsets are in-memory only — deliberately not persisted, since writing on every scroll event would churn storage for something that stops being meaningful once the flow is closed.

**Columns auto-fit the container width.** `fitZoom()` (pre-existing — it's what the toolbar's "Fit to window" button calls) computes `zoom` from `containerRef.current.clientWidth / sum(columnWidths)`, so all columns scale by the SAME factor and stay proportional to each other — it was previously only triggered once, on load and on `chatOpen` toggling. A second `useEffect` now attaches a `ResizeObserver` to `containerRef` (gated on `loaded`, mirroring the load-triggered effect) that calls `fitZoom()` on every container resize — this single observer is what catches window resizes, sidebar collapse/expand, and chat-panel toggling all at once, since all three change the container's actual width; no code here needs to know sidebar state exists. Two guards keep this from misbehaving: (1) the `ResizeObserver` callback debounces 150ms trailing before calling `fitZoom()`, so a dragged window edge or an animated sidebar collapse doesn't fire it once per frame; (2) `fitZoom()` itself now skips applying a proposed zoom that's within 1 percentage point of the current one — without that, applying a zoom change can itself toggle a scrollbar and resize the container again, and on a live-synced flow (`zoom` is mirrored into the Yjs doc) an unthrottled loop would also spam teammates with zoom broadcasts.

**Disabling shortcuts:** flow shortcuts are registered in `ShortcutsOverlay.tsx`'s `GROUPS` array with stable ids (`flow-bold`, `flow-highlight`, `flow-sheet-switch`, …) and each handler checks `isShortcutDisabled(id)` (`src/lib/shortcutPrefs.ts`) before acting, so the user can turn individual ones off from the `⌘/` overlay.

**Move an argument (`⌘↑` / `⌘↓`, Ctrl on Windows):** swaps the cell's content with the cell above / below it in the same column, and moves the caret with it, so an argument can be nudged into position without cut-and-paste. Goes through the same debounced save + history path as typing, so it is undoable with `⌘Z`.

**Draw arrows:** two interchangeable ways to draw a connector arrow linking an argument to its answer across columns (like the line on a paper flow).
- **`⌘L` (keyboard):** press `⌘L` inside the source cell to mark it, arrow-key to the target cell, press `⌘L` again to draw. Pressing `⌘L` twice in the same cell cancels.
- **Toolbar (mouse):** the curved-arrow button enters draw mode — click a source cell, then a target cell.

Both drive the same draw-mode state, so an arrow can be started with `⌘L` and finished with a click, or vice versa. Click the `×` on an arrow's midpoint to delete it; press `Esc` to cancel. Arrows are saved per sheet.

**Insert a cell between two others.** The `+` sits on its own thin hover strip (a 12px band straddling the border, centered exactly on the line) with independent hover state (`hoveredGap`) from the cell's own hover — so it only appears when the cursor is physically over the border between two stacked cells, not anywhere the mouse happens to be inside the cell above it. `insertRowBetween(afterRi, ci)` inserts a blank cell in **that one column** (not a full row), shifting the column's cells from `afterRi+1` down one and remapping any arrow endpoints in that column at/below the insert. Single-column by design — it matches the "+" sitting on the line between two stacked cells, and lets a debater slot a missed argument into one speech's column without disturbing the others. Goes through `persist` + `recordHistory` (undoable) and pushes the shifted cells over live sync.

**Tab content tooltip + truncation.** Long tab names truncate with an ellipsis (`SheetTab`'s name button is `w-full truncate` inside a `flex-1 min-w-0` `FlowTooltip` wrapper — the `min-w-0` is what lets a flex child actually shrink below its content instead of overflowing). Hovering the tab shows a wide, ≤4-line tooltip (`FlowTooltip`'s `wide` variant): the tab's **full name** on the first line, then a content preview built by `sheetSummary(idx)`. If `sheet.aiSummary` is set, that real AI-written sentence (summarizing the argument as a whole, not listing what's on the tab) leads the preview, prefixed `✨` — otherwise it falls back to the top ~3 argument tags (first line of each non-empty cell), a cheap local read of the cells with no AI involved. An empty tab shows just its name plus "Empty".

**Identity, not index, everywhere the live buffer or the active sheet is resolved.** An audit found the index-vs-id confusion in eight more places beyond the initial flush fix, all the same class of bug (React state and `snap.current` resync only in a post-render effect, so `activeSheetIdx` can be momentarily stale):
- `takeSnapshot()` — undo history. A snapshot taken on a stale index baked one tab's cells onto another, so **undo restored the corruption**.
- `currentDataForDoc()` — seeds a fresh live doc. A stale index here misfiled cells and then **broadcast them to the whole team**.
- `pushLiveCell()` — resolved the target sheet by index, so a keystroke could be pushed into another sheet's cell in the shared Y.Doc.
- `clearAiCell`, `setActiveSheetArrows` — mutated the wrong sheet's `aiCells`/`arrows`.
- `sheetSummary`, `ensureSheetSummary`, the Find effect, `flowHasAnyContent` — read the live buffer as if it belonged to a different sheet, which for the AI tab summary meant generating and caching a description of the **wrong tab**.
All now resolve through `cellsOwnerId` (or the sheet's own `id`).

**`hydrateFromDoc` keeps you on your sheet by id.** It used to clamp the old `activeSheetIdx`, so a teammate adding/deleting/reordering a tab silently slid you onto a different one mid-round; it now re-finds your sheet by id and only falls back to the clamped index if your sheet was genuinely deleted.

**Zoom is not adopted from the shared doc.** `hydrateFromDoc` deliberately skips `setZoom`. Zoom is a per-viewer fit to your own window and the grid auto-fits on every container resize, so adopting a teammate's zoom created a feedback loop: they fit to their width and broadcast, you adopt it, your auto-fit corrects to your width and broadcasts back, forever.

**The debounced save is cancelled when the flow changes or unmounts.** `scheduleSave`'s 600ms timer closes over the sheets of the flow that armed it. Navigating to another flow within that window let it fire and push the previous flow's tabs into the new flow's view until the async read overwrote them.

**Live cell buffer is flushed by sheet ID, not index.** `cellsRef` holds the sheet being edited (kept out of React state so typing doesn't re-render the grid), and `cellsOwnerId` records which sheet it belongs to. Every merge back into the sheets array — `persist`, `flushAndGetSheets`, `scheduleSave` — goes through `flushInto` → `flushCellsIntoSheets` (`src/lib/flowCellFlush.ts`), which matches on that owner id. This fixes a real data-corruption bug: the merge used to be `sheets[activeSheetIdx]`, but `activeSheetIdx` (React state) and `snap.current` only resync in a post-render effect, so any flush landing in that window — an async AI-summary write, a debounced save, anything after a tab switch or a drag-reorder that shifted indices — wrote the current tab's cells into a *different* tab's slot, which users saw as arguments teleporting between tabs mid-round. If the owner id isn't present in the list (sheet deleted, or state mid-transition) the buffer is dropped rather than misfiled — losing an unsaved keystroke is recoverable, writing it onto the wrong argument isn't. Pinned by `scripts/test-flow-cell-flush.ts`.

**Arrows are straight lines.** `recomputeArrows()` emits `M x1 y1 L x2 y2` — no bezier. Same-column arrows (an answer that couldn't share its target's row) run down the column's right edge (`max(fr.right, tr.right) - 6`) so the line doesn't cut through the text of the cells between the two endpoints; everything else runs edge-to-edge between the facing sides of the two cells.

**Tab summary is a genuine, lazily-generated AI call (`ai:summarizeFlowSheet`).** Unlike the rest of the flow editor's tooltip content, this one really does call Warroom AI — but only when it needs to, not preloaded and not on every hover. `SheetTab` calls the new `onEnsureSummary` prop (wired to `ensureSheetSummary(idx)` in `FlowView`) on `onMouseEnter`, fire-and-forget:
- `sheetContentSignature(cells)` builds a cheap (non-cryptographic) signature of the sheet's cell contents — sorted `"key:text"` pairs run through a simple rolling hash. If `sheet.aiSummary` is already set AND `sheet.aiSummarySource` matches the CURRENT signature, `ensureSheetSummary` returns immediately — no call. This is what makes repeated hovers free and what invalidates the cache the moment the sheet's content actually changes.
- If the sheet has zero content, or a request for that sheet is already in flight (tracked in `generatingSummary`, a `Set<string>` of sheet ids, so overlapping hovers can't double-fire), it also no-ops.
- Otherwise it flattens the sheet's cells (`{r, c, text}`, sorted `(c, r)` — same order as the local-fallback tag list) into a plain string array and calls `window.warroom.ai.summarizeFlowSheet({ sheetName, event: flowEvent, entries })`. `sheetSummary(idx)` shows "✨ Warroom AI is summarizing this tab…" while the sheet's id is in `generatingSummary`, so the tooltip reflects the in-flight state without any separate loading prop.
- On success, the result is written into that sheet's `aiSummary`/`aiSummarySource` via `setSheets` + `snap.current` + `persist()` — deliberately called with **no** `sheets` override, so `persist()`'s own internal flush (which re-reads live `cellsRef` for the active tab) is what actually lands in storage; passing the async callback's own `updated` array as the override risked clobbering in-progress typing with a stale-at-request-time snapshot of the active sheet's cells.
- **Failures back off instead of retrying on every hover.** A failed summary never caches a signature, so without this each hover started a brand-new 4-attempt retry ladder — one dead key or an exhausted quota became an endless stream of toasts while flowing. `noteSummaryFailure` disables the feature for the session on a quota/rate-limit/auth error (`429`, `RESOURCE_EXHAUSTED`, `quota`, `api key`, `401`/`403`, `NO_KEY` — none of which fix themselves by being asked again mid-round) via the `summaryDisabled` ref, and backs off a single sheet for 10 minutes (`summaryCooldown`) for anything else. The tooltip silently falls back to its local, non-AI tag preview. `SheetTab` also waits a 400ms dwell before firing, so sweeping the cursor across a row of tabs doesn't spend a call on each one.
- A failed response isn't handled specially here — the global AI-error toast (`electron/preload.ts`'s wrapper around every `window.warroom.ai.*` method, `AiErrorToast.tsx`) already surfaces it, and the tooltip just falls back to the local tag list next hover.

The main-process handler, `ai:summarizeFlowSheet` (`electron/main.ts`, prompt `electron/prompts/summarize_flow_sheet.txt`), asks for ONE sentence (≤22 words) describing the position as a whole — explicitly not a list — and is wrapped in `withDelayedRetry` like every other AI call site (uses the `'lite'` model tier, since this is a short, low-stakes summary). It reads only the tags/cites already visible in the flow (same boundary as Auto Flow), never anything from outside it.

**`SheetTab`'s re-render-while-hovered trick.** `getSummary`/`onEnsureSummary` are inline closures re-created every `FlowView` render, so a plain `useEffect(() => { if (hovered && getSummary) setSummary(getSummary()); }, [hovered, getSummary])` inside `SheetTab` re-reads the summary on every parent render while the tab is hovered — including the ones triggered by `ensureSheetSummary`'s `setGeneratingSummary`/`setSheets` calls landing. That's the entire mechanism for the tooltip to go from "summarizing…" to the finished sentence without any dedicated pub/sub: `getSummary` changing identity each render is what drives the poll.

**Undo/redo enablement.** The undo/redo counters (`histIdx`/`history`) are refs, so the toolbar buttons wouldn't re-render on their own. `canUndo`/`canRedo` are mirrored to state via `syncHistButtons()` (called from `recordHistory`, `undo`, `redo`), and passed as `disabled` to the `ToolBtn`s so they grey out (opacity 0.4, click blocked) when there's nothing to undo/redo.

**Sheet ops are undoable.** `addSheet`, `deleteSheet`, `commitRenameSheet`, and `reorderSheet` record history like any cell edit — deleting a tab full of arguments used to be unrecoverable. The subtlety: history snapshots read `snap.current`, which normally only catches up in a post-render effect, so each of these ops writes its new `sheets` (and `activeSheetIdx`) into `snap.current` by hand before calling `recordHistory()` — without that, the snapshot would still hold the pre-op sheets and undo would appear to do nothing. `restoreSnapshot` already clamps `activeSheetIdx`, so undoing a delete that removed the active tab lands safely.

**Tab drag-to-reorder.** `SheetTab` is `draggable` (except while inline-renaming, so the rename input keeps normal text selection) and uses native HTML5 drag events. `FlowView` holds `dragTabIdx`/`dropTabIdx`; on drop, `reorderSheet(from, to)` flushes the live sheet (`flushAndGetSheets`, so no in-progress typing is lost), splices the sheet to its new index, and re-derives the active index by the dragged-past sheet's **id** (not its old numeric index, which shifts as tabs move). The hovered target shows an insertion marker via an `inset 2px 0 0` box-shadow on its left edge, and the dragged tab dims to 0.4 opacity. Because sheet content is keyed by sheet id everywhere (cells, scroll offsets, AI summaries), reordering is purely positional — nothing about a sheet's data moves with the index change.

**Variant switch is content-guarded.** The Stock Issues / Advantage toggle (and the PF Pro/Con-first toggle) only render while `flowHasAnyContent()` is false — switching variant rebuilds the sheets from the default names for that variant, which would silently drop extra/renamed tabs and their contents. `changeVariant` also early-returns if content exists, as a safety net for the brief window before a re-render hides the toggle. The **Policy/PF event toggle was removed from the UI entirely** (a flow's event is set at creation / by Auto Flow's inference) — `changeFlowEvent` stays defined and wired for the future, just unsurfaced.

**Find (`⌘F`):** a find bar ("Find across all tabs…") searches every sheet in the flow. Enter / Shift+Enter jump between matches; Esc closes. Matches are per *cell*, and stepping to one on another sheet switches to it.

Hits are painted with the **CSS Custom Highlight API** (`CSS.highlights` + `Highlight` + `Range`), the same approach as the speech-doc viewer's find — deliberately *not* by wrapping matches in `<mark>`, because cell HTML is user content that gets persisted and broadcast to live teammates, so mutating it to show a search hit would write the highlight into the document. Two registries: `flow-find` washes every hit on the active sheet, `flow-find-current` paints the one you're stepping through in solid amber; both are styled by `::highlight()` rules in `index.css` and cleared on close and unmount. Only the active sheet is mounted, so only its hits can be painted.

`matchRangesIn` (`src/lib/cellHtml.ts`) builds the ranges. It **flattens the cell's text nodes into one string, searches that, then maps the offsets back** — searching each text node separately would miss any hit straddling a tag boundary, which is most of them in a real tag (`preventable <u>death</u>` is two text nodes). It lives in the lib rather than the component so `scripts/test-cell-paste.ts` can exercise the offset mapping headlessly.

**Undo / redo:** `⌘Z` undoes and `⌘⇧Z` redoes, also available as toolbar buttons. Undo covers text edits, column changes, colors, arrows, and the variant / PF-order / event layout switches.

A `FlowSnapshot` holds document state only — **it deliberately carries no active-sheet index**, and `restoreSnapshot` keeps whatever tab the user is currently on (clamped, since undoing an "add sheet" can remove the tab they're standing on). Switching tabs records no snapshot, because navigation isn't an edit; when the index *was* stored and restored, an older snapshot still carried whatever tab happened to be open when it was taken, so undoing an edit made on tab 2 threw the user back to tab 1.

**Column colors:** each column header has an always-visible `▾` menu with a color palette to recolor that column; "Reset to default" restores the side color. The default Aff/Pro and Neg/Con column colors can be set for all flows in **Settings → Flow** (Column colors).

### Live collaboration (realtime co-flowing)

**There is no "Collaborate" button and no "Go live" button** — both existed at different points and both got folded away because they led to (or duplicated) something that now just happens on its own. Sharing a flow always goes live first: `getData` in the `SharePanel` call site (`FlowView.tsx`) calls `startLiveCollab()` before building the share payload, whenever the flow isn't already live and a team is signed in. A manual "Go live" action inside the panel was briefly added when Share/Collaborate were first merged, then removed once getData()'s auto-promote made it a second way to trigger the exact same thing — one button, one behavior.

This closes a real gap: without auto-promoting on share, a plain share handed the recipient a brand-new `flowId` (a genuinely separate copy, per the chat-import branch in `ChatMessage.tsx`/`Chat.tsx` that only reuses the sender's `flowId` when `attachment.data.live` is true) — so if both people happened to have their own copy open at once, there was no shared document to reconcile, just two flows silently diverging. Always sharing live means every recipient joins the exact same doc from the start, so that divergence can't happen. If `startLiveCollab()` fails (offline, promote error), `getData` falls back to a plain snapshot rather than pointing the recipient at a doc that was never actually promoted — check its own return value, not the `live` closure variable, since a `setLive(true)` inside that same call won't be visible to the still-executing closure. The "Send to" step shows a one-line note ("Sending starts a live session…") whenever this is about to happen, gated on `currentUser && currentTeam` directly (not a prop) since `SharePanel` no longer needs an `onGoLive` callback at all.

Two or more teammates type into the same flow at once and see each other's edits appear **character-by-character**, like Google Docs. A green "Live" pill in the toolbar (not a button — just status) shows who else is present and lets you leave the session; each teammate's active cell is ringed and tagged in their color.

The flow's editable state is mapped onto a **Yjs CRDT** document (`src/lib/flowDoc.ts`). Each cell is a `Y.Text` holding its HTML, so concurrent edits merge deterministically — even two people in the same cell never lose text (the cell *this* user is focused in is left alone until blur, to protect the caret). Layout/structure (columns, colors, variant, sheet names) lives in a `meta` map plus the `sheets` array as last-write-wins.

**Transport.** Yjs update + awareness bytes ride a Supabase *Realtime broadcast* channel keyed by the flow's unguessable id (no per-keystroke DB writes). Durability is a debounced base64 snapshot of the doc in a new `flows` table (team-scoped RLS), so a teammate who opens the flow later — or reconnects — loads the current merged state. The Supabase client lives in the main process; the renderer talks to it via the `flowSync:*` IPC bridge (`src/lib/flowSync.ts` ↔ `electron/main.ts`). Late-join convergence is handled by re-broadcasting full state when a new peer's presence appears. Sharing a live flow sends a *pointer* (same id + team, `live: true`) so recipients join the same doc rather than cloning it; each device keeps a local `flow_data_*` mirror so the flow still works offline. Requires a configured Supabase backend and the `flows` table from `supabase/schema.sql`.

### Round Analysis

A magnifying-glass toolbar button next to Share opens **`AnalyzeRound.tsx`**, a wizard that reads the debater's own flow as ground truth for what has been said and where, then asks Warroom AI for a strategic read: what looks dropped or conceded, which clashes are still live and who currently appears to be ahead on each, and concrete suggestions for the next speech in the flow's own speech order.

**Building the flow summary.** The renderer flattens the flow into plain text with `buildFlowSummary()` in `AnalyzeRound.tsx`: for each sheet, for each column (in the flow's actual left-to-right speech order), every non-empty cell in row order, run through `htmlToText()` (`src/lib/cellHtml.ts`). An empty column prints `[Column] (empty)` so the model can see gaps, not just content. The sheets passed in are the caller's current in-memory snapshot — `FlowView.tsx` passes `flushAndGetSheets()` (the same function the Share panel uses), so unsaved edits on the active tab are included.

**Notes + supplementary docs.** A textarea lets the debater add free-text context (which side they're on, the round number, what they think is winning or losing — anything not already on the flow). A drop zone mirroring `SpeechDocViewer.tsx`'s `pickFile()`/drop pattern accepts multiple `.docx` uploads (case docs, blocks); each is read via `speechdoc:extract` and its `.full` text is capped to 20,000 characters per doc before being sent.

**IPC handler:** `ai:analyzeRound` in `electron/main.ts`, prompt template `electron/prompts/analyze_round.txt`. Takes `{ flowSummary, notes, docs, event, clarifications }` and returns either `{ ok: true, question }` or the full structured result:
```ts
{ ok: true, sideALabel, sideBLabel,
  verdict: { leading: 'A'|'B'|'even', reason },
  dropped: { side: 'A'|'B', argument, sheet }[],
  clashes: { topic, claimA, claimB, winner: 'A'|'B'|'even', reasoning }[],
  nextSpeech: { action, why }[] }
```
Uses the `'balanced'` model tier with `maxOutputTokens: 32768` (not the `callAI` default of 8192) — the structured shape runs noticeably longer than the old single `analysis: string` ever did, and a large round's worth of `dropped`/`clashes`/`nextSpeech` entries with reasoning text can genuinely exceed 8192 tokens, truncating the JSON mid-generation and failing to parse. `sideALabel`/`sideBLabel` default to `Aff`/`Neg` (policy) or `Pro`/`Con` (PF) if the model omits them. The handler coerces defensively the same way `ai:autoFlowClassify` does — drops any `dropped`/`clashes`/`nextSpeech` entry missing its required text field rather than letting one malformed entry break the render — and if `verdict.reason` ends up empty (nothing usable to show), checks whether the raw response looks cut off (doesn't end in `}` or `]`) to surface a more specific error than a bare failure message. **Caveat:** the `maxOutputTokens` override only reaches the Gemini branch of `callAI` — `callOpenAI`/`callAnthropic`/`callGrok` all hardcode `max_tokens: 8192` with no override path today, so a large round can still truncate for a non-Gemini provider. The prompt also caps `dropped`/`clashes` at 8 entries each as a second line of defense, independent of the token ceiling.

**This is a structured result, not prose.** The prompt is explicitly told the response feeds a card UI, not a paragraph — every field must be its own short, separate piece. This was a deliberate redesign: the first version returned one `analysis: string` field of flowing prose, which read as a wall of text with no way to scan it quickly. The renderer now mirrors Impact Calc's result view (`ImpactCalcView.tsx`) closely on purpose — a verdict banner, drop cards, and side-by-side clash cards with a winner badge — reusing that same visual language (`Tag`, winner-color banner, claim-vs-claim card layout) rather than inventing a new one, and the two features now look and read the same way. Colors: the verdict banner and clash cards read the debater's *actual* aff/neg (or pro/con) column colors from `localStorage` (`warroom-flow-aff-color`/`warroom-flow-neg-color`, same keys `FlowView.tsx`/`Settings.tsx` use — see "Flow colors" in Settings), not a hardcoded pair, so the analysis visually matches whatever the debater already sees on their flow.

**Ambiguity escape hatch.** Shares the `AIQuestion`/`AIClarification` contract in `src/types.ts` with the guided card cutter (`ai:cutterEmphasize`) — if something essential is genuinely unclear (most commonly which side the debater is on, since that decides every "who's ahead" call), the model can return a `question` field instead of committing to a guess. The UI shows it via `AIQuestionPrompt`, the debater answers, and the same handler is re-invoked with the answer appended to `clarifications`. Capped at one question per session (never asked once `clarifications.length >= 1`) — mirrors `cutter_emphasize.txt`'s `{{QUESTIONS_ASKED}}` convention.

Every text field (verdict reason, argument text, clash reasoning, next-speech action/why) renders through a local `RichText` copy (every AI-output panel in this codebase defines its own — no shared component exists yet) supporting `**bold**`, `*italic*`, `__underline__`, and `` `code` ``, per the "AI feature results always support emphasis" rule.

**Caching.** A finished analysis is persisted to `storage` under `analyze_round_${flowId}` as `{ result, notes, savedAt }` — written right after `runAnalyze()` lands on the `'result'` step, read back in a `useEffect` on mount. Opening the panel again for the same flow (even after fully closing and reopening it) shows the last result immediately instead of the setup screen, with a "Saved analysis from …" note above the verdict banner (and a "Run a new one" link inline) so it's never mistaken for a fresh read of the *current* flow state. The mount effect gates the whole panel behind a `ready` flag rather than defaulting to the setup screen and swapping in the cached result a beat later — avoids a flash of the wrong step. No `flowId` (shouldn't happen in practice, since the panel only opens from an already-open flow) skips caching entirely rather than erroring. The **"New analysis"** button (was "← Analyze again") clears `notes`/`docs`/`analysis`/`clarifications` *and* deletes the cache entry (`storage.write(key, null)`) — a genuine fresh start, not just a re-run, so a stale cache can't resurface after the debater explicitly discarded it.

Round Analysis is a self-contained wizard inside the flow editor, not a Warroom Agent tool — its IPC handler is intentionally absent from `AGENT_TOOLS` and `warroom-mcp/server.js`, the same way the card cutter's handlers are.

## Auto Flow

A wand-icon button next to the sidebar's Flow section opens `AutoFlow.tsx` — a wizard that uploads one or more speech docs (`.docx`) and has Warroom AI sort every card's tag into the right column and sheet of a flow, either a brand-new one or an existing one.

**Extraction.** Each uploaded doc is read with `speechdoc:extractBlocks` (`electron/docxFlowCards.ts`'s `extractFlowCardsFromXml`), which returns `ExtractedFlowCard[]` — `{ pocket, hat, block, tag, cite }` per card, keeping the pocket/hat/block heading ancestry instead of flattening it like `speechdoc:extract` does. **This never returns card body text, only headings and the cite line** — Auto Flow's whole design invariant is that it routes tags, it never re-cuts or reads evidence. A doc that fails to parse or yields zero cards is shown in the target step but doesn't block the rest of the batch.

**Choosing a destination.** The user picks a **new flow** or an **existing flow** (from `flowsIndex`). For a new flow, `inferEventFromPockets()` (`src/lib/autoFlowPlacement.ts`) guesses policy vs. PF from the uploaded cards' pocket labels — policy-style codes (`1AC`, `2NC`, …) vs. PF-style phrases (`Pro Case`, `Con Rebuttal`, `Pro FF`, …) — falling back to the app's current `event` when the docs give no usable signal; the initial `StoredFlowData` is built with `makeDefaultData()` from `FlowView.tsx`. For a policy new flow, `inferVariantFromHats()` (same file) additionally decides Stock Issues vs. Advantage from the aff's hat/block headings — `advantage`/`adv N` language ⇒ advantage, `inherency`/`harms`/`significance` ⇒ stock issues (`solvency` is deliberately not a signal — advantage affs have a solvency contention too), tie-break to advantage. This has **no UI at all** — the Stock Issues/Advantage buttons were removed from the target step (Gemini/the local heuristic decides silently); `newVariant`/`variantInferred` stay wired for the future, just unsurfaced. (Same story for the Policy/PF event toggle, removed earlier — the event is taken from `inferEventFromPockets` only, `setNewEvent` stays wired.) For an existing flow, its **actual current** columns (`customColumns` if set, else the default array for its event/pfOrder) and sheet names are read fresh from `flow_data_<id>` before classification, since the user may have renamed either from the defaults.

**Classification — `ai:autoFlowClassify`.** IPC handler in `electron/main.ts` (placed directly after `speechdoc:extractBlocks`), prompt template `electron/prompts/auto_flow_classify.txt`. Takes `{ docs, existingSheetNames, existingColumns, event, variant, clarifications }` and returns `{ ok: true, placements }` or `{ ok: true, question }`. Uses the `'balanced'` model tier. For every card, the prompt is told to decide five things: (1) **column** — match the card's `pocket` case-insensitively against `existingColumns` (e.g. `2NC` and `1NR` both route to a column literally named `2NC/1NR` if that's what's present); (2) **sheet** — match `hat`, then `block`, then `pocket` topically against `existingSheetNames`, proposing a new sheet name (`isNewSheet: true`) when nothing plausibly fits rather than forcing a bad match; the prompt explicitly rules that numbered placeholder tabs from the default layouts ("Off 1"…"Off 4", "Adv 1"…"Adv 3", "Contention N") are **not** topical matches — every case and off-case position must get a properly-named sheet (the semantic stock-issues tabs when they genuinely fit, else a new sheet named after the position), and when naming a new sheet **prefer the doc's own recurring shorthand** for a position (a doc that says "Federalism DA" once but "Fism DA" in every tag after gets a "Fism DA" tab). Three further rules harden this against real 1NC docs that label every off-case block with the SAME generic header ("1NC", "Off", "1NC—OFF") instead of naming the position: (a) **generic headings are not the position name** — when the hat/block/pocket is a generic speech/section label, the model must infer the specific position from the card's own TAG (and neighboring tags) rather than filing on the literal heading; (b) **never merge distinct positions** — a CP and a DA (or two different DAs) under identical "1NC—OFF" headers are separate sheets, and a position is never dropped or absorbed into another just because it's awkward to name; (c) **existing flow with unnamed slots** — when the sheet list has some named tabs and some numbered placeholders (user named "Off 1/2/4", left "Off 3"), each position matches the named tab it belongs to and every OTHER position goes to a NEW sheet, which the write step drops into the remaining empty placeholder — a position is never crammed into a named tab it doesn't belong to. On the write side, `ensureSheet` in `commitWrite` **always appends a brand-new sheet** for a name that doesn't exist yet — it never renames an unused default slot into place. (It used to: it hunted for an empty `/^(off|adv|advantage|contention)\s*\d+$/i` tab and took it over. That quietly repurposed slots the user may have been holding, and made tab order depend on which placeholder happened to be free rather than on the order positions came up in the doc.) The leftover defaults are removed afterwards instead — see **Sheet creation and cleanup** below; (2b) **sheetRole** (`'advantage' | 'offcase' | null`) — which family the card's position belongs to, so tabs are ORDERED: aff advantages first (in 1AC order), then off-case. `distinctNewByRole('advantage'|'offcase')` collects each role's distinct new sheet names in first-appearance order (the model is told to keep placements in document order, so this is 1AC order), and a pre-pass `slotInto` renames the aff placeholder slots (`/^(adv|advantage|contention)\s*\d+$/i`) to the advantage names and the `/^off\s*\d+$/i` slots to the off-case names — running BEFORE any card is placed so it only touches still-empty placeholders. Since aff slots precede off slots in every default layout, advantages end up as the leftmost tabs, in 1AC order, with off-case after; (3) **cite** — a **shortened** cite (`Author 'YY`, or an abbreviated source name if there's no individual author) rather than the verbatim credentials paragraph `ExtractedFlowCard.cite` carries — the handler passes this shortened `cite` straight through to the write step, so no client-side truncation is needed; (4) **respondsTo** — the exact tag text of the card this one directly answers (a perm, a no-link, impact defense), or `null`; (5) **isPlan** — `true` for the single policy plan-text card. The handler coerces `respondsTo` to a trimmed string-or-null and `isPlan` to a boolean; both are best-effort hints that degrade to normal placement if the model omits them.

**Batching — why classify is not one call.** `ai:autoFlowClassify` used to build one prompt with `JSON.stringify(docs).slice(0, 60000)` and cap the reply at 32,768 output tokens. On a real packet that is wrong in both directions: a measured single-file 1AC carries **778 cards**, so the input JSON (250k+ characters) was cut *mid-object* — most cards never sent, and what was sent malformed — while 778 placement objects is well past any 32k output cap, so the reply came back cut off. `parseJsonLoose` then returned `null`, `|| {}` swallowed it, and the handler returned `{ ok: true, placements: [] }`: a multi-minute wait ending in "Warroom AI didn't propose any placements" with no error surfaced anywhere.

The handler now flattens `docs` to an ordered `FlatFlowCard[]` (`electron/autoFlowBatch.ts`) and processes it in `CLASSIFY_BATCH_SIZE` (120) chunks. Document order is preserved end to end, because the prompt numbers advantages by first appearance in the 1AC and the write step lays tabs out in the order placements come back. After each batch, `mergeSheetNames` folds the tabs that batch invented into the next batch's `EXISTING_SHEETS_JSON`, so one position can't come back as "Heg Adv" in batch 1 and "Hegemony" in batch 2 and end up as two tabs. Only the first batch may return a clarifying `question` — later batches pass a non-zero `QUESTIONS_ASKED` so the prompt's own gate suppresses it, and a question aborts the whole run (the renderer re-invokes from the top after the answer) rather than stitching partial work onto placements made under a different assumption.

**Adaptive splitting.** If a batch's response comes back cut off, `classifyBatch` halves the batch and recurses, rather than failing or retrying the same too-large request. `CLASSIFY_BATCH_SIZE` is therefore an optimistic starting guess the run self-corrects from, not a limit that has to be right up front. Truncation is detectable at all because `callAI` now inspects each provider's own signal — Gemini `finishReason: MAX_TOKENS`, OpenAI/Grok/LM Studio `finish_reason: 'length'`, Anthropic `stop_reason: 'max_tokens'` — and throws `truncatedResponseError`; previously every provider returned its partial text and the caller had no way to tell it apart from a complete answer. (`callAI` also now joins **all** Gemini `parts` rather than only `parts[0]`, its own silent truncation vector, and `callOpenAI`/`callAnthropic`/`callGrok` finally honor `extraConfig.maxOutputTokens` instead of hardcoding 8192 and ignoring the argument.) A single card that still can't be answered is a genuine failure and throws with the provider's reason plus the first 300 characters of what came back.

`ai:autoFlowSummarize` is batched the same way at `SUMMARIZE_BATCH_SIZE` (25 — smaller because summaries carry card **bodies**), but per-batch failures are swallowed by design: summaries are best-effort, so a failed batch costs only those cards their summary and they fall back to `tag + cite`.

**Progress and telemetry.** Both handlers emit `ai:autoFlowProgress` (`{ phase, batchesDone, totalBatches, cardsDone, cardsTotal }`), surfaced in `AutoFlow.tsx` as a progress bar and a "Sorting batch 3 of 7 — 240 / 819 cards" line instead of a blank multi-minute spinner. `totalBatches` can grow mid-run when a batch splits. The handler also returns `stats: { cardsIn, placed, dropped, batches }`, shown on the review step as "N of M cards sorted" with a red call-out for anything the validity filter dropped — a silently shorter list used to be indistinguishable from a smaller document. The preload bridge lives in its own `api.autoFlow` namespace, deliberately **outside** `api.ai`: preload's error-toast wrapper is `async` and would turn `onProgress`'s synchronous unsubscribe return value into a Promise.

**No `withDelayedRetry`.** Both Auto Flow handlers deliberately skip it. On failure the renderer drops the user back on step 2 with the "Sort with Warroom AI" button, so they can retry themselves — sitting through 8s/30s/60s of invisible backoff first would only delay an error they can act on immediately. See CLAUDE.md's "AI call retries + error surfacing" rule; every other user-triggered AI handler skips it for the same reason.

**Live writing (new flows only).** A new-flow run skips the review step and writes visibly. `commitWrite(live)` computes the full result exactly as before, but also records an ordered `writeLog` of every cell write. `replayIntoFlow` then persists an emptied copy of the finished layout, navigates to the flow, and replays the log in groups — each group is one `storage.write` plus one `warroom-flow-updated`, which `FlowView` already listens for and reloads from.

Tab-following needs no new plumbing: `activeSheetIdx` is part of `StoredFlowData` and `FlowView` restores it on every reload, so writing the index of the sheet currently being filled *is* the view switch. Groups are sized from `FILL_TARGET_MS / FRAME_MS` so an 800-card packet and a 40-card one both take about the same wall-clock time, with an extra `TAB_SWITCH_MS` beat whenever the write crosses to a different sheet. The finished `finalSheets` (arrows, `aiCells`, tab summaries, and the unused-default cleanup) is written as the last frame, so the end state is byte-identical to a non-live run. A `skipLive` ref — a ref, not state, since the loop reads it between awaits — breaks out to that final frame.

`commitWrite` takes `ctxIn`/`listIn` overrides because the live path is invoked in the same tick as `setTargetCtx`/`setPlacements`, before React has flushed; `ClassifyCtx.target` carries the destination for the same reason, and so the clarifying-question resume path still knows where the result is going. Adding into an **existing** flow deliberately keeps the review step and the single silent write — that flow holds the user's own work, so approval stays opt-in.

**Sheet creation and cleanup.** The rule, shared via `src/lib/flowSheetNaming.ts` so any future flow-editing feature follows it: **need a sheet → make one**, then once the whole operation is finished, drop every sheet that is *both* still default-named *and* completely empty.

`PLACEHOLDER_SHEET_RE` (`/^(off|adv|advantage|contention|sheet)\s*\d+$/i`) is what "default-named" means — the numbered slots the default layouts ship with, plus `Sheet N` from `FlowView`'s "+" button. Anything else ("Politics DA", "Case", "RFD/Notes", "Turns") is a real name and survives even when blank, because an empty tab with a real name is telling the user the position existed but nothing landed on it. `pruneUnnamedEmptySheets` never returns an empty array — if every sheet qualifies (a run where every card was skipped) it hands back the original list rather than leaving a flow with zero tabs.

Two consequences worth noting. First, the old `structuralKeepNames` set is gone: "keep anything with a real name" already subsumes "keep RFD/Notes and the stock-issues aff tabs". Second, cleanup now runs for an **existing** flow too, not just a new one. Under the old rename scheme it couldn't — the user's spare slots were theirs to keep — but now that positions are appended, leaving them would mean every run stacks named tabs after a row of dead defaults. Nothing is lost, since a sheet has to be literally empty to qualify.

Tab ORDER is still a deliberate pass (`createNewSheetsForRole('advantage')` then `('offcase')`) rather than a side effect of Pass 1's iteration. Pass 1 walks `accepted` in document order and would usually produce the same result, but a doc that opens with an off-case card would invert it, and advantages-left-of-off-case is a decision, not a coincidence. Covered by `scripts/test-flow-sheet-naming.ts`.

**Ambiguity escape hatch.** Shares the `AIQuestion`/`AIClarification` contract (`src/types.ts`) with the guided card cutter and Round Analysis — capped at ONE question for the whole batch, never asked once `clarifications.length >= 2`. Worth asking about: a chunk of cards with no usable pocket label at all, or two very differently-named sheets equally plausible for a hat. Never asks permission to create a new sheet — `isNewSheet` already covers that. The renderer's `runClassify`/`answerQuestion` functions in `AutoFlow.tsx` mirror `CardCutter.tsx`'s `runEmphasize`/`answerQuestion` resume-loop shape exactly.

**Review step.** Proposed placements are grouped by destination sheet (new tabs marked **NEW**), each row showing the card's tag (truncated) and its "Sheet → Column" destination with a checkbox to drop it before committing. No inline destination editing in v1 — a wrong placement can be fixed by hand afterward.

**Optional AI card summaries — `ai:autoFlowSummarize`.** A toggle switch on the target step (**off by default**, `summarize` state, styled as a real switch rather than a checkbox so the on/off state is unambiguous) replaces each card's `tag + cite` cell content with a short AI summary of the card built from its tagline **and its evidence body**, capped to strictly fewer words than the tagline itself.

- **Word cap is preloaded.** `extractAll` computes every tagline's word count the moment the docs are uploaded (`wordCounts`, keyed `` `${fileName} ${tag}` ``) — see CLAUDE.md's preload rule — so the cap is in hand before the user ever flips the toggle. The handler is told `maxWords` per card and the prompt (`electron/prompts/auto_flow_summarize.txt`) requires *strictly fewer*; `ai:autoFlowSummarize` then **hard-truncates to `maxWords - 1`** defensively rather than trusting the model to count.
- **Bodies never reach the renderer.** This is the one Auto Flow path that reads card bodies, and it does so entirely in the main process: the handler re-extracts each source `.docx` with `extractFlowCardsFromXml(xml, headingLevels, /* includeBody */ true)` (bodies capped at `BODY_CAP` = 4000 chars/card), builds a `` `${fileName} ${tag}` `` → body map, sends tag+body to the AI, and returns **only the short summaries**. The default (non-summary) path still never requests bodies at all, preserving the "routes tags, never reads evidence" invariant.
- **Feeds the tab hover tooltip too.** `commitWrite` folds each sheet's per-card summaries (up to 3, joined, truncated to 160 chars) into `SheetData.aiSummary` — no extra AI call, just reusing text already generated. `FlowView.tsx`'s `sheetSummary()` leads with that (prefixed `✨`) when present, before falling back to its cheap non-AI first-line-of-each-cell preview.
- **Retries on failure.** Like every other AI call in the app (see "AI call retries" in the Architecture section), the model call here is wrapped in `withDelayedRetry`, which retries the whole call — prompt, parsing, everything — at 8s, then 30s, then 60s, before finally giving up. If all four attempts fail, the renderer falls back to plain tag+cite (per its existing best-effort try/catch) and a toast surfaces the error via `AiErrorToast.tsx`. This covers the AI content this handler produces: the per-card summaries (which replace the tagline in the cell) and the tab's AI summary folded from them.
- **Summary cells are tracked, but not ringed.** `SheetData.aiCells?: string[]` holds the cell keys written from a summary. **No `.ai-glow-ring` is drawn from this** — an AI-generated summary standing in for the tagline is still a tagline, and per CLAUDE.md's AI-ring rule, taglines never get the ring (only the toggle that turns summary mode on does). `aiCells` is kept anyway because `clearAiCell()` still needs it: it drops a key on the first user edit of that cell (the content is theirs from that point on, whether or not anything was ever rendered differently for it), `moveCell` swaps membership with the content, and `insertRowBetween` bumps the keys along with the cells/arrows.
- A summary **replaces** tag + cite (no cite line underneath) — that's what keeps it under the tagline's word count — but still gets the user's Auto Flow tag emphasis. Summaries are best-effort: any card the model skips falls back to normal tag+cite.

**Write step.** Runs entirely client-side in `AutoFlow.tsx`'s `commitWrite()`, writing straight to `storage.write('flow_data_<id>', …)` — **not** through the live Yjs sync path (an acknowledged v1 limitation; live-collaborating peers won't see an Auto Flow write until they reload the flow). It's a **three-pass** placement so answers can align to what they answer:

- **Tab-order pre-pass:** before any card is placed, `slotInto` renames the empty aff placeholder slots to the advantage sheet names (in 1AC order) and the off placeholder slots to the off-case names, per each placement's `sheetRole` (see the classification section). This is what puts advantage tabs first, in the order they came up in the 1AC, with off-case after. Because it renames the leftmost slots, `sheets[0]` becomes advantage 1's tab, so the plan (Pass 0) lands at the top of the first advantage's flow rather than on a bare "Adv 1" placeholder.
- **Pass 0 (plan):** the `isPlan` card is forced to the very first cell of the very first sheet (`sheets[0]`, row 0, col 0), regardless of the column/sheet the AI proposed — or the first empty row of column 0 if 0-0 is already occupied (adding into an existing flow).
- **Pass 1 (originals):** every card with `respondsTo == null` is placed first, at the `firstEmptyRow()` of its column, so its cell address is known before answers are placed. A `placedByTag` map records where each card landed, keyed by `normTag(tag)` — case/punctuation/whitespace-normalized, not the raw string.
- **Matching `respondsTo` against `placedByTag` (`resolveRespondsTo`).** The classify prompt tells the model to copy the answered card's tag EXACTLY, but LLMs routinely paraphrase, fix a typo, or drop punctuation even when told not to — an exact-string lookup silently dropped most same-row alignments in practice. `resolveRespondsTo` tries, in order: an exact `normTag` match; a substring match either direction; then the `placedByTag` entry with the highest word-overlap ratio, accepted only above a 0.5 similarity floor (so an unrelated card is never chosen as a fallback).
- **Pass 2 (answers) is a worklist, not one pass.** A response can itself be answered by a later response (a 1NC turn → 2AC answer → 1NR extension), and the model's output order isn't guaranteed to keep that chain in doc order, so a single left-to-right pass would miss later-appearing links. The write step instead loops: each round, write every remaining `respondsTo` card whose target is already placed, and repeat until a round makes no progress; whatever's left (a dangling reference or a genuine cycle) is written plainly with `firstEmptyRow()`, no alignment or arrow. For each card that does resolve: if the answered card is on the **same sheet**, a **different column**, and its row is free in this card's column, it's written on that **same row** (adjacency is the visual link — no arrow). Otherwise it drops to `firstEmptyRow()` and a `FlowArrow` (`{ id, from: "ri-ci", to: "ri-ci" }`, pushed onto the sheet's `arrows`) is drawn from the answered card's cell to it. Cross-sheet answers (arrow endpoints are per-sheet cell keys) never get an arrow, just normal placement.
- **Placeholder slots are claimed by family.** `ensureSheet` builds a `roleByName` map from the placements and prefers a placeholder of the position's own family (`/^(adv|advantage|contention)\s*\d+$/i` for advantages, `/^off\s*\d+$/i` for off-case), falling back to any free placeholder and then to appending a new tab. Without this, a position that reached `ensureSheet` without being slotted by the tab-order pre-pass took whatever placeholder came first — an off-case DA could land in an empty "Adv 2" and break the advantages-first ordering.

**Blank-tab prune (new flows only).** After all cards are placed, `commitWrite` drops any sheet that ended up with no written cell AND isn't a "structural keep." `structuralKeepNames` is captured from the default sheet names BEFORE the tab-order pre-pass renames anything, as the non-placeholder defaults (everything not matching `/^(off|adv|advantage|contention)\s*\d+$/i`): RFD/Notes, the stock-issues aff tabs (Inherency/Harms/Solvency), PF's Turns. So a 2-advantage doc's unused `Adv 3`, the unused `Off 3`/`Off 4` slots, and any named-but-empty sheet a skipped card left behind (e.g. `ensureSheet` created the tab, then the card was dropped for a `column not found`) are all removed, while the intentionally-blank structural tabs survive. Guarded so it never empties the flow to zero sheets, and it only runs when `isNewFlow` — an existing flow's own empty tabs are the user's and never touched.
- **Arrow geometry for same-column connections.** `FlowView.tsx`'s `recomputeArrows()` used to always anchor the source on one side and the target on the opposite side (built for connecting adjacent columns left-to-right) — for a same-column arrow (source and target share the same `x`, one stacked below the other because the aligned row was taken) that put the two ends on opposite edges of the column, producing a large lopsided hook across the cells between them. It now detects `sameColumn` (`|fr.left − tr.left| < 2`) and instead anchors **both** ends on the column's right edge, jogging out by a small fixed distance (20px) regardless of how far apart the rows are, drawing a clean bracket that hugs outside the column rather than sweeping through it.

Sheet lookup/creation is case-insensitive exact name match; `findColumnIndex()` (`src/lib/autoFlowPlacement.ts`) matches the column by case-insensitive exact match against the flow's real columns (no fuzzy matching on this side — that's entirely the AI's job upstream, since it was told to echo a column back verbatim); `firstEmptyRow()` scans `cells['<row>-<col>']` for the first unoccupied row 0..`NUM_ROWS`-1. If a column has no room left, the placement is skipped and surfaced in a "N cards didn't fit" summary rather than dropped silently. The pure helpers plus `inferEventFromPockets`/`inferVariantFromHats` have a headless test, `scripts/test-auto-flow-placement.ts` (included in `npm run test:flows`).

**Tag styling.** The cell HTML is `tag<br>cite`, with the tag wrapped in whatever emphasis is set at **Settings → Auto Flow tag style** (`src/lib/autoFlowTagStyle.ts`, key `warroom-autoflow-tag-style`, defaults `{ bold: true, italic: false, underline: false, color: null, fontSize: 13 }`). Only `bold`/`italic`/`underline` are actually applied to the cell (as `<b>`/`<i>`/`<u>`) — `color` and `fontSize` are captured and shown in the settings live preview but never written into a cell, because `src/lib/cellHtml.ts`'s `ALLOWED_STYLE_PROPS` has no per-run color or font-size support (a flow has no text-color picker, and cell font size is a view-level setting, not per-cell) — anything else would be silently stripped by `cellToHtml()`/`sanitizeCellHtml()` the next time the flow renders. The cite line is always plain text.

Auto Flow is a self-contained wizard, not a Warroom Agent tool — its IPC handler is intentionally absent from `AGENT_TOOLS` and `warroom-mcp/server.js`, the same way the card cutter's and Round Analysis's handlers are.

## Speech Doc Viewer

The `SpeechDocViewer` renders `.docx` files in-app using `docx-preview`. It is always mounted (hidden when inactive) so it preserves state across navigation. Recent docs are tracked in `localStorage` under `warroom-speech-doc-recents` (cap `RECENTS_MAX` = 40). That list doubles as the sidebar's **Cases** list, so every write dispatches a `storage` event and the sidebar re-reads — the cap is a real library limit, not just a "recently opened" convenience.

Opening a `.docx` from Finder triggers the `onFileOpen` IPC event and navigates to the speech-doc view. Speech docs can also be attached to chat messages and shared with teammates.

**Multi-upload.** Both the drop zone and the file picker accept many docs at once. `dialog:openFiles` opens a `multiSelections` dialog and trusts + persists every chosen path. `importDocs(paths)` batch-writes them all to recents via `addRecents` (one write, one event) **before** loading the first — so the whole batch appears in the sidebar immediately, and a doc that fails to render still lands there rather than vanishing.

**Drop zone feedback.** This is one of the app's three file-drop targets — AutoFlow, AnalyzeRound (supplementary docs), and this one — all sharing `useDragActive()` (`src/hooks/useDragActive.ts`) for the drag-over reaction (accent border + tinted background while a file is dragged over; `onDragLeave` checks `relatedTarget` so hovering the zone's own children doesn't flicker it off). After a drop, this zone unmounts in favor of `LoadingPanel`/`step === 'loading'`, same as Auto Flow swapping to its `step === 'extracting'` `LoadingState` screen — visible "something is happening" feedback that doesn't need its own progress bar. AnalyzeRound's zone is the one exception: it stays mounted through the read, so it shows a `ProgressBar` (`src/components/ProgressBar.tsx`, indeterminate — `wr-indeterminate` keyframe in `index.css`) in place of the drop prompt while `docsLoading` is true.

**Folder import.** `pickFolder()` calls `dialog:openFolderOfDocx` (main process — recursive walk, capped at 2000 files, same trust anchor as the dialog-based imports), batch-adds every found `.docx` to recents the same way, then creates a new `CaseFolder` named after the picked directory and files every imported doc into it in one `useCaseFolders().update()` call, so a folder import always lands as one correctly-named group rather than scattering into the top level.

Electron removed `File.path` in v32, so dropped files can't be read from `dataTransfer` directly. The preload's `dialog.resolveDroppedFiles(files, accept)` resolves them via `webUtils.getPathForFile`, filters by extension, and calls `fs:trustDropped` to trust + persist each path. This takes `File` objects rather than strings on purpose: `getPathForFile` only resolves genuine `File`s — a renderer cannot forge one carrying an arbitrary path — so an OS drag-drop is as legitimate a trust anchor as a file dialog, and the `checkPath` guarantee (handlers only read paths the main process handed out) stays intact.

The toolbar also includes **Focus mode** (hides body text, showing only card structure and highlighted/underlined runs), **Find** (in-doc search), **Reading time / auto-scroll**, **Send to Flow** (push a card/heading into a flow sheet, see below), **Cross-Ex Practice**, and **Card Credibility** (see below). Outline navigation lives on a left-edge pull-tab instead of the toolbar (see below). The open document's name is always rendered in the toolbar between the tool cluster and the AI-tool pills (`fileName`, `.docx` stripped).

**Side-by-side compare (up to 3 panes).** `SpeechDocViewer`'s default export is now a thin wrapper that mounts 1-3 independent `DocPaneViewer` instances in a row. Pane 0 always tracks the app's global `view` state, so every existing open-doc call site (Sidebar, Home, CasesGrid, OC-case save flow) keeps working unchanged and keeps OC live-case support. Panes 1 and 2 are extra compare panes, tracked in `appStore`'s `extraDocPanes: [string|undefined, string|undefined]` (`undefined` = closed; every other value is always a real, loaded file path — see below) plus a `focusedPane: 0|1|2`. A **compare-doc** button (`IcoAddPane`) lives in every pane's tool cluster (and on the idle drop-zone, top-right) rather than a hidden hover strip, so it's always discoverable; it's hidden once 2 extra panes are already open. Each extra pane shows the same drop-zone/browse/recents empty state as the main pane and loads its file locally, but it **must report that path back up** via the `onPaneDocPathChange` prop, which the wrapper writes into `extraDocPanes[slot]`. This is not optional bookkeeping: an earlier version let the slot sit at `''` forever once opened, so the store only ever knew "a pane is open", not *which doc was in it* — which silently broke every feature keyed on the **set** of open docs (per-combination layout memory and the sidebar's compare-views list both saw fewer than 2 real paths and no-oped). `loadFile` calls it right after setting `loadedPath`, so the resulting prop change is a no-op in the auto-load effect rather than a reload loop.

**"+ compare doc" is local, ephemeral state — never written into `extraDocPanes`.** It used to write the `''` open-but-empty sentinel straight into the store, which is exactly the shape session-restore (`saveSessionPanes`/`loadSessionPanes` in `appStore.ts`, persisted to `localStorage`) can't tell apart from "a real saved pane" — click **+**, close the app before ever dropping a file into it, and the next launch resurrected a phantom empty third pane, unprompted, with nothing to show but its own drop-zone. `addPane()` now sets `pendingEmptySlot: 0 | 1 | null` (wrapper-local `useState`, not store state) instead; the `panes` array construction inserts a `{ pending: true }` entry for that slot only while it's still both non-null *and* the corresponding `extraDocPanes` slot is still `undefined`, so it renders identically to before but is invisible to persistence — there's simply nothing for `saveSessionPanes` to see. An effect clears `pendingEmptySlot` back to `null` the moment a real file lands in that slot (`extraDocPanes[pendingEmptySlot] !== undefined`); closing a pending pane's × clears it directly rather than calling `setExtraDocPane` (which would be a no-op on an already-`undefined` slot). `openExtraCount`/`openPaneCount`/`canAddPane` all count the pending slot as open too, so the **+** button and `toolbarCompact` react to it exactly like a real third pane while it's showing.

Only the **focused** pane responds to pane-scoped keyboard shortcuts (currently ⌘F/Ctrl+F) — gated by a `focused` prop threaded into those `useEffect` listeners — so three mounted panes don't all react to the same keypress. Clicking anywhere in a pane (`onMouseDownCapture`) focuses it. Extra panes get a close (×) button next to their filename that clears their store slot. Side panels with a preferred fixed width (`OutlinePanel`, `CredibilityPanel`, `CrossExPanel`) use CSS `min(Npx, X%)` plus `overflow-hidden` on their row so a narrow pane clips its own content instead of visually spilling into the next pane's toolbar. Double-clicking a pane's title renames it in place — an OC case's `db.cases[id].name`, or a plain file's recents entry — never the file on disk.

**Navigating anywhere leaves compare mode.** `setView`, `goBack`, and `goForward` all reset `extraDocPanes` to `[undefined, undefined]` and `focusedPane` to 0. Without this, clicking a doc in the sidebar while comparing only swapped the file *inside pane 0* — the 2-3 pane layout stayed up, so the user had no way back to reading a single doc, and each click silently redefined the set of open docs (spawning a compare-view entry every time). Restoring a saved compare view therefore sets its extra panes **after** calling `setView`, in the same tick. The main pane reporting its own newly-dropped file uses `setMainDocPath` instead of `setView` precisely to avoid both side effects — it's the same view gaining a file, not a navigation, so it must not push nav history or tear down the compare panes.

**Pane widths, per-pane outline state, and sidebar override — all lifted to the wrapper, all persisted per doc combination.** These used to be local to `DocPaneViewer` (outline) or purely deterministic (sidebar). Now:
- `outlineOpen` is a **controlled prop** on `DocPaneViewer` (`outlineOpen`/`onOutlineOpenChange`), backed by `paneOutlineOpen: boolean[3]` state in the wrapper — DocPaneViewer still renders `OutlinePullTab`/`OutlinePanel` itself (no change to *where* the outline's DOM lives, just who owns the boolean), falling back to its own local state only if unmounted standalone (never happens in practice).
- Pane widths are real pixel values (`paneWidthsPx`, from `computePaneWidthsPx`), not `flex-1` — each pane wrapper renders `width: Npx; flex: 0 0 auto` once the row's width has been measured via `ResizeObserver` on the scrollable row ref (`rowWidthPx`); before the first measurement it falls back to `flex: 1 1 0%` so there's no flash-of-zero-width.
- **`utils/docComboLayout.ts`** persists `{ paneWidths, outlineOpen, sidebarExpanded, chatOpen, geminiOpen }` in `localStorage['warroom-doc-combo-layouts-v2']`, keyed by `comboKeyFor()` — the exact, ordered doc paths of every currently-open pane joined on a unit-separator char. Fewer than 2 resolved paths (or an OC case in pane 0, which has no plain path) returns `null` and nothing persists. The wrapper re-hydrates `paneOutlineOpen`/`paneWeights` from the saved combo whenever `comboKey` changes (`lastComboRef` guard).
- **Divider drag**: a 5px handle between adjacent panes (`onDividerMouseDown`) adjusts `paneWeights[i]`/`paneWeights[i+1]` from mouse delta (`deltaPx / rowWidthPx * totalWeight`), clamped to a 12%-of-total floor each, and **snaps to dead-equal width** (`DIVIDER_SNAP_PX = 10`) whenever the drag lands within 10px of the halfway point, so nudging toward center reliably lands on exactly 50/50 instead of a near-miss. On mouseup it writes the final weights into the current combo via `saveComboLayout`. Disabled (`dividersEnabled = false`) whenever the "space" outline-layout method has any pane's outline open — that split isn't meant to be user-adjustable.
- **Sidebar, AI panel, and team chat overrides — same mechanism, three targets.** `Sidebar.tsx`'s `useCollapsed()` hook reads `extraDocPanes`/`view` from the store; its `toggle()` (fired only by the user's own collapse/expand click — the deterministic force-collapse path calls `setC` directly, bypassing `toggle()`) writes `saveComboLayout(comboKey, { sidebarExpanded: !next })` whenever multi-pane is active. `appStore.ts`'s `setChatOpen`/`setGeminiOpen` do the equivalent for the chat and AI panels — every UI call site (`TitleBar.tsx`'s toggle buttons, `Home.tsx`, `Chat.tsx`'s close button, `GeminiPanel.tsx`'s close button) goes through these, so any manual open/close while a combo is active is recorded as that combo's override automatically, with no per-call-site wiring needed. The wrapper's force-collapse effect in `SpeechDocViewer.tsx` applies all three overrides once per combo (`appliedOverrideForRef`), right after its default "just became multi → collapse sidebar, close chat/AI if open" dispatch, so an existing override always wins. Forced changes use separate `forceChatOpen`/`forceGeminiOpen` store actions that skip the override-recording logic (a forced close isn't a user preference); leaving multi-pane restores chat/AI to whatever they were immediately before entering it (`chatWasOpenRef`/`geminiWasOpenRef`), not unconditionally re-opened the way the sidebar always re-expands — chat/AI default to closed far more often than the sidebar defaults to collapsed, so blindly reopening them on exit would be a bigger surprise than the sidebar case.
- **Toolbar overflow menu**: the wrapper passes `toolbarCompact={openPaneCount > 1}` to every `DocPaneViewer`. When set, the reading-time and send-to-flow toggles drop out of the tool cluster and the two `ToolbarPill`s are replaced by a single `ToolbarOverflowMenu` (⋯, opens on hover with a ~160ms close delay so the pointer can cross the gap). Menu rows keep full text labels; rows flagged `ai: true` (Credibility, Cross-Ex) get a small gradient dot rather than the full `.ai-glow-ring` (the ring's `inset: -2px` mask bleeds into zero-gap stacked rows), while the ⋯ trigger itself gets neither — its contents are a mix of AI and non-AI tools, and ringing it would promise an API call just to open a menu. Comments is not part of this menu — it's a standalone, always-icon-only button regardless of pane count (see Doc Comments below). The highlight-readability slider follows the opposite rule from Comments: it's folded *into* this menu (via `ToolbarOverflowMenu`'s `extra?: React.ReactNode` prop, appended after a divider) rather than kept as its own standalone trigger once compact, so a compact pane never shows two "⋯" buttons side by side — `!toolbarCompact && <HighlightReadabilityMenu />` renders the standalone version only when there's no overflow menu for it to live inside instead.
- **Saved compare views**: `docComboLayout` also records `paths` + `savedAt` per combo (`rememberComboView`, called from the wrapper's combo-change effect) and exposes `listComboViews()` / `deleteComboView()` / `pruneComboViews()` plus a `COMBO_LAYOUTS_CHANGED` window event that `writeAll` announces. `CompareViewsGroup` in `Sidebar.tsx` renders them right under Cases — above folders/docs, no text header, just the rows and a light `border-bottom` divider separating them from the regular list — resolving display names from the live `buildCaseItems` list (so renames propagate) and restoring all panes on click via `setView` + two `setExtraDocPane` calls. Deletion goes through `pushUndoToast(message, onUndo)`. `pruneComboViews` is guarded on a non-empty name map — it deletes, so a partial recents read must not be able to wipe the list (same class of hazard as the `case_folders` incident).
- **Rename a compare view**: double-click a row (`CompareViewRow` in `Sidebar.tsx`, same local-state input pattern `FolderRow` already uses for folder rename) to give it a custom label — `renameComboView(key, name)` saves it as `customName` on that combo's `ComboLayout`. An empty/whitespace-only name (or retyping the auto label verbatim) clears `customName` back to `undefined`, which falls back to the auto-generated joined-doc-names label; the row's `title` tooltip always shows the full joined names underneath the custom name so the actual docs stay discoverable even once renamed.

**Toolbar must not clip.** The toolbar row deliberately has **no** `overflow-hidden`: `IconBtn`/`ToolbarToggle`/`ToolbarPill` render their hover tooltips as `absolute top-full` elements *below* the bar, so clipping the row silently swallows every tooltip in the pane (this shipped as a bug once). Overflow is instead handled by shrinking — the title flexes with `min-w-0`, and in multi-pane the analysis tools fold into the ⋯ menu. `FocusBtn` is unaffected either way since it positions its tooltip `fixed` from a measured rect.

**Two outline-layout methods** (Settings → "Outline layout in compare view", `localStorage['warroom-doc-outline-layout']`, `warroom-doc-outline-layout-changed` event, default `'space'`), both computed in `computePaneWidthsPx()` and both achieved purely through per-pane width numbers — no separate DOM element is inserted for the outline; it still renders *inside* whichever pane owns it, at that pane's own left edge, and the trick is sizing that pane's box (and its neighbor's) so the outline visually lands in the right place:
- `'squish'`: the active pane borrows up to `OUTLINE_SPACE_PX` (248, matching `OutlinePanel`'s own width) from one neighbor — left neighbor, or right if the active pane is index 0 — floored so the neighbor never drops below 120px. Total row width is unchanged (100%, no scroll); the active pane's own reading width is unaffected, the neighbor absorbs the cost.
- `'space'`: the active pane's "partner" is the next pane (index+1) if one exists, else the previous one (index-1) — this asymmetry is deliberate (matches product spec: opening the outline on the *last* pane pairs it with the one before; anywhere else it pairs with the one after). Active + partner + the outline column together fill `rowWidthPx − SPACE_PEEK_FRACTION * rowWidthPx` (i.e. ~85% of the viewport), each reading pane getting `(rowWidthPx − OUTLINE_SPACE_PX − peek) / 2` with a 160px floor; the active pane's box is its reading share *plus* `OUTLINE_SPACE_PX`. **Every other pane keeps its natural weighted width, untouched** — they leave the viewport by being scrolled past, not resized. Row total therefore exceeds the viewport (intentional — `overflow-x-auto` on the row), and an effect scrolls to the *first pane of the pair* minus the peek, so the pane before it stays visible at the left edge as a scroll affordance. This replaced an earlier design that crushed non-pair panes to a 64px sliver: users read that as "the app broke my first doc", and a pane that narrow can't render its own toolbar coherently anyway. `'space'` only ever has one active pane at a time — `handleOutlineOpenChange` clears every other pane's `outlineOpen` when opening a new one under this method (opening a second one under `'squish'` is fine, they compose independently).

**Focus mode always shows cite paragraphs in full.** `applyFocusMode` treats a cite paragraph (the one right after a tag) the same as the tag paragraph above it — always visible, regardless of mode — *unless* the debater actually highlighted part of it, in which case normal highlight/underline rules take over. This used to only keep the paragraph's *leading bold run* visible (the assumed author+date) and hide everything after the first non-bold span, on the theory that a cite always bolds its author. Plenty of cites don't bold the author at all, so that leading-bold span never existed and the entire cite silently vanished — the paragraph-level check now applies to any cite, bold or not.

**Office-font substitution.** macOS ships no Calibri, so `docx-preview`'s inline `font-family: Calibri` would fall back to the browser default serif (Times New Roman-like) — wrong for nearly all debate docs. A one-time global `@font-face` block (id `wr-docx-fonts`) redefines the Office families (`Calibri`, `Calibri Light`, `Aptos`, `Aptos Display`, `Cambria`, `Cambria Math`) with `local()`-only source chains that resolve to real Office fonts when installed, else metric-compatible open fonts (Carlito/Caladea), else a clean system sans-serif (`Helvetica Neue`/`Arial`) for the sans families.

**The theme-font gap.** Aliases alone are not enough. Modern Word docs often leave the latin font *unset* on body runs — a run carries only `w:rFonts w:cs="Calibri"` (complex-script) and inherits its real font from `docDefaults` → `w:asciiTheme="minorHAnsi"` → the **theme** font (Aptos) in `theme1.xml`. `docx-preview` does **not** resolve theme fonts, so those runs emit no inline `font-family` at all and fall through to Chromium's default serif. This is why a doc could render sans-serif headings (which set Calibri explicitly) but serif body text, despite the document intending one font throughout — and why an `@font-face 'Aptos'` alias cannot fix it, since the string "Aptos" is never emitted. The fix: the injected `#wr-docx-fonts` style block sets a page default, `section.docx-render { font-family: <Calibri sans stack> }`, so theme-inherited runs land on the sans stack while runs that DO resolve a font (Calibri headings, a genuinely Times-New-Roman body) keep it — docx-preview styles those per-element, which beats this selector.

**Mind the page class.** The page `<section>` takes its class from `renderAsync`'s `className` option (`createPageElement(this.className, ...)`), so `SpeechDocViewer` pages are `section.docx-render` and `section.docx` matches nothing there. `GoogleDrivePanel` passes no `className` and gets docx-preview's `'docx'` default; `CasePreview` passes a per-item hashed class because docx-preview scopes all generated CSS to that class and shared classes would make thumbnails clobber each other. Check the call site before writing a selector. See `DEBATE_DOC_STRUCTURE.md` §6.

**Stale Times New Roman on deep headings.** A different problem than the theme-inheritance gap above: Word's built-in Heading5–9 styles default to Times New Roman, and templates that only ever customize the shallow levels a debate doc actually uses (1–4) leave that stale default on any tag that happens to nest deep enough to hit Heading5+. That font is set *inline* on the paragraph (not just implied by a class), so it wins over the page-level CSS default on specificity — a class selector can't fix it. `forceHeadingFont(container, headingClasses)` walks every `<p>` after render and, for any paragraph `headingLevelOf()` identifies as a heading, sets `font-family` to the same Calibri stack with `!important`, overriding the stale inline font regardless of what triggered it. `CasePreview.tsx` applies the same fix to its thumbnails, but regex-only (`/heading[\s_-]?[1-9]/i` on the paragraph's className) rather than the full `styles.xml` resolution — it catches the built-in-style case this exists for without an extra IPC round-trip per thumbnail render.

### OpenCaseList-imported cases

Cases imported from an opponent's disclosure (**+ Save to Cases** in the opponent file viewer) are stored in `db.cases` with an `ocSource` object (`teamName`, `label`, `url`, `importedAt`, `byteLen`). The `Router` detects `view.kind === 'case'` with an `ocSource` present (`ocCaseActive`) and routes it to the always-mounted `SpeechDocViewer` instead of the block-based `CaseView`, so it gets the full toolset. The viewer derives the active OC case from `view` + `db` (no second instance), loads the docx via `loadOcCase`, and renders it through the shared `applyRender` path. The docx bytes are cached in `localStorage` under `warroom-oc-docx-<url>` (capped ~2.5 MB/doc), pre-warmed at import time, so reopening is instant and offline — no OpenCaseList re-fetch. The toolbar shows an "Imported from [team]" label and a **Check for changes** button (`checkOcChanges`) that re-fetches, compares byte length against the stored `byteLen`, and reloads + re-caches if it changed. Per-doc state (cross-ex, credibility, dismissed warnings, share) is keyed on a synthetic `oc:<url>` path so it works without a real local file.

### Find (in-document search)

A magnifier toolbar button (or ⌘F / Ctrl+F) opens a find bar. Matches are painted using the **CSS Custom Highlight API** (`CSS.highlights` + `Highlight` + `Range`) rather than by wrapping nodes in `<mark>`, so the document DOM is never mutated — focus mode, the outline `data-outline-id`s, and dark-mode fixes all stay intact. `buildFindMatches` walks text nodes (skipping `data-focus-hidden` ones), builds a `Range` per case-insensitive match (capped at 5000), and registers two highlights: `wr-find` for all matches and `wr-find-active` for the current one, styled via injected `::highlight()` CSS. Enter / Shift+Enter (or the chevrons) move between matches and scroll the active `Range` to center; the bar shows "current / total". Searching is debounced 120ms. Highlights are cleared on close and when a new doc loads.

### Reading time & auto-scroll

An hourglass toolbar button opens a popover estimating how long the document takes to read **aloud** at the user's words-per-minute. The word count is "spoken words" only — `collectSpoken` walks paragraphs and counts a run when its paragraph is a heading (pocket/hat/block/tag), when the run is highlighted, or when it is the leading bold author+date of a cite (the paragraph right after a tag). It deliberately does NOT count plain underlined or generally-bold body text — counting those inflated the estimate ~3× versus Verbatim, which measures highlighted words. This is computed at load; if there is a non-collapsed selection inside the viewer (tracked via a debounced `selectionchange` listener while the popover is open), it counts spoken words within that selection instead. Highlight detection goes through `isSpanHighlighted`/`isHighlightedEl` (`data-hl-kind` first — the tag `tagHighlightElements` stamps from the doc's pristine color right after render, see "Highlight readability slider" further down — falling back to the raw brightness heuristic only for untagged elements), so it stays correct after the readability slider or dark-mode dimming has recolored a highlight; re-deriving "is this a highlight" from *current* computed background used to undercount spoken words once a highlight had been recolored, which quietly shortened the estimate and — since auto-scroll paces itself to that estimate — made playback feel faster than it should. The WPM is persisted in `localStorage` under `warroom-reading-wpm` and exposed via `loadWpm`/`saveWpm`; preset chips set ~175 (lay/traditional) and ~300 (flow/spreading) with on-screen guidance.

**Auto-scroll** drives `scrollWrapRef.scrollTop` with a `requestAnimationFrame` loop; a floating control pill lets the user pause/resume, change speed live (the loop reads `wpmRef`), or stop. Manual scrolling during playback is detected and the accumulator resyncs to the user's position. Auto-scroll stops on doc reload and viewer unmount. Pace is either flat or **adaptive** (Settings → "Adaptive reading pace", `warroom-doc-adaptive-pace`, default on, `warroom-doc-adaptive-pace-changed` event):
- **Flat** (setting off): a constant rate, `(wpm/60000) * (scrollHeight / docWords)` px/ms — the document's total height divided by its total spoken-word count, applied uniformly, so the whole doc takes exactly `docWords/wpm` minutes regardless of where the spoken content actually sits.
- **Adaptive** (default): the same `collectSpoken` pass that computes `docWords` also requests `wantRanges: true`, and `buildSpeedProfile` (`SpeechDocViewer.tsx`) attributes each returned spoken Range to its containing `<p>` (via `.closest('p')`), producing one `SpeedSegment { top, bottom, words }` per paragraph — position measured by `getBoundingClientRect()` deltas against `scrollWrapRef` (not `offsetTop`, since a paragraph's `offsetParent` isn't guaranteed to be the scroll wrapper) so it's directly comparable to `scrollTop`. Every `autoStep` frame looks up the segment roughly 35% of a viewport-height ahead of the current scroll position (approximating where the eye is actually reading, not the sliver of text just entering view) and computes local pace as `segmentHeightPx / segmentWords` — dense cards (many spoken words in a short paragraph) scroll slower, sparse context (few or no spoken words over a tall paragraph) scrolls faster. Clamped to `[0.35×, 3×]` the flat rate so an empty-segment edge case can't spike to an absurd speed, and eased toward the clamped target with per-frame exponential smoothing (`1 - e^(-dt/500ms)`) so pace changes read as a gradient at paragraph boundaries rather than a visible step. Because `Σ(segmentHeightPx / segmentWords × segmentWords) = Σ(segmentHeightPx) = scrollHeight` by construction, the *total* time to reach the bottom stays the same `docWords/wpm` minutes as the flat rate — adaptive pacing redistributes *where* that time is spent, it doesn't change how much of it there is (the speed clamp introduces only minor drift from this, on outlier segments). The smoothed pace value resets fresh (`smoothedPxPerWordRef.current = 0`) each time playback starts, not on resume after a pause.

### Outline (heading navigation)

A slim **pull-tab** (`OutlinePullTab`) fixed to the left edge of each pane — not a toolbar button or a permanent panel — opens `OutlinePanel` as a normal flex sibling (not an overlay) listing every heading in the document — pockets, hats, blocks, and card tags — indented by level, so the user can jump anywhere in one click instead of scrolling. Opening it pushes the doc content over rather than covering it; the panel's own header × (or the pull-tab again) closes it. Every doc load calls `setOutlineOpen(localStorage['warroom-doc-auto-outline'] === 'true' && built.length > 0)` — a plain binary read of the Settings → "Always open the outline" toggle, checked live: on shows it for every doc, off leaves it closed every time (no "first doc of the session" carve-out or remembered state — it's deterministic on the setting alone). Row height and indent were tightened (`py-0.5`, 11px-per-level indent, 16px chevrons) versus the old panel so more of the doc's structure fits without scrolling. `docx-preview` renders every paragraph as a `<p>` and tags it with a class derived from the paragraph's style id (`docx-render_<styleid-lowercased>`); Verbatim and Word built-in heading styles use style ids `Heading1`–`Heading9`, so heading paragraphs carry classes like `docx-render_heading4`. `buildOutline` scans for `<p>` elements whose class matches `/heading(\d)/i`, stamps each with a stable `data-outline-id`, and records its level + text. Clicking an entry `scrollIntoView`s the matching paragraph and flashes it. A scroll listener on the viewer (throttled with `requestAnimationFrame`) tracks which heading is currently at the top of the viewport and highlights it in the panel. Prev/next chevron buttons live **in the outline header** (not the toolbar) and step through the headings relative to the active one. If a doc uses no heading styles, the panel shows a "No headings found" notice.

**Click-to-jump pin.** `scrollToHeading` sets `pinnedActiveUntilRef.current = Date.now() + 500` before scrolling. Without this, the `scroll` event that `scrollIntoView` fires re-triggers the scroll listener above, and a short/bare heading (an organizational tag with no body under it — "Case" immediately followed by "Procedurals," common in deep-nested docs) lands within that listener's 90px detection window right alongside the *next* heading down; the listener's "last heading within the window wins" rule then silently overrides the just-clicked heading with its neighbor a frame later. The scroll listener checks the pin and skips its own update while it's active, so a click can't be immediately undone by the scroll it causes.

**Heading-level collapse.** Like Verbatim's NavPaneCycle, a layers button in the outline header cycles `visibleDepths` from 1 up to the number of distinct heading depths present, then back to 1. Items deeper than `visibleDepths` are filtered out, so the user can collapse a long file to just pockets/hats and expand back. Distinct levels are compressed to consecutive depths (`depthOf`) so an H1→H4 jump doesn't over-indent.

**Per-branch collapse (Word Navigation Pane style).** Independent of the depth-cycle cap above, each branch can fold on its own. `buildOutlineTree` reconstructs parent/child structure from the flat heading list — a classic "nearest preceding item with a strictly smaller level is the parent" stack algorithm, built from raw `level` (not the collapsed rank) so a level skip still nests correctly. Collapsed branches are a `Set<string>` of item ids, reset to empty whenever `items.length` changes (a new doc loaded, the same heuristic the depth-cycle reset already relies on). Two different notions of "depth" are in play simultaneously and deliberately kept separate: `depthOf(item.level)` (level-rank) still governs indentation width and the depth-cycle cap exactly as before, while the raw structural tree depth governs only which nodes a collapsed ancestor hides. A chevron only appears on a node if it has at least one child that isn't *already* excluded by the depth-cycle cap — otherwise clicking it would visibly do nothing.

**Highlight-outlier warnings.** `computeHighlightWarnings` measures each card's `highlighted_words / total_body_words` ratio, computes mean + standard deviation across all cards (needs ≥4 cards with bodies ≥20 words), and flags cards >1.5σ above the mean as `'over'` and >1.5σ below as `'under'`. These are cross-referenced into the outline items (a card tag carries both `data-outline-id` and `data-cred-id`) so flagged tags show an amber `WarnBadge` with a popover explaining the issue and a permanent dismiss. Dismissals are stored per-doc in `localStorage` under `warroom-hl-warn-<path>`.

### Send to Flow

A grid-with-arrow toolbar button opens a top-right popover that bridges the speech doc to a Verbatim-style flow (`.xlsx`) sheet, mirroring Verbatim's Send-to-Flow. The user picks a **mode** — `text` (the current selection, or the active heading if nothing is selected) or `shorthand` (the active card's tag plus its cite author+date, extracted by `citeShorthandAfter` from the leading-bold run after the tag) — then a target **flow**, **sheet**, and **column**. The content preview updates live via a `selectionchange` listener. On send, the popover reads `flow_data_<id>` from storage, finds the next empty row in the chosen column (`NUM_ROWS` cap), writes the cell, and saves; column resolution mirrors the FlowView/MCP logic via `flowColumnsOf` (custom columns, else `POLICY_COLS`/`PF_*_COLS`). It then dispatches a `warroom-flow-updated` CustomEvent so an open flow live-reloads. The Send-to-Flow and Reading-time popovers are mutually exclusive (both anchor top-right).

### Cross-Ex Practice

A "Cross-Ex Practice" button in the viewer toolbar opens a right-hand panel that uses Warroom AI to generate targeted cross-examination questions for the open document, each paired with a model answer. The document is run through the same `speechdoc:extract` used by token-saving, giving the AI the **highlighted/underlined text** (what the opponent actually reads) separately from the **full small text**. The `ai:crossExQuestions` handler loads the skill for the user's current event (`cx_debate` for Policy, `ld_debate` for LD, `pf_debate` for PF) so questions use the right vocabulary and strategy. Prompt templates: `electron/prompts/cross_ex_questions_initial.txt` (first generation) and `electron/prompts/cross_ex_questions_followup.txt` ("3 more like this"); both reference the shared `electron/prompts/cx_shared_rules.txt` and (initial only) `electron/prompts/cx_side_guidance.txt` via `{{CX_SHARED_RULES}}` / `{{CX_SIDE_GUIDANCE}}` placeholders. The trap drill (`ai:crossExTraps` / `ai:crossExGradeTrap`) uses `electron/prompts/cross_ex_traps.txt` and `electron/prompts/cross_ex_grade_trap.txt`.

Question rules enforced by the prompt: questions target highlighted text only (the one exception being un-highlighted small text that directly and completely contradicts highlighted text in the same card); questions are 1-3 sentences and answers 2-4 sentences; no markdown emphasis (key phrases use 'single quotes', rendered bold by `CxText`).

**Aff/Neg sections.** The handler asks the model to decide whether the doc is Aff, Neg, or both — using speech labels (1AC/2AC/1AR/2AR = aff; 1NC/2NC/1NR/2NR = neg) and argument type — and returns `{ groups: [{ side, questions }] }`. Question counts are weighted by how much highlighted content each side has (e.g. 8 aff cards vs 1 neg card → several aff questions, 0-1 neg). The panel renders an Aff / Neg header per group when both sides are present.

### Card Credibility

A shield-icon "Credibility" toolbar button opens a right-hand panel that grades the evidentiary credibility of every card in the open doc. It is **mutually exclusive with the Cross-Ex panel** — opening one closes the other. The renderer extracts cards directly from the rendered DOM via `buildCards`: a "card" is a paragraph at the deepest heading level present (Heading4 in Verbatim docs) used as the tag, plus the following non-heading paragraphs as the cite (capped at ~80 words / 600 chars). Cards are sent **numbered** to the model.

`buildCards` skips any heading with no citation text under it (section headers, blank tags, analytics) using a `wordCount(cite) === 0` check, so only real cards (tag + cite) are scored.

The `ai:scoreCards` handler in `electron/main.ts` takes `{ cards: { tag: string; cite: string }[] }` and returns `{ ok, scores?: { score, verdict, author, recency, source, claim, reason, press }[], error? }`. In **one AI call** the model scores all cards at once and returns a JSON array in the **same order**; results map back to cards by index. Each card gets an overall **score 0–10**, a one-word **verdict** (Strong 8–10 / Solid 6–7 / Shaky 4–5 / Weak 0–3), four sub-scores (**Author qualifications**, **Recency**, **Source quality**, **Claim fit** — whether the cite actually supports the tag's claim), a short **reason**, and a **"press"** line — the single best cross-examination attack on that card's credibility. The prompt gives the model an explicit rubric per factor: author scored by **domain match** (with org reputation as a proxy when no individual credentials are stated — RAND/CBO/CRS high, ideologically-aligned think tanks mid, media low), recency by **topic-specific decay rate** (geopolitics decays fast, theory slow), and source by a publication-quality hierarchy. Prompt template: `electron/prompts/card_credibility_scoring.txt`.

The call uses `callAI(prompt, 'balanced')`. The **balanced tier** is the user's selected model from Settings, but never the cheapest "lite" model — e.g. Gemini 2.5 Flash Lite is bumped up to Gemini 2.5 Flash (analogously for OpenAI/Anthropic). The prompt instructs the model to judge author and source **only** from what the cite text states and to **never fabricate** credentials, dates, or outlets.

Results are cached per document in `localStorage` under the key `warroom-cred-<path>`, keyed by a content hash (`hashCards`, which hashes the tag text only — cite text can vary slightly between renders) so the cache is invalidated when the doc's cards change; this makes reopening instant and free. `loadCred`/`saveCred` read and write the cache, and a **Re-score** button forces a fresh pass. The panel lists each card with a colored score chip and a chevron affordance; clicking a card expands its four sub-score bars, reason, and press line. Over/under-highlighted cards (from `computeHighlightWarnings`, see Outline) also surface a dismissible highlight warning with the exact percentage in the expanded view. A **Go to card in document** button scrolls the doc to that card and flashes it.

Each question renders as a pill with:
- A **Show answer** disclosure that reveals the model answer — hidden by default. The answer is the likely **opponent response only**, written in the opponent's voice. The strategic follow-up is a separate `press` field, rendered under the answer in its own labeled **Press next** box so coaching advice never reads as part of the opponent's answer. `press` is optional (questions saved before the split have it folded into `answer`; they re-split on regeneration).
- A **3 more like this** button that calls `ai:crossExQuestions` again with the question as a `basedOn` seed (scoped to that side), inserting three fresh questions inline below.

**Short-doc warning.** After extraction the panel checks word counts and warns if there's very little highlighted text (under ~120 words) or the doc is short overall (under ~400 words), explaining you'll get few/shallow questions.

**Harder questions (trap drill).** A second footer button opens an interactive trap drill. `ai:crossExTraps` (balanced tier) generates 3 traps — each a setup question that baits a wrong answer, with a gotcha follow-up, ideal answer, and lesson. The user types an answer; `ai:crossExGradeTrap` (lite / flash-lite tier, to keep per-answer grading cheap) returns a verdict (`avoided` / `fell` / `partial`) plus tailored feedback — confirming how they avoided the trap, or springing the gotcha and giving the fix.

The panel's **Generate / Regenerate** action and the **Harder** button live in the footer. Generation uses the `balanced` model tier. Grouped questions (including any "3 more like this" inserts) are persisted per-document in `localStorage` under `warroom-cx-questions-<path>`, so they survive closing/reopening the panel, reloading the doc, and app restarts — they are only cleared when the user regenerates. Traps are ephemeral (regenerated each time the drill opens).

### Doc Comments

Team (or private) comments anchored to a highlighted span of text in an open speech doc — Google-Docs style. Backed by `doc_comments` (`supabase/schema.sql`), reached through `window.warroom.docComments.*` (main.ts handlers, mirrored in `preload.ts` and typed in `types.ts`), following the exact same "everything goes through main.ts" pattern as chat/team files (`src/lib/supabase.ts`: no Supabase call is ever made from the renderer). Unlike message content and Team Files, comment bodies are **plaintext at rest** — same tier as `shared_notes`, not the E2E-encrypted tier — since this is a lower-sensitivity, easily-revoked annotation layer, not message history.

**Anchoring, not DOM ids.** `docx-preview` assigns no stable per-paragraph identity across renders, so a comment is anchored by `(anchor_para_index, anchor_occurrence)`: the index of its `<p>` within `containerRef.querySelectorAll('p')` at comment-creation time, and which (0-based) occurrence of the exact selected text (`anchor_text`) that paragraph's own text content that selection was. On load, `resolveCommentAnchor` tries that exact paragraph first (`nthIndexOf(text, anchor_text, anchor_occurrence)` → `rangeFromTextOffset`, which walks the paragraph's text nodes to convert a flat character offset into a real `Range` spanning however many inline elements — bold, italic, highlight spans — the selection crossed); if the paragraph no longer contains that many occurrences (the file was re-imported with different content), it falls back to searching every paragraph in the doc for the anchor text, so a drifted anchor lands on *a* real match rather than silently vanishing. The write side (`postComment`) computes `anchor_occurrence` as `countOccurrences` of the exact selected text within everything *before* the selection's start offset in its paragraph — this is the same value `resolveCommentAnchor` looks for, verified to round-trip correctly (including repeated phrases within one paragraph) via a standalone script during development, not just read-through.

**Card-anchored comments (`anchor_kind: 'card'`).** Hovering a card's tag paragraph (`[data-cred-id]`, set by `buildCards` on every doc load regardless of whether the Credibility panel is open) reveals a small margin comment icon — `openComposerFromCard` — so commenting on a whole card never requires manually selecting its text first. `anchor_text` stores the tag's own text (not a body excerpt); resolution matches by exact tag-text equality among the doc's current `<p>` elements (same identity `buildCards`/`hashCards` already use for score-cache continuity, since docx-preview assigns no stable id) and then spans the highlight from that tag through the last paragraph before the next heading via `cardRangeFromTagEl` — the identical "walk siblings until a heading" rule `buildCards`/`computeHighlightWarnings` use to define a card's extent, so the highlight covers precisely what Credibility would score. The hover affordance itself debounces its clear on `mouseout` by 200ms (`cardHoverTimeoutRef`) so the pointer can travel from the tag to the floating icon without it disappearing first — the same gap problem the ⋯ overflow menu solves the same way. `pendingComment` is a discriminated union (`{kind:'text', range, ...} | {kind:'card', tagEl, ...}`); `postComment` branches on `.kind` to compute the right anchor fields.

**Reply threads.** A reply is just another `doc_comments` row with `parent_id` set to its thread's root — no separate table. `postReply` copies the root's `anchor_kind`/`anchor_text`/`anchor_para_index`/`anchor_occurrence` onto the reply (a reply has no independent anchor of its own); `scrollToComment` resolves a reply's id back to its `parent_id` before looking it up in `commentRangesRef`, so clicking anywhere in a thread jumps to the one highlighted span the whole thread shares — same as Google Docs. `CommentThread` renders the root, a collapsed "N replies" toggle (`expanded` local state, closed by default), and an inline `MentionableTextarea` reply composer. Deleting a root comment cascades to its replies via `parent_id ... on delete cascade` in the schema; the optimistic local delete in `deleteComment` filters out matching replies client-side too (`c.id !== id && c.parent_id !== id`) so the UI doesn't wait on the round-trip to catch up.

**Resolve / reopen.** Any team member can resolve a thread, not just its author — real teams comment-review each other's docs, and gating resolution to the original poster would make it a one-person feature. Since RLS's `update_own_doc_comments` policy is author-only, this goes through a `security definer` RPC instead of a plain row update: `resolve_doc_comment(p_comment_id, p_resolved, p_resolved_by_name)` (`supabase/schema.sql`, same pattern as `join_team_by_code`/`is_team_member`) checks `is_team_member` on the comment's team rather than `user_id = auth.uid()`, then sets `resolved`/`resolved_at`/`resolved_by_name`. `resolveComment` in `SpeechDocViewer.tsx` updates local state optimistically before awaiting `window.warroom.docComments.resolve(...)`. Resolved root comments render at 65% opacity in the panel and drop out of the highlight registry (the anchor-resolution effect only paints `!c.parent_id && !c.resolved` comments) but keep a resolved `Range` in `commentRangesRef` so clicking a resolved comment still scrolls to it. The panel splits into an always-visible open list and a collapsed "N resolved" disclosure (closed by default) rather than mixing resolved threads into the main list, mirroring Google Docs' own resolved-comment behavior.

**@Mentions.** `MentionableTextarea` (shared by the new-comment composer and every reply box) wraps `MentionPicker` with `types={['member']}` — a comment isn't the place to attach a case or flow, just to loop in a teammate — using the exact same `@(\w*)$` trigger-match-and-replace convention `Chat.tsx`'s composer already established (`@${item.name.replace(/\s/g,'_')} `). There's no separate mention storage or notification: `renderCommentBody` re-parses `body` at render time, splitting on `@\w+` tokens and bolding/coloring (`#4285F4`) any that match a live team member's display name (underscores converted back to spaces) — the same "no backing store, plain text convention" chat mentions already use, just with a visual chip on the display side that chat doesn't have.

**Highlight.** Resolved ranges are painted via the CSS Custom Highlight API on their own registry name (`wr-comment`), same mechanism as in-doc find (`FIND_HL`) — paints without mutating the DOM, so it composes cleanly with focus mode, the outline, and dark-mode fixes. Color is a light `rgba(147,51,234,0.14)` purple, deliberately outside the cyan/yellow/green space real evidence highlighting uses in the source `.docx` (see `DEBATE_DOC_STRUCTURE.md`), so a comment's highlight never reads as the document's own emphasis.

**Add flow.** The existing selection word-count bubble (`selBubble`) now also clones the live `Range` (`r.cloneRange()` — the native Range mutates/collapses as the selection changes, so the composer needs a snapshot). Two paths open the composer against that same selection: clicking the small comment-bubble button that renders beside the word-count pill (`openComposerFromSelection`), or pressing `⌘⌥M` / `Ctrl+Alt+M` — Google Docs' own "insert comment" binding, `doc-insert-comment` in `shortcutPrefs.ts`. The shortcut is a no-op without a live, non-collapsed `selBubble` (same requirement as the button) and without a signed-in `currentTeam`; it also force-shows comments first if they were hidden, so the composer never opens invisibly. Either path opens a floating composer (quote preview, textarea, a **Team** / **Only me** segmented toggle defaulting **Team**, Cancel/Post — `⌘Enter` posts, `Esc` cancels) anchored near the selection.

**One button, one combined state.** `commentsVisible` (`localStorage['warroom-doc-comments-visible']`, default on) is the single source of truth — it gates the highlight registry, the thread-list panel, and whether the composer can be open, all together; there's no separate "open the panel" vs "show highlights" split anymore. A single icon-only **Comments** `IconBtn` (no `ai-glow-ring` — commenting never calls a model) toggles it; toggling off cancels any open composer too. It's a plain toolbar button, not part of the `ToolbarPill`/`ToolbarOverflowMenu` group Credibility and Cross-Ex use, so it never folds into the ⋯ menu and never picks up the ring `ToolbarPill` applies unconditionally to its children (that ring was a bug from reusing `ToolbarPill` for a non-AI action — fixed by moving Comments off it entirely). Clicking a comment row in the panel calls `scrollToComment`, which scrolls its anchored range into view and briefly flashes its background (`rgba(147,51,234,0.35)`, same flash pattern as `scrollToCard`) so the jump is easy to spot.

**Realtime — one subscription owned by the wrapper, not each pane.** Up to 3 `DocPaneViewer` instances can be mounted at once, but `main.ts` keeps only a single active Supabase channel per `docComments:subscribe` call (same constraint `chat:subscribeTeamFiles` already has) — if each pane subscribed independently, whichever unmounted first would call `unsubscribe` and kill live updates for every other still-open pane. `SpeechDocViewer`'s default export (the always-exists-exactly-once wrapper) is the sole subscriber, keyed on `currentTeam.id`; it re-broadcasts every Postgres change as a `warroom-doc-comment-change` window `CustomEvent`, and each pane's own effect listens for that and filters to `row.doc_key === filePath` (`filePath` doubles as `doc_key` — it's already either the real path or the synthetic `oc:<url>` key `loadOcCase` uses).

## Impact Calc

Impact Calc is a full-screen hub for everything impact-weighing. Open it from the **Impact Calc** card on the home screen. It has two areas: **Practice** (the Outweigh game) and **Tools** (the doc-comparison analyzer and the Impact Library; Head-to-head Matchups is still coming soon).

### The Outweigh game
A practice drill where you spar with Warroom AI over impact calculus. It follows the app's active event setting:
- **Policy** — Aff/Neg terminology, impacts tied to the plan/counterplan action.
- **Public Forum** — Pro/Con terminology, no plan/counterplan; weighing is framed the way it actually reads in Summary/Final Focus (accessible register, avoids policy jargon like "solvency" or "the DA").
- LD currently falls back to the Policy framing (not built out separately yet).

A badge in the game header shows which event is active. Pick a difficulty:
- **Novice** — concrete, intuitive impacts (recession, an outbreak, a regional conflict); no theory.
- **JV** — classic impacts (nuclear war, bioweapons, hegemony); engage scope, probability chains, timeframe, reversibility.
- **Varsity** — extinction/existential matchups and framework wars; you must win the metric before the calc resolves.

Then choose how to start:
- **Surprise me** — Warroom AI invents a topic and takes a side against you.
- **Pick my own topic** — optionally attach one of your imported cases or speech docs for your side and/or the opponent's, say which side you want to argue, and add any notes. The generated scenario is grounded in that material instead of an unrelated invented one. No docs yet? Drag a `.docx` onto the app, or use the **Import doc** quick action on the home screen — or just skip docs and use the side/notes fields.
- **Use current topic** — pulls the current resolution for the active event straight from the Topics feature (`topics:getStored`) and grounds the scenario in it. If no current topic has been fetched yet for that event, it tells you to open Topics first instead of silently falling back to an invented one.

The round runs in three beats:
1. **Your impact** — Warroom AI presents its impact (claim, warrant, and ratings on the four dimensions). You write your own impact and a short calc explaining why yours outweighs.
2. **AI rebuttal** — Warroom AI delivers a tight 1–2 minute rebuttal speech, defending its impact and attacking yours on a specific dimension. You get a final shot (the last word) with a 60-second pressure timer that never blocks you — once it hits zero it counts overtime instead, and the result screen flags if you went over.
3. **Decision** — a judge calls the round: who won, a 1–10 score on your calc work, a written verdict, dimension-by-dimension feedback, and concrete tips. It also independently grades the opponent's rebuttal (its own 1–10 score + a short critique).

The judge call (`ai:outweighJudge`) is a fully separate, stateless request from the one that wrote the rebuttal (`ai:outweighRebuttal`) — it's never told it authored that speech, so grading the opponent's rebuttal can't be biased by the model recognizing its own writing.

The game is powered by `ai:outweighScenario`, `ai:outweighRebuttal`, and `ai:outweighJudge` in the main process. Prompt templates: `electron/prompts/outweigh_scenario.txt`, `electron/prompts/outweigh_rebuttal.txt`, `electron/prompts/outweigh_judge.txt`.

### Compare two docs (Tools)
The original analyzer compares two of your own cases, speech docs, or a flow:
1. Pick **Your doc** and **Their doc** (a case, an imported speech doc, or a flow — only one flow per comparison).
2. Click **Analyze Impact Calc**. Warroom AI extracts every impact claim from both, finds the direct clashes, and weighs them across all four dimensions.

Reading the results:
- **Clashes** — each row matches one of your impacts against the opponent impact it directly competes with.
- **Dimension winners** — for each clash, a winner is called on magnitude, probability, timeframe, and reversibility.
- **Overall verdict** — a summary declaring which side wins the exchange and why, suitable for a final rebuttal.

Saved comparisons are listed for one-click reopening. The comparison tool is powered by `ai:compareImpactsText` (prompt template: `electron/prompts/compare_impacts_text.txt`; the older docx-upload variant `gemini:compareImpacts` uses `electron/prompts/compare_impacts_docs.txt`). Everything in Impact Calc runs on the best model tier (your selected model, never Flash Lite).

### Impact Library (Tools)
A **shared, community-built** database of impacts. Unlike the rest of the app it is **not team-scoped** — every signed-in user reads and contributes to the same global pool. It lives in Supabase and uses the user's **chat account**, so they sign in through the chat panel to browse or contribute (the screen shows a sign-in prompt otherwise). Each entry is an AI-structured impact: the four dimensions broken out separately (each with a one-line warrant), a set of standard **answers** (how to beat it), and search tags.

**Contributing** is a three-step wizard:
1. **Source** — pick one of the user's cases/speech docs and/or paste a card or describe the impact, choose the event, hit **Draft with AI**.
2. **Edit draft** — the AI returns a structured impact (title, claim, four dimensions each with rating + note, answers, tags); the user corrects anything wrong.
3. **Review & submit** — the AI re-runs on the *edited* version to (a) regenerate answers/tags, (b) drift-check the edit against the source and flag unsupported claims, and (c) flag likely duplicates already in the library. The user picks attribution — **anonymous by default**, or opt in to credit by chat display name — then submits.

**Browsing**: search (title/claim/tags/answers), event filter, and sort by **Top** (net likes), **Newest**, **Saved** (personal bookmarks), or **Mine**. Each entry has **like**, **dislike**, and **save** buttons; likes/dislikes take an optional quick reason tag (dislike reasons include "AI error"). Users can delete their own entries.

Powered by `ai:impactLibraryDraft` (prompt template: `electron/prompts/impact_library_draft.txt`) and `ai:impactLibraryReview` (prompt template: `electron/prompts/impact_library_review.txt`) plus the `impactlib:*` Supabase handlers (`impactlib:list` / `submit` / `update` / `delete` / `vote` / `save`). Tables: `impact_library`, `impact_library_votes`, `impact_library_saves` — **re-run `supabase/schema.sql`** to create them. Like/dislike counts are denormalized on `impact_library` and kept in sync by a trigger on the votes table.

## LM Studio (local provider)

A fifth AI provider alongside Gemini/OpenAI/Anthropic/Grok, selectable in Settings → AI API key → **LM Studio**. LM Studio (lmstudio.ai) runs models on the user's own machine and serves an OpenAI-compatible REST API on localhost with **no authentication**, which makes it structurally different from every hosted provider:

- **No API key.** Nothing in `secure_*.json`; `getProviderForTask` returns the sentinel string `'local'` as `apiKey` purely so the existing `if (!apiKey) throw 'NO_KEY'` guard stays meaningful for hosted providers without every call site special-casing local mode. On the renderer side `providerIsConfigured()` (`GeminiPanel.tsx`) returns `true` unconditionally for `lmstudio`, so the "No API key set" banner never fires.
- **No cost tiers of its own**, but `taskTier` isn't fully ignored: `getProviderForTask` passes it into `lmstudioConfig(tier)`, which checks `app_settings.lmstudioPerCallModels[tier]` (a `{ lite, balanced, best }` object, editable under Settings → LM Studio → Advanced) and uses that model id instead of `lmstudioModel` if set for that tier. `'user'` tier maps to no override. `MODEL_TIER_IDS` still has no `lmstudio` entry — this is a flat per-tier override, not the hosted-provider tier system.
  - **Tier fallback chain** (`TIER_FALLBACK_CHAIN` in `electron/lmstudio.ts`): a tier with no override of its own borrows the next tier down in quality — `best` tries `balanced` then `lite`; `balanced` tries `lite`. `lite` is the exception (nothing below it) and borrows `balanced` instead. If the whole chain is empty, `resolveLmStudioConfig` falls back to `lmstudioModel`/`LMSTUDIO_DEFAULT_MODEL`, same as having no `lmstudioPerCallModels` at all.
  - What actually calls each tier (grep `callAI(prompt, '` in `main.ts` to re-verify if this drifts): `lite` → `ai:summarizeFlowSheet`, `ai:crossExGradeTrap`, `chat:generateGeminiTitle`. `balanced` → `chat:geminiAgentTurn` (main AI chat), `ai:autoFlowClassify`/`autoFlowSummarize`, `ai:extractCards`, `ai:analyzeRound`, `ai:teamSummary`, `ai:crossExQuestions`/`crossExTraps`, `ai:scoreCards`. `best` → `ai:cutterEmphasize`, `gemini:compareImpacts`, `ai:compareImpactsText`, `ai:outweighScenario`/`outweighRebuttal`/`outweighJudge`, `ai:impactLibraryDraft`/`impactLibraryReview`, `gemini:importFlow`. `'user'` (no override slot) → `ai:suggestBlocks`, `ai:missionBrief`.
- **The model id is user-owned free text.** It depends on how the user downloaded the model, so Settings offers presets (Gemma 4 12B QAT / **Gemma 4 12B**, the default / Gemma 4 E4B) as *shortcuts only*, plus a free-text field and a "Loaded models" button that lists what the running server actually reports.
- **Local failure modes.** Never quota or auth — instead "server isn't running", "model isn't loaded", "too slow for this machine".

### Code layout

Pure logic lives in `electron/lmstudio.ts` (not inline in `main.ts`) so it's testable without Electron — same split as `docxFlowCards.ts`. Exercised by `scripts/test-lmstudio.ts` (`npm run test:lmstudio`), which covers URL normalisation, config resolution, body building, error mapping, and response parsing, then runs the real request bodies against a mock OpenAI-compatible server on a throwaway port.

| Export | Purpose |
|---|---|
| `normalizeLmStudioUrl` | Accepts a URL with or without `/v1` and normalises to the `/v1` root, so `http://localhost:1234` and `http://localhost:1234/v1/` both work. |
| `resolveLmStudioConfig(settings, tier?)` | Pure resolution from an `app_settings` object → `{ baseUrl, model, options, sendTools }`. Optional `tier` ('lite'\|'balanced'\|'best') applies `settings.lmstudioPerCallModels[tier]` over `lmstudioModel` when set. |
| `buildLmStudioChatBody(cfg, args)` | Chat-completions body. User `options` are spread **last** so they override Warroom's defaults — that's the point of the options box. `stream: false` is pinned. |
| `lmstudioHttpError` | Provider's exact text (per the "AI call retries" rule), falling back to Warroom copy only when the body isn't parseable. |
| `lmstudioConnError` | Distinguishes unreachable (→ "open the Developer tab and click Start Server") from `AbortError` (→ timed out, try a smaller model). |
| `looksLikeToolUnsupported` | Narrow test for "this model can't do tool calling" — see below. |
| `parseLmStudioModels` / `readLmStudioText` / `readLmStudioToolCalls` | Response parsing. |

`app_settings` keys: `lmstudioBaseUrl` (default `http://localhost:1234/v1`), `lmstudioModel` (default `google/gemma-4-12b`), `lmstudioOptions` (JSON **string**, as typed), `lmstudioTools` (bool, default `true`), `lmstudioPerCallModels` (object, `{ lite?, balanced?, best? }` — parsed from Settings' own JSON textarea before write, same tolerate-malformed-input handling as `lmstudioOptions`).

A malformed `lmstudioOptions` blob is **ignored, not fatal** — the user types into that box freely and a half-finished `{"temp` must never be why an AI call fails. Settings shows the JSON error inline instead.

### Tool-calling fallback

**Tool calling normally just works.** Gemma 4 has native structured tool-use support, and — importantly — for models *without* a tool-capable chat template LM Studio does **not** error: it substitutes its own system prompt and a standardised tool-call format, converting `tool`-role messages to `user` role for templates that lack the role ([LM Studio docs](https://lmstudio.ai/docs/developer/openai-compat/tools)). So the `tools` field is safe to send to any loaded model.

The `lmstudio` branch of `chat:geminiAgentTurn` still keeps a defensive fallback: on a 400/500 whose body matches `looksLikeToolUnsupported`, it retries once **without** tools so the chat degrades to a plain conversation instead of failing outright. Given LM Studio's own fallback this should rarely fire — it exists for third-party OpenAI-compatible servers pointed at the same setting, and for LM Studio versions/models that reject the field. The match is deliberately narrow so a genuine 400 about something else surfaces as itself rather than being retried into a confusing second error. The `lmstudioTools` toggle skips sending tools at all.

### Timeout

`LMSTUDIO_TIMEOUT_MS = 600_000` (10 min) rather than the hosted providers' 45s: local inference is far slower, and a 12B model on consumer hardware can genuinely spend minutes on a long completion. A hosted call hanging that long means something is broken; a local one is just working.

### IPC

| Channel | Purpose |
|---|---|
| `lmstudio:listModels(baseUrl?)` | `GET {baseUrl}/models` → id list. `baseUrl` lets Settings probe a URL the user typed but hasn't saved. |
| `lmstudio:test` | Saves, then round-trips a one-token prompt through the configured model, returning the model id the server actually served, its reply, and elapsed ms. |

Both are exposed as `window.warroom.lmstudio.*` in their own preload namespace — deliberately **not** under `api.ai`, whose wrapper loop turns every method into a retry-and-toast call. That's wrong for a button the user just clicked and is watching: a failure should come straight back, not stall for 8/30/60s.

### Renderer error copy

`humanizeGeminiError` (`src/utils/geminiError.ts`) branches early for `lmstudio` — the hosted advice about quotas, API keys, and internet connectivity is all wrong for a local server, so it maps to local guidance instead (start the server / load the model / try a smaller model / raise the context length).

## Warroom Agent (AI)

Warroom AI is an agentic AI assistant that lives in a resizable right-side panel (`GeminiPanel`). It supports multi-turn conversation and tool calls. Its system prompt is built in `chat:geminiAgentTurn` from `renderPrompt('agent_system', {})` plus (on the first turn of a session) `renderPrompt('agent_title_suffix', {})` appended, plus a topic-context prefix and a custom-skills suffix. Prompt templates: `electron/prompts/agent_system.txt`, `electron/prompts/agent_title_suffix.txt`.

### Model selection
- **Gemini 2.5 Flash Lite** — cheapest, fastest; auto-enables token saving
- **Gemini 2.5 Flash** — default; best balance of cost and quality
- **Gemini 3.5 Flash** — highest quality; best for complex analysis

Agentic tasks (tool calls, sub-agent searches) always use Gemini 2.5 Flash regardless of the model selection above.

### @mentions / attachments
Type `@` in the chat input to attach context from your local data:
- `@case` — attach a full case
- `@block` — attach a block's cards
- `@flow` — attach a flow spreadsheet
- `@opponent` — attach opponent profile / disclosures
- `@member` — mention a team member
- `@image` — paste an image from clipboard
- `@speechdoc` — attach a speech doc

### Token saving
When attaching a speech doc, "token saving" mode sends only underlined text, citations, and headings (not small body text) to reduce token usage. Auto-enabled for Flash Lite. Can be toggled globally in Settings or per-conversation.

### Quote-reply
Hovering any message (yours or Warroom AI's) reveals a Reply button next to Edit/Copy/Retry. Clicking it stores a `{ id, role, text }` snapshot in `replyingTo` state and shows a quote bar above the composer; sending attaches that snapshot to the new message as `GeminiMsg.replyTo` and injects a one-off `[The user is replying to ...]` context line into that turn's `userParts` (not into `m.text`, so the displayed message and later turns stay clean). Editing or retrying a message that has `replyTo` restores it into `replyingTo` so the requote isn't lost. Clicking a quoted snippet scrolls to and briefly highlights the original message via its `id="msg-<id>"` element, if still in the loaded history.

### Agent tool calls
Warroom AI can call the following tools during a conversation:
- `get_skill(skill_name)` — loads a skill .md file (cx_debate, pf_debate, ld_debate, card_cutting, user_manual, documentation, or user-added custom skills)
- `search_logos` — searches the Logos debate evidence database via a hidden webview in `AgentSearchViews`
- `search_openevidence` — searches the Open Evidence Project via a second hidden webview in `AgentSearchViews`
- `save_card_to_library` — saves a card with full verbatim body text to the `__agent_inbox__` block inside the `__agent__` case ("Agent Saves")
- `fetch_article` — fetches and extracts text content from a URL (for cutting cards from web sources)
- `search_warroom` — searches the user's saved Warroom data: cases (with extracted content keywords), opponents (disclosure titles, aff/neg names), judges (paradigm), tournaments, speech docs, and current topics. Use when the user asks to find something in their prep files. Returns ranked results grouped by type.
- `search_tabroom_tournament` — searches Tabroom for tournaments by name
- `get_tournament_details` — fetches full info for a Tabroom tournament by numeric ID
- `save_tournament_to_app` — saves a Tabroom tournament to the user's tournament list
- `search_judge` — looks up a judge on Tabroom by name and returns their paradigm. Caches the paradigm to the judge record (creating one if needed), so a repeat lookup of the same judge is instant unless `refresh` is passed.
- `scout_opponent` — pulls an opponent's disclosed rounds/cites from OpenCaselist (if linked) and runs the same AI scouting pipeline as the opponent profile's "AI Scout" card, returning an AFF/NEG summary with citations. Caches to `disclosures.aiScout` so a repeat ask is instant unless `refresh` is passed.
- `write_skill` — creates/updates a custom skill .md file in the user's skills folder. **Gated on explicit user approval**: the renderer shows a card above the composer with the skill name and full content and blocks the tool loop until the user answers (`pendingSkill` / `resolvePendingSkill` in `GeminiPanel.tsx`, step status `awaiting`). It is the only approval-gated tool, because a written skill is re-read into the system prompt of every later session (`buildCustomSkillsSuffix`) while `fetch_article` / `search_logos` / `search_openevidence` pull attacker-controllable web text into the current one — without the gate, a fetched page could induce a persistent prompt injection. Declining returns a functionResult instructing the model not to retry; cancelling the step or unmounting resolves as a decline so the loop can't wedge. The MCP server intentionally has no write_skill equivalent (read-only `get_skill`), so this gate can't be sidestepped through it.
- `navigate_app` — opens any view for the user (top-level views, or a case/block/opponent/tournament/flow resolved by name)
- `list_flows` / `read_flow` — list flow sheets and read a flow's columns + filled cells
- `edit_flow_cell` — writes a single cell in a flow sheet (by flow name, column header, 1-based row). Writes to `flow_data_<id>` storage and dispatches a `warroom-flow-updated` event so an open FlowView reloads live.
- `rename_chat` — renames the current chat's title. Off by default (Settings → "Let Warroom AI rename chats") — filtered out of the tools array server-side in `chat:geminiAgentTurn` when the setting is off, so the model is never even offered it. Prompt guidance is conservative: only on a genuine topic shift, never on the first exchange. Blocked once the user manually renames the chat (`titleSetByUser` flag on the conversation).

The agent runs 3–5 searches per evidence request in parallel. Saved cards always use the complete verbatim card body — never a summary. The save handler validates the body is non-empty before writing to the DB.

Click any completed tool-call step to expand a transparency panel showing the exact args sent and result returned.

### Streaming
Text responses stream token-by-token across every provider (Gemini, OpenAI, Anthropic, Grok, LM Studio). `chat:geminiAgentTurn` in `electron/main.ts` parses each provider's own SSE format and forwards deltas to the renderer over a `chat:agentStreamChunk` event scoped by a per-turn `requestId`, while still accumulating the full response server-side for tool-call detection and title extraction. Gemini has a known API quirk, `MALFORMED_FUNCTION_CALL`, where streamed tool-calling occasionally breaks down mid-response — when that happens the handler transparently retries that turn once on the non-streaming endpoint before giving up.

### Chat sessions
Each conversation has an auto-generated title (generated after the first exchange). Sessions are stored locally. The active session ID is tracked in Zustand as `geminiActiveId`. Click a chat's title in the panel header to rename it manually — sets `titleSetByUser`, permanently locking the title against the auto-title and `rename_chat` alike.

### Retry on transient failures
Every AI provider call (Gemini, OpenAI, Anthropic, Grok — both single-turn helper calls and the multi-turn agent tool-calling loop) goes through `fetchWithRetry` in `electron/main.ts`. It retries HTTP 429/500/502/503/504/529 and network-level errors (dropped connection, timeout) up to twice with exponential backoff + jitter, honoring a `Retry-After` header when the provider sends one. It does **not** retry 400/401/403 — a bad API key or malformed request won't succeed on a second try. For the agent loop specifically, `fetchWithRetry`'s `timeoutMs` option gives each retry attempt a fresh 45s `AbortController` rather than reusing one that already fired.

## Team Chat

Team chat uses Supabase for real-time messaging. It appears in a resizable panel on the right side (separate from the Warroom AI panel). Features:
- Team creation with invite codes; members can join/leave; owner can kick members
- Channel messages and direct messages (DMs) between team members, plus group DMs
- Message editing and deletion
- Quote-reply: hovering any message reveals a Reply button. It captures a snapshot (sender name + content) and stores it on the new message as `reply_to_id` / `reply_to_sender_name` / `reply_to_content` (the content snapshot is encrypted the same way as `content` — see Encrypted chat below). Because it's a snapshot rather than a live join, the quote survives the original message being edited or deleted. Clicking the quoted block scrolls to the original message via `id="msg-<id>"` if it's still loaded.
- Attachments: cases, blocks, flows, opponents, images, speech docs — shared with edit or view permissions. Clicking received attachments expands a content preview; "+" button imports to your library.
- Round references in messages (link to a specific round)
- Unread count badge on the chat icon in the sidebar
- User lookup by email via `lookupUserByEmail`

### Auth
Chat uses Supabase auth (email + password). Credentials are stored encrypted on device via `safeStorage`. Sign-in state is cached in `localStorage`.

### Chat width
The chat panel is resizable (260–600 px, default 320 px). Width is persisted in `localStorage` as `warroom-chat-width`.

### Composer: send/dictate button, optimistic send, autogrow
`SendDictateButton.tsx` is one icon-only button shared by team chat, DMs, and Warroom AI: a dictation mic when the box is empty, swapping to a send icon once there's content. `variant="solid"` (chat) uses `var(--item-selected-bg)`; `variant="gradient"` (Warroom AI) uses the same blue→pink gradient as `.ai-glow-ring` plus a small spark badge. `useAutoGrowTextarea.ts` grows the composer up to 1/3 of the chat panel's own height (measured via a `panelRef` on the root container, not the window), then scrolls internally.

Sending is optimistic: `sendMessage()`/`send()` push a client-generated `tmp-*` id into the message list and clear the composer before the network call resolves. On success the placeholder is dropped and the authoritative row arrives via the same realtime subscription that delivers other members' messages (it fires for the sender's own inserts too). On failure the placeholder is removed and the composer text/attachments/reply are restored, with the real error shown inline.

### Dictation
`src/utils/dictation.ts`'s `transcribeRecording(blob, mimeType)` is the one shared entry point — all three composers (Warroom AI, team chat, DMs) call it instead of duplicating the record/encode/invoke logic they used to each carry separately. It reads `app_settings.dictationUseOffline` to pick a path, then calls `window.warroom.dictation.transcribe`, which fans out in `electron/main.ts`'s `dictation:transcribe` handler:

- **Gemini** (`apiProvider === 'gemini'`): the recorded blob (webm/opus) is sent inline as base64 to `generateContent`, same as before this was ever routed by provider.
- **OpenAI** (`apiProvider === 'openai'`): `callOpenAIWhisper()` uploads the blob as a file to `/v1/audio/transcriptions` (`model: 'whisper-1'`) — this is a multipart/form-data POST, not JSON, since that's what the endpoint requires; the only such call site in the file.
- **Anthropic/Grok**: neither has a transcription API, cloud or otherwise. The handler returns a clear error naming Gemini/OpenAI and the offline option, instead of a confusing "no Gemini key" message when the user deliberately picked a provider that was never going to support this.
- **Offline (Beta)**: `electron/offlineWhisper.ts` runs a small local Whisper model (`Xenova/whisper-tiny.en`) via `@huggingface/transformers`, entirely on-device — no key, no network, independent of `apiProvider`. Settings → General → "Offline dictation model" downloads it (~75MB, cached under `<userData>/warroom/offline-models`, tracked ready via `app_settings.dictationOfflineModelReady` rather than probing the filesystem) and toggles `dictationUseOffline`. Marked Beta everywhere it's surfaced: CPU inference is slower and less accurate than a hosted model.
  - **Uninstall**: the "Uninstall" link next to the ready-state message calls `dictation:removeOfflineModel`, which deletes the cache directory (`fs.rm(cacheDir, { recursive: true, force: true })`) and clears the in-memory pipeline singleton (`removeOfflineWhisperModel()` in `offlineWhisper.ts` — resetting `transcriberPromise` matters within a single running session, since otherwise a download→uninstall→re-download cycle would hand back a pipeline still pointed at deleted files). Also flips both `dictationOfflineModelReady` and `dictationUseOffline` back to `false` — leaving the toggle on would mean the next dictation attempt (or the next silent cloud-failure fallback) tries to run inference against files that no longer exist.
  - **Download progress**: the model is several separate files (weights, tokenizer, config), and `@huggingface/transformers`' `progress_callback` reports each file's own 0-100% independently — shown naively, the visible number resets to 0 every time a new file starts. `makeProgressAggregator()` in `offlineWhisper.ts` instead tracks `{loaded, total}` per file as events arrive and emits one running percentage across every file's summed bytes (`WhisperProgress.overallPct`), plus a plain-language `label` for whichever file is currently active (`friendlyFileLabel()` maps substrings like `.onnx`/`tokenizer`/`config` to "model weights"/"tokenizer"/"model config" rather than showing the raw filename). Settings shows both: the button text ("Downloading model weights… 42%") and a thin progress bar underneath — indeterminate (`wr-indeterminate` CSS animation) until the first file reports a real total, since `overallPct` is `undefined` before that.

**Silent fallback**: `transcribeRecording()` in `dictation.ts` tries the cloud path first whenever `dictationUseOffline` is off — that's the common case, unchanged cost. If that call fails for any reason (bad key, rate limit, network error, malformed response) *and* `dictationOfflineModelReady` is true, it retries once through `transcribeOfflineFallback()`, which does the PCM decode only at that point (not on every call, since cloud succeeds the overwhelming majority of the time). Never triggers a download on its own — if the model isn't there yet, dictation just fails the way it always did pre-fallback. No UI signal either way; this is intentionally invisible to the user, same as every other dictation failure being swallowed silently.

**Why the renderer decodes audio, not the main process**: the offline path needs 16kHz mono Float32 PCM, but MediaRecorder only produces compressed webm/opus, and the main process has no audio-codec decoder of its own. So `dictation.ts`'s `decodeToFloat32Mono16k()` uses the *renderer's* Web Audio API (`AudioContext.decodeAudioData` + an `OfflineAudioContext` sized to 16kHz/1 channel for the resample-and-downmix in one pass) before the PCM ever crosses the IPC boundary — the main process just reinterprets the base64 bytes as a `Float32Array` directly (`new Float32Array(buffer.buffer, buffer.byteOffset, ...)`), no decoding of its own required.

**Packaging note**: `@huggingface/transformers` pulls in `onnxruntime-node` (a native `.node` addon) and `sharp` (also native). Both are marked `external` in `electron.vite.config.ts` (Rollup can't safely bundle a runtime `require()` of a platform-specific native binary — same class of issue as the existing `undici` external, just for a native addon instead of a Node builtin) and `onnxruntime-node` is `asarUnpack`'d in `electron-builder.yml` (native addons can't be `dlopen`'d from inside an asar archive).

### Avatars
`Avatar.tsx` is the shared identity icon for a team room, DM, or group DM, used in the all-chats list, Quick Chat, and the pin picker. Team room = rounded square, `var(--accent)` background, team initials. DM = circle, background from `paletteColorFor(userId)` (a small hash over a fixed 6-color palette chosen to read on every theme), person's initials. Group DM = circle split into a 2×2 grid, one initial per each of the first 4 members in `channel.members` order.

### Team Files
Team rooms (not DMs) have a per-team file library, `TeamFiles.tsx`, backed by the `team_files` table, kept separate from the message stream. Reached via a Chat/Files toggle bar under the room header by default, or a single Files icon in the header if Settings → Chat → "Team files display" is set to icon mode (`getFilesBarStyle()`/`setFilesBarStyle()` in `chatPrefs.ts`, localStorage key `warroom-files-bar-style`). A speech-doc attachment sent directly in a team-room chat message (not just via "+ Add file") auto-forwards into `team_files` too, reusing `teamFiles.upload` — see `forwardSpeechdocToTeamFiles()` in Chat.tsx, fired from `sendMessage()` after a successful send, skipped for oversized/summarized attachments.

Each row stores `name` and `data_b64` (the raw file bytes, base64) encrypted client-side with the team key exactly like message content; `uploader_name` stays plaintext, same tier as a message's sender name. The list shows file name, "Modified <relative time>", and uploader. Opening a file decrypts `data_b64`, writes it to a temp file via `fs.writeTempFile`, and opens it in the Speech Doc Viewer.

**Remove vs. delete**: the trash icon (uploader only) calls `chat:removeTeamFileContent`, which clears `data_b64` and sets `removed = true` but keeps the row — name, uploader, and dates stay visible as a record. This is distinct from `chat:deleteTeamFile` (a full row delete, RLS-scoped to the uploader), which the UI no longer calls but which still exists.

**Auto-update**: the uploader's own device watches the local file on disk with Node's `fs.watch` (`electron/main.ts`), debounced 1.2s to absorb multiple change events per save. On a debounced change, main.ts sends the raw (unencrypted, IPC-only — never over the network) bytes to the renderer via `chat:localTeamFileChanged`; encryption has to happen in the renderer because `chatCrypto.ts` uses the Web Crypto API. An effect in the top-level `Chat()` component (always mounted per `App.tsx`, so it runs even when the Files panel is closed) re-encrypts and calls `chat:updateTeamFileContent`, bumping `updated_at`. Every other team member is subscribed to Postgres changes on `team_files` (same realtime pattern as chat messages) and sees the row update live.

The fileId → local path mapping is persisted device-side only, in `team_file_watches.json` — it never syncs anywhere, since it's only meaningful on the machine that uploaded each file. Watches are restored from that file at every launch (`restoreTeamFileWatches`), so auto-update survives a restart without re-uploading. This means auto-update only works while the uploader's own Warroom app is running; teammates just see `updated_at` move and re-open the file for the latest version.

**"+ Add file" only sources from the app's own library** — a two-step picker ("From your speech docs" / "From your flows"), no raw OS file dialog. Speech docs use the mechanism above unchanged (a real path on disk, `fs.watch`). Flows have no file on disk, so they get a parallel, simpler mechanism: adding one calls `flowDataToXlsxBase64()` (`utils/flowImport.ts` — a pure serializer shared with `FlowView.tsx`'s own xlsx export, so the two can't drift) to build the initial upload, then registers a `fileId → flowId` watch in `team_file_flow_watches.json` (same shape/restore story as the docx map, different file) via `chat:watchFlowTeamFile`. There's no `fs.watch` for a flow — instead, `FlowView.tsx`'s `persist()` (its autosave) calls `pushToWatchedTeamFile()` after every save, debounced 1.5s: it asks main.ts (`chat:getWatchedFileIdForFlow`) whether this flow has a linked Team File, and if so, serializes + encrypts + calls `chat:updateTeamFileContent` directly from the renderer — no IPC round-trip to read bytes off disk needed, since the flow's data is already in memory where it saved. `chat:isWatchingTeamFile` checks both watch maps, so the 🔄 indicator works the same for either source.

### Oversized attachments (2MB cap) and AI summarization
`fileSizeGate.ts` defines `MAX_ATTACHMENT_BYTES` (2MB). The chat composer's speechdoc/flow mention-attach (Chat.tsx `handleMentionSelect`) and Team Files' speech-doc source (`TeamFiles.tsx` `addFromSpeechDoc`) measure the source before sending, and show `OversizedFilePopup.tsx` when it's over the cap. "Send name only" attaches/uploads a placeholder (`{ oversized: true, sizeBytes }` for chat, empty `data_b64` for Team Files) with no real content, permanently — there's no later "upgrade to full content" path. "Summarize with Warroom AI" calls the new `speechdoc:summarizeForAttachment` IPC handler with the already-extracted doc text (chat/Team Files both call `speechdoc:extract` client-side first, so the handler never re-parses the docx itself) and the `cx_debate` skill injected into the prompt, wrapped in `withDelayedRetry` per the AI-retry convention. The result is stored as `{ summarized: true, summary }` on a chat attachment, or in `team_files.summary_text` (a new nullable column, encrypted like `name`/`data_b64`) for a Team Files upload. Wherever the attachment is later opened — `ChatMessage.tsx`'s `AttachmentChip`, or `TeamFiles.tsx`'s row — it shows the summary (or a "too large, name only" notice) instead of trying to open real content that was never sent.

### Quick Chat
Off by default (`chatPrefs.ts`: `isQuickChatEnabled()`/`setQuickChatEnabled()`, localStorage `warroom-quick-chat-enabled`). Settings → Chat → "Quick chat" opens `QuickChatPicker.tsx`, which lets the user pin the team room and/or any DM/group DM (`warroom-quick-chat-pins`, a `QuickChatPin[]`) and optionally assign each pin a keyboard shortcut, stored separately in `warroom-quick-chat-bindings` (keyed by `quickchat-<pinId>`, reusing `shortcutPrefs.ts`'s `KeyBinding` shape but not its registry, since pins are dynamic/user-defined rather than a fixed app shortcut list). `findQuickChatConflict()` checks a candidate binding against every core app shortcut (`DEFAULT_BINDINGS`) and every other pin before allowing it — a clash surfaces a rebind-in-place prompt (see the CLAUDE.md rule "Keyboard shortcuts must not conflict"), resolvable fully inline when both sides are pins, or by opening the full Shortcuts overlay when the clash is with a core app shortcut. Pinned icons render in `TitleBar.tsx`'s `QuickChatBar`, just left of the main chat icon; clicking one (or firing its shortcut) sets `appStore`'s `pendingChatTarget`, which the always-mounted `Chat()` component consumes to jump to that room/DM.

### Pinned messages
A shared pin board per team room or per DM/group DM, backed by the `pinned_messages` table — exactly one of `team_id`/`dm_channel_id` is set. Pinning snapshots `sender_name`/`content` (encrypted client-side, same convention as a reply-to quote) so a pin survives the original message being edited or deleted; `message_id` is kept as a soft link purely for "Jump to message". Reached via a "Pins" tab — a 3-way Chat/Files/Pins bar in team rooms (or a Pins icon alongside Files in icon mode), and an always-shown 2-way Chat/Pins bar in DMs (DMs ignore the files-bar-style setting since they have no Files tab to make a tradeoff against). The pin/unpin toggle lives in each message's hover-action row (`PinIcon` in ChatMessage.tsx). Any team/DM member can unpin, not just whoever pinned it. Realtime subscriptions are keyed per scope in a `Map` (`pinsChannels` in main.ts) rather than one shared channel variable, since the message list (for the pin-icon highlight) and the Pins tab can both be subscribed at once.

### Per-chat desktop notifications
Each chat (team room = `'team'`, or a dm_channel_id) has an independent notification level — All messages / Mentions & replies only / Nothing — set in Room/DM Settings (`NotifLevelPicker.tsx`) and stored in localStorage (`warroom-chat-notif-levels`, `chatPrefs.ts`). Team-room notifications fire from `ChatBody`'s existing always-mounted subscription (the background instance that also drives the unread badge). DMs need a separate `chat:subscribeAllDMs` IPC subscription (no column filter — RLS still scopes it to the user's own channels) since the per-open-DM subscription only exists while that DM is actually open. "Mentions & replies" is decided by `messageMentionsOrReplies()`: the decrypted content contains `@Display_Name`, or the message directly replies to one the user sent (checked via `reply_to_sender_name`, not a full thread trace). The renderer decides whether to notify (it's the only side with the decrypted content) and calls `chat:showNotification` just to display it — deliberately separate from the daemon's category-toggle system (pairings/results/etc.).

### Presence: online status and typing
One Supabase presence channel per team (`presence-<teamId>`) covers both online status for every member and typing state for the team room and every DM — each client tracks `{ userId, displayName, typing }`, where `typing` is a scope key (`'team'` or a dm_channel_id) or `null`. No message content ever crosses this channel. Deliberately lighter weight than the live-flow channel's private+RLS setup — presence here only reveals "so-and-so is online/typing", so an unauthenticated but team-scoped channel name is a proportionate tradeoff. `useTypingTracker(scopeKey)` (Chat.tsx) re-tracks on each composer keystroke and clears itself after 2.5s idle. Raw presence state lives in `appStore`'s `presenceState` (not chat-local) so any component can read it via `chatPrefs.ts`'s `presenceList()`/`isUserOnline()`/`typingDisplayNamesFor()` without prop drilling. `ChatAvatar`'s optional `online` prop draws the status dot; currently wired up in the all-chats DM list (1:1 DMs only).

### Instant-open message cache
`chatCache.ts` keeps the last 50 decrypted messages for each of the last 5 chats the user opened (team room and/or DMs, LRU by `lastOpened`) in local userData JSON (`chat_cache_<chatId>` + a `chat_cache_index` of which chats are cached), via the existing generic `storage:read`/`storage:write` IPC. `loadMessages()` in both `ChatBody` and `DMBody` renders the cached list immediately (no "Loading messages…" flash for a recently-visited chat) while the real Supabase fetch runs in the background and then fully replaces it — the cache is a "show something now, reconcile shortly after" layer, never a source of truth, so a stale cached edit/delete self-heals within one fetch. The realtime message handlers also update the cache incrementally so a quick reopen has the very latest message too. Evicting a chat past the 5-chat cap clears its cache file. Stores plaintext (already-decrypted) content, same trust tier as every other local userData file.

**Highlight readability slider (⋯ menu).** Word's raw highlighter colors render at full saturation — green in particular (`#00ff00`-ish) is noticeably harsher against black text than yellow/cyan at the same technical luminance, since pure green sits at the peak of the human eye's contrast sensitivity (the luminance formula weights G at 0.587 vs. R/B's 0.299/0.114). `applyDarkModeViewerFixes` already handles this on a *dark* page (dims every bright highlight via `dimHighlightToHsl`), but a *light* page — the common case, and the default even in dark mode since "Keep speech docs light" defaults on — had nothing touching highlight color at all until this.

Rather than hardcode a fix, `docxViewerUtils.ts` exposes a 0–100 dial, `warroom-highlight-readability` (`loadHighlightReadability`/`saveHighlightReadability`, default 50, `HIGHLIGHT_READABILITY_CHANGED` window event): 0 renders Word's exact original colors, 100 fully mutes them toward per-color pastel targets (`HL_SOFT_TARGET`) — yellow/cyan/green all soften, each staying recognizably its own hue rather than converging on one generic look. **Detection has to happen before any softening does**: `tagHighlightElements` walks a freshly-rendered doc once, classifies each element's *computed* background against Word's three known raw colors (`classifyRawHighlight`), and stamps the match onto `data-hl-kind` — because once a highlight has been recolored even slightly, computed-style classification no longer recognizes it as "raw." Every later read — dragging the slider, toggling dark mode, focus mode, reading-time word counting, anything — goes through that tag instead via `isSpanHighlighted`/`applyHighlightReadability(container, pct)` (interpolates `HL_RAW → HL_SOFT_TARGET` by `pct/100`, cheap enough to call on every slider input) or `resetHighlightReadability(container)` (snaps straight back to `HL_RAW`), never by re-inspecting computed style.

That reset step matters for hand-off correctness: `applyDarkModeViewerFixes` computes its own dim from whatever color is currently on screen, so `resetHighlightReadability` must run *before* it whenever a page goes dark, or the dim would compute from an already-softened starting color. `SpeechDocViewer.tsx`'s live theme-sync effect does exactly that (reset-then-dim on the dark branch, `removeDarkModeViewerFixes`-then-`applyHighlightReadability` on the light branch, `highlightReadability` in its dependency array so a slider change re-syncs the open doc immediately); the per-doc-load render pipeline now calls `tagHighlightElements` unconditionally, before branching on dark/light, so the tag exists regardless of theme — focus mode and reading-time word counting both need it even on a dark page, where `applyHighlightReadability` itself never runs.

**UI**: `HighlightReadabilityMenu.tsx` exports both the standalone "⋯" trigger (default export — its own open state, its own localStorage read/write, dispatches the change event itself so multiple open panes stay in sync with zero prop wiring) and `HighlightReadabilitySlider` (named export — just the label/track/endpoints, no trigger or popover chrome of its own). Single-pane / non-compact toolbars render the standalone trigger; compact multi-pane toolbars fold `HighlightReadabilitySlider` into the pane's existing `ToolbarOverflowMenu` instead (via its new `extra?: React.ReactNode` prop, rendered after a divider) — two separate "⋯" buttons used to sit side by side once `toolbarCompact` was true, which is why this merge exists. Wired into every interactive docx-preview viewer that can show highlighted evidence: `SpeechDocViewer.tsx` and `GoogleDrivePanel.tsx`'s `WordViewer` (next to the file name, shown only when `isDocx(file)` — always applies there with no dark/light branch, since that viewer's page is hardcoded to a white background regardless of app theme). `CasePreview.tsx` also uses `renderAsync` but is a static, non-interactive grid-tile thumbnail with no toolbar of any kind — no viewer chrome to hang a menu on, so it's excluded. `CardBody.tsx`'s card-library rendering (`Library.tsx`/`BlockView.tsx`) uses the same raw palette via `cardFormat.ts` but is a different rendering path (formatted `CardRun[]`, not docx-preview passthrough) and wasn't in scope here.

## Storage & Security

### Local data
- `userData/warroom/db.json` — main database (cases, blocks, cards, opponents, tournaments, rounds)
- `userData/warroom/flows_index.json` — list of open flows with metadata
- `userData/warroom/app_settings.json` — debate event, Gemini model, token saving
- `userData/warroom/secure_*.json` — encrypted secrets (Gemini key, OC credentials, GDrive tokens, chat credentials)
- `userData/warroom/skills/` — user-added skill files (.md)

### Secure storage
Sensitive values (API keys, passwords, OAuth tokens) are encrypted with Electron's `safeStorage` (OS keychain-backed AES encryption). In dev mode, base64 fallback is used since the safeStorage key changes on each rebuild.

### Encrypted chat
All team-chat and DM content is encrypted client-side before it leaves the client. Message text and every shared attachment (cases, blocks, flows, opponents, tournaments, speech docs) are encrypted with AES-256-GCM; Supabase only ever stores ciphertext. Each team has one symmetric key, derived from the team's `key_seed` via PBKDF2 (200k iterations, SHA-256, salted with the team id) — implemented in `src/lib/chatCrypto.ts`. `key_seed` is a server-generated random value that every member receives, so everyone derives the identical key with no key-distribution handshake, and the derived key is never transmitted. It is deliberately **not** the invite code: the two have opposite lifetimes — an invite code gets pasted into group chats and must be revocable, while the KDF input can never change or all history becomes unreadable. Keeping them separate is what makes **Reset invite code** (Room settings, owner-only) possible without breaking decryption of existing messages. Teams created before this split were backfilled with `key_seed = ` their then-current invite code, which is why `teamKeyFor()` falls back to `invite_code` when `key_seed` is absent — that fallback reproduces the original key, never a wrong one. Encryption/decryption happen in `Chat.tsx` (load, realtime, send, edit for both rooms and DMs), `SharePanel.tsx` (share-to-room / share-to-DM), and `TeamFiles.tsx` (upload, auto-update, open). Ciphertext is tagged with a `wre1:` prefix so legacy plaintext rows decrypt transparently (anything without the prefix is passed through). Metadata — sender name, timestamps, attachment `name`/`type`, `team_files.uploader_name` — stays plaintext for display; only `content`, attachment `data`, the quote-reply snapshot field `reply_to_content`, and `team_files.name` / `team_files.data_b64` are encrypted (`reply_to_sender_name` stays plaintext, same tier as sender name). Warroom AI does not read team-chat history, so no plaintext chat is sent to the AI provider.

**This is NOT end-to-end / zero-knowledge encryption.** The key is derived from `teams.key_seed`, which is stored server-side and handed to every member. So it protects content if only the message/attachment rows leak (an over-broad RLS SELECT, or a partial dump excluding `teams`), but it does NOT protect against a full database compromise or a malicious operator, who can re-derive every team key from the stored seed. Treat it as defense-in-depth over RLS, not as a guarantee the operator can't read messages. The threat model is documented at the top of `src/lib/chatCrypto.ts`.

### Live-flow channel security
Collaborative "live" flows sync over a **private** Supabase Realtime broadcast channel named `flow-<flow id>` (`config: { private: true }` in `flowSync:join`). Private channels enforce RLS on `realtime.messages`, so the `can_access_flow_channel` / `flow_members_can_read_broadcast` / `flow_members_can_send_broadcast` policies in `schema.sql` are what restrict who can read or inject live edits — only a member of the flow's team. (When the channel was public, the flow UUID was the only secret, so anyone with the anon key and a flow id could join.) Incoming cell HTML from remote peers or AI/MCP writes is **sanitized** through an allowlist parser (`sanitizeCellHtml` in `FlowView.tsx`) before it touches any `innerHTML`, stripping scripts, event handlers, and non-formatting tags.

### Path safety
IPC handlers that read arbitrary file paths maintain a `trustedPaths` set — only paths originating from a file dialog or internally-generated temp files are accepted. This prevents a compromised renderer from reading arbitrary disk paths.

### File writes
JSON writes use a write-then-rename pattern (`db.json.tmp` → `db.json`) to prevent data loss on crash.

### Rate limiting
Two layers, because the Supabase anon key ships inside every installer — anyone can extract it and call Supabase directly, which makes any purely client-side throttle bypassable for the shared-backend surfaces.

- **App-level (electron/main.ts, `checkAuthRateLimit`)** — throttles `chat:signIn` (5/5min per email), `chat:signUp` (3/hour per email), and `chat:resetPassword` (3/hour per email — the most important one, since unthrottled this lets anyone email-bomb any address) using an in-memory `Map<string, timestamp[]>` keyed by `action:email`. Resets on app restart. This stops a bug or runaway retry loop in the app's own UI from hammering auth, but is not bypass-proof — enable Supabase's own **Authentication → Rate Limits** dashboard setting for the layer that actually can't be routed around.
- **Postgres-level (`supabase/schema.sql`, `rate_limit_events` table + `enforce_rate_limit()`)** — a generic security-definer function that logs an event and raises if the calling user (`auth.uid()`) has exceeded N actions of a given type in a trailing window, self-cleaning old events on each call. `BEFORE INSERT`/`BEFORE UPDATE` triggers call it for: team messages (20/30s), DM messages (20/30s), Impact Library submissions (5/hour — stricter, since it's shared content visible to every user, not a private chat), Impact Library edits (15/hour, guarded by `pg_trigger_depth() > 1` so the vote-count-refresh trigger's internal `UPDATE` on `impact_library` doesn't consume a random voter's edit budget), and Impact Library votes (60/hour, `BEFORE INSERT OR UPDATE` since the client upserts). Triggers fire regardless of which client made the request, so a client cannot skip the check by not calling it.
  - **`enforce_rate_limit` is not itself callable.** PostgREST exposes every `public` function as an RPC endpoint, and this one takes the action, cap, *and* window as parameters — so a signed-in user could call it directly with a near-zero window, and its own first statement (which deletes the caller's events older than that window) wiped their counter. `enforce_rate_limit('team_message', 999, interval '0')` reset every limit above. EXECUTE is now revoked from `public`, `anon`, and `authenticated`; the `rl_check_*` triggers are SECURITY DEFINER owned by `postgres`, so they still call it. The same revoke applies to the trigger functions themselves and to `refresh_impact_vote_counts`, none of which a client ever needs to invoke.
  - **`lookup_user_by_email` is rate-limited too** (30/hour) — it maps an email to a user id and display name, so unthrottled it was an account-existence oracle for any signed-in user.

### Tabroom monitor flow
Main process polls Tabroom every ~30s. On a new pairing, it fires parallel requests for judge paradigm (Tabroom scrape), OC disclosures (OC API), and DL stats. Results are bundled into a `TabroomRoundBrief` and sent to the renderer via IPC. `App.tsx` handles the event: deduplicates, upserts the opponent, creates the round, and navigates.

### AI call retries
**Scope: calls the user cannot retry themselves.** Every handler was audited against this rule, and exactly three still qualify: **`ai:summarizeFlowSheet`** (fires on tab hover, no button, falls back silently to the tag list), **`ai:crossExTraps`** (auto-runs from a `useEffect` when the drill opens), and **`chat:generateGeminiTitle`** (names a session in the background; the user never sees it run). Everything else — Auto Flow, Round Analysis, the card cutter, cross-ex questions and grading, card scoring, scouting summaries, Mission Brief, block suggestions, Impact Calc, the Outweigh game, the Impact Library, flow import, oversized-attachment summaries — renders its error next to a live retry control (a step the user is returned to, or an inline error beside the still-visible trigger), so it calls the model directly. ~100s of invisible backoff before showing an error the user could re-fire in one click is worse than failing fast. Decide the retry affordance when adding a new AI call; a call with one never gets `withDelayedRetry`. The three qualifying handlers wrap their call with `withDelayedRetry` (`electron/main.ts`, next to `fetchWithRetry`) — a generic `(fn: () => Promise<T>) => Promise<T>` wrapper, not tied to `callAI`'s signature, so it wraps `callAI(...)` and `callGeminiWithSearch(...)` calls alike at every one of the ~22 call sites across the file. On a thrown error it retries at **8s, then 30s, then 60s** (4 attempts total) before letting the error through. This sits ABOVE `fetchWithRetry`, which already retries a single transient HTTP 429/5xx inside one request — `withDelayedRetry` is for when a call is still failing after that, i.e. an extended outage or a bad response the model keeps producing.

On the renderer side, `electron/preload.ts` wraps every method on `api.ai` and `api.gemini` (not the raw `ipcRenderer.invoke` calls — the already-defined methods, once, in a loop) so a final failure — either a thrown error or a resolved `{ ok: false, error }` — dispatches a `window` `CustomEvent('warroom:ai-error', { detail: { source, message } })`. `AiErrorToast.tsx` (mounted once in `App.tsx`, alongside the Tabroom monitor toast) listens for that event and shows the message in a dismissible toast, auto-clearing after 7s. Because this can fire while the user is mid-round flowing, it is deliberately small and non-blocking: bottom-RIGHT corner (out of the flow's way), a single truncated line by default that expands to the full provider text on click, identical repeats collapsed into a `×N` counter on one toast instead of stacking, and at most 2 on screen at once. The original return value / thrown error still passes through unchanged, so every component's existing `if (!res.ok)` / try-catch handling keeps working exactly as before — the toast is purely additive, not a replacement for inline error UI.

**Truncation is never silent — neither direction.** Two failure modes used to be invisible. *Output*: every provider returns partial text when it hits its output cap, and `callAI` read it as a complete answer; it now checks each provider's own signal (`finishReason: MAX_TOKENS` / `finish_reason: 'length'` / `stop_reason: 'max_tokens'`) and throws `truncatedResponseError`, which callers must let propagate — the fix is sending less per call, not retrying. *Input*: prompts were capped with bare `text.slice(0, N)` calls, so a long document was quietly reduced to its first N characters and the user got a confident answer built on part of their evidence. Every such cap now goes through `await capForPrompt(text, limit, label)` (`electron/main.ts`), which **asks first and blocks**: it sends `ai:confirmTruncation` to the renderer and awaits the answer before the model is called at all. `TruncationConfirm.tsx` (mounted in `App.tsx`) shows the modal — "sending 60,000 of 412,000 characters (15%) of your flow" — with **Cancel** / **Send shortened anyway**. Declining throws, so the call never happens and no tokens are spent; the thrown message opens with `Cancelled —`, which preload matches to suppress the AI error toast (a deliberate cancel is not a failure, so only the feature's own inline message shows). Because one operation can cap several inputs (Round Analysis caps the flow, each uploaded doc, and the docs as a whole), asks arriving while the dialog is open are collected into the same dialog and answered together. `capForPrompt` being async is why call sites are hoisted out of `renderPrompt({...})` object literals and why `.map()` loops over cappable inputs became `for` loops. Where the work is genuinely batchable, batch instead of capping (see Auto Flow). Never cap the **assembled** prompt — that truncates the instructions off the end rather than the evidence; `ai:analyzeRound` used to do exactly that with a `prompt.slice(0, 120000)` stacked on top of its per-input caps, and no longer does.

**Long inputs — the user's choice, not a hard-coded one.** `app_settings.longInputAllowed` (default `false`) and `longInputMethod` (`'sample' | 'passes'`) drive `electron/longInput.ts`, read via `readLongInputPrefs()`. With the master switch off, an over-long input is capped and confirmed exactly as described above. With it on:

- **`'sample'`** — `splitFlowSummaryIntoSheets` cuts the flow at its `=== Sheet: … ===` headers, and `sampleSections` water-fills the budget so every sheet gets a share proportional to its size, with unused allowance redistributed (so many small sheets survive whole next to one huge one). Trimming is line-wise, never mid-card. `buildCoverageNote` then tells the model, per sheet, *how many cards it cannot see* — the unit a debater actually counts in — plus an explicit instruction never to call something dropped on a partially-visible sheet. That last part is the real fix: the old silent slice produced confidently wrong "they dropped this" claims about cards that were simply never sent.
- **`'passes'`** — `chunkSections` groups whole sheets into chunks (a sheet is never split, since half a position is worse than one oversized chunk), each chunk gets an `analyze_round_pass` call that takes dense factual notes, and `analyze_round` then runs over the concatenated notes with `INPUT_KIND` telling it it's reading notes rather than the flow. Per-pass progress goes out on `ai:analyzeRoundProgress`.

The trade-off is stated once, in `LONG_INPUT_DILEMMA`, and mirrored in the Settings copy so the two can't drift: sampling keeps the real text but not all of it; passes cover everything but the final call reasons over notes.

**The context-window hard stop.** `overContextLimit(prompt, modelId)` runs inside `callAI` *before* the request. `CONTEXT_LIMITS` maps model-id prefixes (longest match wins) to conservative input capacities, with `DEFAULT_CONTEXT_LIMIT` for anything unrecognised including local LM Studio models; `estimateTokens` uses 3.5 chars/token, deliberately low so a flow's dense bracketed lines don't under-estimate. Over the limit throws a message naming the real token counts, stating that nothing was sent, and pointing at the setting. The provider would 400 on this anyway — doing it locally means the user hears it in their own terms and spends nothing. No toggle bypasses it.

**The toast shows the provider's exact error, not a paraphrase.** `geminiHttpError`/`openaiHttpError`/`anthropicHttpError`/`grokHttpError` (`electron/main.ts`) each parse that provider's own error JSON and build the thrown `Error` from its real `message` plus HTTP status and status/type/code (e.g. `Gemini [429 RESOURCE_EXHAUSTED]: You exceeded your current quota...`), falling back to a Warroom-authored generic sentence only when the body isn't parseable JSON. That text flows unmodified through `withDelayedRetry` → the handler's `sbErr(e.message)` → preload's dispatch → the toast. This is deliberately separate from `humanizeGeminiError()` (`src/utils/geminiError.ts`), which several components (`AutoFlow.tsx`, `CardCutter.tsx`, `AnalyzeRound.tsx`, `MissionBrief.tsx`, `GeminiPanel.tsx`) call on the RENDERER side to paraphrase the same error into something friendlier for their own inline error UI — the toast answers "what actually happened," the humanized inline message answers "what should I do."

**Deliberately not wrapped:** `api.chat` (mixes `geminiAgentTurn` with plain Supabase message/DM CRUD — wrapping the whole namespace would toast on something like a failed "delete message"). The agent chat turn (`chat:geminiAgentTurn`) already has its own error channel (`onGeminiError`) and its tool-call loop can have side effects (saving a card, opening a panel, etc.), so blindly retrying-and-toasting the whole turn isn't a safe fit — a user can just resend a chat message themselves. `agent:fetchArticle` is a plain webpage fetch, not a model call, so it's out of scope entirely.

## NSDA Topics

Warroom monitors **speechanddebate.org/topics/** for the latest Policy, Public Forum, and Lincoln-Douglas resolutions.

### Topic monitor
- On every app launch, Warroom checks whether a new topic has dropped and updates stored data.
- PF and LD topics drop on known dates (Aug 1, Oct 1, Dec 1, etc.) at 9:00am CT. The app polls aggressively only on release days — up to every 2 minutes in the 30-minute window after release time.
- When a new topic is detected, a **desktop notification** fires immediately. Clicking it opens the Topics screen.
- A vivid **in-app banner** appears at the top of the window (amber for PF, red for LD) with a pulsing indicator and the full resolution text. It persists until dismissed.

### Topic brief
- When a new topic drops, an AI-generated brief is automatically requested. It covers: resolution breakdown, Aff/Neg arguments, frameworks, core clash, research priorities, and pitfalls.
- The brief can be regenerated at any time from the Topics screen.
- Requires an AI provider configured in Settings → AI API key — any of them, including LM Studio (local, no key needed).
- Generated by `generateTopicBrief`, routed through `callAI(prompt, 'balanced', ...)` like every other AI feature — it used to be a standalone hardcoded Gemini `generateContent` call, which meant it silently did nothing for non-Gemini users. Failure is swallowed on purpose (`console.error` only): this fires automatically in the background when a topic changes, with no user-facing action to attach an error toast to. Prompt template: `electron/prompts/topic_brief.txt`.

### Policy topic context
The current Policy topic is injected into every Warroom AI conversation as system context, so the agent always knows what resolution is being debated without you needing to state it.

## AI Prompts

Every prompt Warroom sends to an AI provider (Gemini/OpenAI/Anthropic/Grok) is extracted into its own plain-text template file, using the exact same bundled+user-override architecture as skills.

### Loader (electron/main.ts)
- `userPromptsDir()` → `<userData>/warroom/prompts/`
- `bundledPromptsDir()` → `electron/prompts/` in dev, `resources/prompts/` when packaged (via `electron-builder.yml` `extraResources`)
- `listPrompts()` — lists bundled + user `.txt` files; user overrides bundled by name; each entry carries a short human `label` from `PROMPT_LABELS`
- `readPromptTemplate(name)` — sanitizes `name`, checks the user dir first then bundled, returns raw file contents or `null`
- `renderPrompt(name, vars)` — loads a template and substitutes every `{{KEY}}` token with `vars[KEY]`; **throws** if the template is missing or if a placeholder has no matching var (a missing placeholder is treated as a bug, not silently ignored)
- `ensureUserPromptFile(name)` — seeds the user-editable copy from the bundled default on first access (if it doesn't already exist) and returns its absolute path

### IPC / preload
- `prompts:list` → `{ ok, prompts: { name, source, label? }[] }`
- `prompts:openInEditor(name)` → calls `ensureUserPromptFile` then `shell.openPath(path)` so it opens in the OS's default text editor
- Exposed on the renderer as `window.warroom.prompts.{list, openInEditor}`

### Call sites
Every `callAI` / `callGeminiVision` / `callGeminiWithSearch` invocation in `electron/main.ts` (including `generateTopicBrief`, now routed through `callAI` like everything else) and the agent's `AGENT_SYSTEM` / `AGENT_TITLE_SUFFIX` strings build their prompt via `await renderPrompt('<name>', { PLACEHOLDER: value, ... })` instead of an inline template literal. Dynamic content (document text, names, dates, computed helper strings like `affSection`/`judgeSection`) is passed in as `{{PLACEHOLDER}}` values; static instructional wording lives only in the `.txt` file. Two prompts, `cx_shared_rules.txt` and `cx_side_guidance.txt`, are shared blocks referenced by several cross-ex prompts via `{{CX_SHARED_RULES}}` / `{{CX_SIDE_GUIDANCE}}` rather than duplicated.

One exception: `chat:generateGeminiTitle`'s prompt (chat session title generation) is still an inline template literal in `main.ts` — its extraction was blocked by the local security tooling (the prompt's "User: … Assistant: … Title:" scaffolding pattern-matched a prompt-injection heuristic) and needs a human to authorize the file write.

### Editing a prompt
Editing `<userData>/warroom/prompts/<name>.txt` (or triggering the seed-then-edit flow via any "View/edit this prompt" link in the Documentation page) changes what gets sent to the AI on the **very next call** — no rebuild or restart needed. Deleting the user override falls back to the bundled default again.
